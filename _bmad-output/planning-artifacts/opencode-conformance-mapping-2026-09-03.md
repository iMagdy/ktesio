**Purpose:** prove the Adapter Contract is not Hermes-shaped before Story 6-6 freezes v1, by walking **every** contract surface — the [`AgentAdapter`](../../crates/ktesio-adapter-api/src/adapter.rs) trait, every `adapter.toml` manifest section, and all 8 TCK section ids — to opencode, recording change proposals (`CP-6.5-<letter>`, format of CP-6.1, proposals only, nothing applied), and closing with the explicit contract-freeze-risk list Story 6-6 must resolve. This story applies **nothing**: no CP application, no `CONTRACT_VERSION` bump, no code, no live-opencode integration.

**Dispositions:** every surface below carries exactly one of —
- **mapped** — opencode has a real structural counterpart; the contract surface is exercisable against it;
- **not_applicable** — opencode's actual structure gives the surface nothing to exercise (reason stated from structure, not convenience);
- **freeze risk (R#)** — the surface cannot be disposed of honestly until Story 6-6 decides; cross-referenced in the closing list.

**Coverage column (FR-29):** each row names who covers the axis — **opencode**, **Hermes** (per `hermes-agent-verification-2026-08-25.md`), and/or **mock/TCK-probe-only**. An axis covered only by the mock is exactly the Hermes-shape hole FR-29 exists to close.

## 5. Change proposals (`CP-6.5-<letter>`, CP-6.1 format — proposals only, nothing applied)

**CP-6.5-a — interaction channel vocabulary is Stdio-only; opencode's real channel is HTTP.**
- **Finding:** `InteractionChannelKind` has exactly one variant, `Stdio` (`crates/ktesio-adapter-api/src/manifest.rs:138`), and the schema's own doc reserves the extension point: "A future channel … adds a second variant only once a real second implementation exists" (manifest.rs:127-135). opencode is that real second implementation candidate: its programmatic surface is `POST /session/:id/message` + SSE + `/tui/*` over HTTP (characterization §6), and a spawned `opencode serve` never reads stdin (`serve.ts:13-23`).
- **Proposed contract change:** add a second variant `InteractionChannelKind::Http` in the 6-6 freeze (or explicitly document in v1 that opencode-class agents run interaction out-of-band — but see the registration-bar collision below), with the engine continuing not to branch on the channel until an adapter actually delivers through it. An additive minor bump under the 0.x semver policy, mirroring story 4-1's own reasoning.
- **Registration-bar collision with the "declare unsupported" fallback:** leaving the channel Stdio-only and declaring opencode's `interaction` unsupported on every OS does **not** yield a legal manifest today: if interaction is the adapter's only capability key, a declaration whose every entry is `unsupported` fails `CapabilityDeclaration::has_any_support` (`crates/ktesio-adapter-api/src/capability.rs:153-159`) and is rejected by manifest validation ("it declares no supported capabilities", `crates/ktesio-adapter-api/src/manifest.rs:333-341`) — an **unregisterable adapter**. Option (ii) is therefore not equivalent to option (i); making it legal would itself require a second contract change (relaxing `has_any_support`, e.g. to admit a "channel-pending" declaration), and 6-6 must choose knowingly between: (i) add `Http` (opencode registers with a supported interaction), (ii) relax the viability bar and let opencode register interaction-unsupported, or (iii) keep the bar and route opencode's supported capability through some other declared axis — none of which is free.
- **Affected crate/types:** `ktesio-adapter-api` `manifest::InteractionChannelKind` (+ `as_str`/`Display` arms, the `from_toml_str` section-attribution chain at manifest.rs:253-267), `docs/manifest.md`; option (ii) would additionally touch `capability::CapabilityDeclaration::has_any_support`. **6-6 decides; this story applies nothing.**

**CP-6.5-b — normative meaning of an omitted stop template.**
- **Finding:** opencode has no stop/restart/status verbs (characterization §3); a manifest `[lifecycle]` requires only `start` (manifest.rs:318-327), so an opencode manifest legitimately omits `stop`. The contract nowhere states what an omitted stop *means* (Hermes needed a template; opencode must not).
- **Proposed contract change:** document in the lifecycle section: an omitted `[lifecycle.stop]` means the engine's process termination is the normative stop; adapters whose agents own graceful-stop verbs declare templates. TCK `lifecycle` asserts stop = child process exit (tree-kill parity per CP-6.1-c).
- **Affected crate/types:** none (documentary) — `docs/manifest.md`, `ktesio-conformance` lifecycle-section docs.

**CP-6.5-c — `self-reported` must cover adapter-implemented shims, not only agent-native output.**
- **Finding:** the metering module describes the channel as "the agent emits `KTESIO_USAGE {json}` sentinel lines on its stdout" (`crates/ktesio-adapter-api/src/metering.rs:10-33`) — accurate for Hermes-shaped agents, but opencode never emits sentinels; its usage is reachable only by tailing agent surfaces (SSE `message.updated`, `GET /session`) (characterization §5). The contract text, read literally, implies agents natively emit; a shim adapter synthesizes the same wire form from agent APIs. The `sequence` replay-dedup key needs a defined provenance for shims (agent message ordinals).
- **Proposed contract change:** one documentary paragraph in the metering section: the `self-reported` channel is adapter-implemented; the sentinel stream may be produced by an adapter shim over the agent's own usage surfaces, with `sequence` derived from the agent's per-Run message ordinals. No type change (the wire form is unchanged).
- **Affected crate/types:** none (documentary) — `ktesio-adapter-api` `metering` module docs, `docs/manifest.md`.

**CP-6.5-d — config File target is TOML-bound AND Agent-Home-placed; opencode's native config is JSON at an XDG root.**
- **Finding:** the File-target blocker has **two halves**. Format: `ConfigTarget::File` renders "a TOML document at `path`" (`crates/ktesio-adapter-api/src/config.rs:71-75`); opencode reads `opencode.json` (JSON/JSONC) (characterization §4). Placement: a `FileTarget` renders to a path **relative to the Ktesio-owned Agent Home**, with the engine as sole writer (`config.rs:78-104`, AD-6), while opencode reads its config from its **XDG-bound root** (`${XDG_CONFIG_HOME:-~/.config}/opencode/`, `packages/core/src/global.ts:13` @ `4b7e19e`) — a rendered file lands where opencode never looks unless the adapter *also* points `XDG_CONFIG_HOME` into the Agent Home. The two halves connect **only through CP-6.5-f's XDG pointer**: File-target delivery for opencode = CP-6.5-f + a format fix, jointly.
- **Proposed contract change:** bless **env-content delivery as the documented pattern for JSON-config agents** (opencode's `OPENCODE_CONFIG_CONTENT` accepts the whole runtime config as an env value — zero contract change, and it sidesteps the placement half entirely), and *reserve* an additive `FileTarget` format qualifier for post-v1 if a second JSON-file consumer appears. Recommend option (i) for v1. Delivery-honesty rider: opencode's `{env:VAR}` substitution replaces an **unset var with an empty string, silently** (<https://opencode.ai/docs/config/>; `config/variable.ts:33-36` @ `4b7e19e`), so any Ktesio delivery that renders `{env:VAR}` templates must guarantee every referenced var is set — or fail the render — before the child launches; the contract's config section should state that requirement for adapters to substitution-based agents.
- **Affected crate/types:** none for (i) (documentary); (ii) would touch `ktesio-adapter-api` `config::FileTarget` — reserved, not proposed for the freeze.

**CP-6.5-e — adapters to self-updating agents must pin updates off (and supervisor config is authoritative only absent managed config).**
- **Finding:** opencode auto-downloads updates at startup unless `autoupdate = false` or `OPENCODE_DISABLE_AUTOUPDATE` (`cli/upgrade.ts:9-14` @ `4b7e19e`; docs: "OpenCode will automatically download any new updates when it starts up"). A supervisor that owns the binary path cannot tolerate the binary replacing itself mid-fleet. **Authority caveat (re-verified at the pin):** supervisor-delivered config rides *below* the enterprise tail of the merge chain — `OPENCODE_CONFIG_CONTENT` merges before the managed dir's `opencode.json`/`opencode.jsonc` (`config.ts:530-536`) and macOS MDM preferences, which the source comments "override everything" (`config.ts:538-547`). On a machine with managed config, an enterprise file can override the supervisor's `autoupdate = false` (or re-point providers), silently re-arming exactly the behavior this CP pins down.
- **Proposed contract change:** documentary requirement in the config section: an adapter for a self-updating agent MUST map the agent's update-disable mechanism (env or config) and the start seam MUST deliver it; the adapter docs must additionally state whether the agent's config chain contains a higher-authority (managed/MDM) layer that can override supervisor-delivered values, so an operator on a managed machine can verify the pin survived. Candidate TCK `config_mapping` assertion (a mapping exists for the agent's update pin when the agent self-updates — knowable from adapter docs).
- **Affected crate/types:** none (documentary) — `docs/manifest.md`, `ktesio-conformance` config section docs.

**CP-6.5-f — name opencode's isolation keys (the CP-6.1-e analogue).**
- **Finding:** opencode's data/config roots resolve through `xdg-basedir` — `${XDG_DATA_HOME:-~/.local/share}/opencode` (`packages/core/src/global.ts:2-11` @ `4b7e19e`) — so `XDG_DATA_HOME`/`XDG_CONFIG_HOME` are the per-instance isolation levers, exactly as `HERMES_HOME` was for Hermes (CP-6.1-e). Unlike `HERMES_HOME`, they are **not documented interfaces** (characterization §7/§10 axis 2).
- **Proposed contract change:** name `XDG_DATA_HOME` + `XDG_CONFIG_HOME` as opencode's canonical isolation keys in the adapter docs, with the explicit churn caveat (undocumented lever; re-validate per pinned release). Pairs with R6 (undocumented-lever standing) and underpins R9 (per-instance roots are what makes shared-root concurrency moot).
- **Affected crate/types:** none (documentary) — `docs/` adapter notes only.

**Completeness check:** CP ids are sequential from `CP-6.5-a` through `CP-6.5-f`; each proposes without applying; none touches the memory wire vocabulary (R3 carries the memory findings as input only, per the story's Ask-First boundary).

## 6. Contract-freeze risks (for Story 6-6 — every unresolved axis, none silently absorbed)

Each entry: the axis, the evidence gap, and the decision 6-6 must make before tagging contract v1.

**R1 — Interaction channel vocabulary.**
Axis: `[interaction]`/`Capability::Interaction` vs opencode's HTTP-native sessions.
Evidence gap: the contract's only channel is Stdio (manifest.rs:138); opencode's stdin is never read; its real surface is `POST /session/:id/message` + SSE (characterization §6). No honest manifest value exists for opencode today — and the naive fallback is illegal: declaring `interaction` unsupported on every OS leaves a single-capability declaration that fails `has_any_support` (capability.rs:153-159) and manifest validation (manifest.rs:333-341), i.e. an unregisterable adapter (see CP-6.5-a).
Executable TCK legs by option: (i) **add `InteractionChannelKind::Http`** — the vocabulary lands, but **no interaction leg is executable against opencode** without a further engine change: the engine never branches on the declared channel (the AD-12 stdin pipe is unconditional, manifest.rs:158-172) and `send_input` writes the child's stdin, so HTTP delivery needs a real engine-side send implementation beyond this CP; (ii) **stay Stdio-only** — the applicable leg is the **unsupported fail-fast probe** (`send_input` must fail typed, never hang), which opencode-as-manifest-adapter exercises honestly, but option (ii) requires first relaxing `has_any_support` (a separate contract change) or giving opencode a different supported capability to carry registration.
Decision 6-6 must make: which option (i / ii + viability-bar relaxation / iii-other-supported-axis), and — for (i) — whether the engine gains a real HTTP send_input implementation in v1 or the channel is declared-but-unimplemented with the TCK leg deferred. The decision fixes the opencode `[capabilities].interaction` level and `[interaction].channel` value.

**R2 — Metering source declaration for opencode.**
Axis: `[metering]` / `AgentAdapter::metering_source`.
Evidence gap: both contract variants are structurally viable at the pin (shim → self-reported; `options.baseURL` loopback → engine-observed); the FR-19 guarantee ("delayed batches reconcile without double-counting") holds differently for each (shim dedup rides `sequence`-as-message-ordinal; loopback is inherently per-request).
Decision 6-6 must make: name the normative v1 path for opencode-class agents in the metering section, and state which FR-19 reconciliation guarantee binds for each variant.

**R3 — `memory.dir` applicability for memory-less agents + the `GuaranteeLevel` wire form.**
Axis: TCK `memory` section / reserved engine key `memory.dir` / `GuaranteeLevel` (engine-API-only).
Evidence gap: opencode has no native consumer for a memory directory (characterization §7); `memory.dir` delivery would be a silent no-op — the ratified "unmapped key is delivered NOWHERE" decision ("Decision 6": `crates/ktesio-adapter-api/src/adapter.rs:84-86`; restated for the engine key at `crates/ktesio-engine/src/domain/config.rs:139-141`). `GuaranteeLevel`'s wire form was explicitly deferred to 6-6 with the `--json` memory surface — the deferral and the transferred DC-6 "ONE intentional announced key-set edit" obligation are ratified at `_bmad-output/planning-artifacts/epics.md:600` (Story 5-2, Q-1/Q-2) and restated as a binding 6-6 AC at `epics.md:614`.
Decision 6-6 must make (input only — this note proposes no memory vocabulary): whether v1 permits adapters that cannot consume `memory.dir` (and what the public backing read then reports), and the wire form of `GuaranteeLevel` + the deferred `--json` memory surface, with the DC-6 announcement.

**R4 — Stop verification without an exit-code contract.**
Axis: TCK `lifecycle` stop leg / `[lifecycle].stop` optionality.
Evidence gap: opencode documents no exit codes or signal handling (characterization §10 axis 1); stop is engine-side process termination. The TCK must assert *something* about stop; the contract currently doesn't say what (graceful acknowledgment vs child exit vs tree-kill).
Decision 6-6 must make: bless CP-6.5-b's normative "omitted stop = engine signal-stop; TCK asserts child exit," and decide whether any graceful-stop acknowledgment concept enters v1 (Hermes' exit-75 handoff is the counter-example).

**R5 — Config File target format binding.**
Axis: `[config]` file rules vs JSON-config agents.
Evidence gap: `FileTarget` renders TOML only (config.rs:71-75); opencode needs JSON; env-content delivery (CP-6.5-d option i) fully covers opencode but leaves the file path unexercisable for it.
Decision 6-6 must make: bless env-content delivery as the documented pattern for v1 and record the format-qualified file target as reserved, or add the qualifier to v1.

**R6 — Undocumented isolation levers.**
Axis: `[config]` isolation keys for opencode (`XDG_DATA_HOME`/`XDG_CONFIG_HOME`).
Evidence gap: the levers work at the pin by construction (`xdg-basedir`) but are not documented interfaces; they can move without a docs-visible deprecation (characterization §10 axis 2). `OPENCODE_TEST_HOME` is test-only.
Decision 6-6 must make: whether undocumented env levers are acceptable isolation keys for contract v1 (with a per-release re-validation obligation), or whether isolation keys must be documented agent interfaces.

**R7 — Usage honesty (unknown vs zero).**
Axis: metering honesty semantics across sources.
Evidence gap: Hermes labels cost honesty (`CostStatus ∈ {actual, estimated, unknown}`); opencode silently coerces missing usage to zero (`session.ts:339-340,363-400` @ `4b7e19e`) — no docs statement, no label. The contract currently says nothing about what a `self-reported`/`engine-observed` source must do when the provider omits usage.
Decision 6-6 must make: whether contract v1 takes a stance on unknown-usage reporting (any vocabulary is 6-6's to add — this note records only the gap and the two real-agent precedents).

**R8 — Readiness depth and endpoint discovery.**
Axis: TCK `lifecycle` start/readiness leg (characterization §10 axis 4 + the port-discovery fold from review).
Evidence gap: `GET /global/health` returns a constant `healthy: true` plus version — it proves process liveness, not per-instance readiness (provider auth validity, instance routed); and the endpoint itself moves: the default port *prefers* 4096 then **silently** falls back to any free port (server.ts:117-122), the manifest `OpTemplate` is a verbatim exec/args/env copy with no substitution (manifest.rs:94-103), and no unified key carries a port — so a supervisor that must know where the child listens cannot assume 4096 and cannot template it; today it must parse the child's startup line ("opencode server listening on http://<host>:<port>", `serve.ts:20`) or pin `--port` and own collision handling.
Decision 6-6 must make: whether contract v1 defines a readiness concept distinct from liveness (and what an adapter must declare about its health surface's semantics), and how endpoint discovery is normative — pinned `--port` with engine-owned collision error, or startup-line parsing as a documented adapter convention.

**R9 — Concurrent-instance safety on shared data roots.**
Axis: isolation keys (CP-6.5-f) / TCK `memory`-adjacent state isolation (characterization §10 axis 5).
Evidence gap: sessions/state are per-XDG-root SQLite; docs are silent on two servers sharing one data dir; the only in-source hint is a global file-lock primitive initialized over the state root (`Flock.setGlobal({ state })`, `packages/core/src/global.ts:33` @ `4b7e19e`) with no documented concurrency guarantee.
Decision 6-6 must make: whether contract v1 mandates per-instance isolated data roots (each instance's `XDG_DATA_HOME`/`XDG_CONFIG_HOME` inside its own Agent Home, making shared-root concurrency out of contract scope), or whether any shared-root mode is admissible and under what stated caveats.

**R10 — Agent-side abort vs contract stop (in-flight teardown guarantees).**
Axis: TCK `lifecycle` interruption/stop legs vs opencode's `POST /session/:id/abort` (characterization §10 axis 6).
Evidence gap: opencode's abort — "Abort an active session and stop any ongoing AI processing or command execution" (`groups/session.ts:253-263`, description at `:262` @ `4b7e19e`) — ends one session's work inside a still-running server, but the docs specify no teardown guarantee for in-flight tool subprocesses, and abort is not a contract verb (the contract's verbs are start/stop/pause/resume).
Decision 6-6 must make: whether agent-side abort is declared out-of-contract (engine-owned termination semantics only, with the TCK asserting process-level outcomes), or whether adapters to abort-capable agents should map abort as an interruption surface — and, if the latter, what `send_input`-initiated interruption promises (ties to R1's legs).

**R11 — Per-OS declaration stance for WSL-recommended agents.**
Axis: TCK `capability_edges` / per-OS Capability Declaration on Windows (characterization §10 axis 7).
Evidence gap: opencode's Windows story is "run via WSL for the best experience"; native-Windows behavior has no supported-behavior matrix in the docs, so any native-Windows support level an adapter declares would be best-effort at best — yet the contract lets an adapter declare `guaranteed` on windows with nothing checking the claim against agent reality.
Decision 6-6 must make: whether contract v1 constrains per-OS declarations for agents whose vendor recommends a compatibility layer (e.g. a docs requirement, or TCK guidance, that windows levels for such agents are capped at `best-effort`), or leaves per-OS honesty entirely to the adapter author.

**Freeze-risk count: 11 (R1–R11).** Per-section carrying: `interaction` (R1), `metering_self_reported`/`metering_engine_observed` (R2, R7), `memory` (R3, R9), `lifecycle` (R4, R8, R10), `config_mapping` (R5, R6), `capability_edges` (R11) — seven of the eight TCK sections carry at least one freeze-risk decision; `pause` carries none (its disposition is settled: not_applicable, unsupported-everywhere declaration). Mapped-clean surfaces (no risk): the `capability_edges` declaration→projection machinery, `kind()`, `start()` spawn/readiness mechanics, the manifest-adapter pause/resume omission path, `contract_version`/`[adapter]` manifest plumbing, and the env/flag halves of `config_mapping`.
