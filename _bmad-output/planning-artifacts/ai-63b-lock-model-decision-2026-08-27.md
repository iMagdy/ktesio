# AI-63(b) — Engine Concurrency Model Decision

**Winston (System Architect) · 2026-08-27 · verified at HEAD `12e3fec`**

---

## 1. Recommendation

**Adopt per-instance serialization with a short-hold store gate** — demote `Mutex<Registry>` to a gate held for the duration of *one store call* and never across FS/fork/wait work, and replace `Mutex<Supervisor>` with a name-keyed `InstanceCell` that every check-then-act sequence takes for exactly one instance — **grafted with the enforcement layer from the "Enforced AD-17" proposal and the measure-first instrumentation from the "Staged Hybrid" proposal**, because per-instance locking on its own re-scopes the debt without bounding it and deletes the social forcing function that has been enforcing AD-17.

### Where the judges disagreed, and how I resolved it

The three lenses produced three different winners:

| Lens | 1st | 2nd | 3rd | 4th |
|---|---|---|---|---|
| Correctness / race-safety | **Lattice** | Enforced AD-17 | Actor | Staged Hybrid |
| Epic 7 daemon + NFR-4 | Actor | **Lattice** | Staged Hybrid | Enforced AD-17 |
| Migration cost / testability | Enforced AD-17 | Staged Hybrid | **Lattice** | Actor |

The Lattice is the only model that is never last, and it is 1st, 2nd, 3rd. That alone is suggestive, not decisive. What decides it:

**I weight the correctness lens highest.** Three reasons, in order:

1. **This engine's product is a ledger and a lifecycle.** The failure mode of a wrong answer here is a silent billing under-count or a phantom enforcement — errors with no observable signal, on a system whose entire value proposition is "you can trust the token and dollar numbers." A latency regression announces itself; a ledger regression does not. AD-7's single-writer + read-your-writes property is the highest bar and the correctness lens is the only one that scores against it.

2. **The Epic 7 lens partly disqualified itself as a discriminator.** Its own verdict is that *no* candidate's lock model is the binding NFR-4 constraint — the binding constraint is unbounded SQL (`usage_totals` at `store/sqlite.rs:651` and `cost_totals` at `:688` are full row scans of `usage_events WHERE instance_id = ?`, with no rollup table anywhere in the schema at `sqlite.rs:56-146`) plus a duplicated config fold (`fleet_entry_for` calls `effective_config` twice per instance with identical arguments, `engine.rs:485` and `:523`). Both are model-independent. Once the largest NFR-4 term is removed from the comparison, that lens separates the models much less than its ranking implies.

3. **Two of the three cheapest options had their central mechanism refuted against source.** I re-verified both refutations myself:
   - **Enforced AD-17's lease is not implementable as described.** `self.backend.stop(&mut supervised.handle, window)` (`supervisor.rs:~1128`) is *one call* owning `&mut handle` for the entire SIGTERM→wait→SIGKILL→confirm window; you cannot release the lock across it without moving the handle out of `running`. And its stated safety net does not cover the normal path: `poll_once`'s reconcile is gated on `stop_unconfirmed` (`supervisor.rs:1821-1823`), and the non-stuck branch does `self.running.remove(&name); continue;` (`:1844-1845`) — silently dropping the `Supervised` out from under a Phase C that would then never run PR #126's rescue drain.
   - **Staged Hybrid's Stage 1 is unsafe as scoped.** Its `EnforcementPlan` carries no run id, and it justifies deferred execution by citing the restart precedent — which holds only because `(Running, Start)` is an invalid row. But `transition.rs:132` is `(Running, Stop) => Ok(Stopping)`. A breach recorded against Run X, executed one tick later, will legally kill Run Y.

The migration-cost lens is a **schedule argument, and I treat it as one.** It is correct that Enforced AD-17's Steps 0-3 change zero `Supervisor` signatures and that is genuinely the largest cost driver in the tree. But that proposal's own author states plainly that without its Layer 3 lease it does not survive Epic 7's daemon lifetime — and the lease is the part that does not compile. A cheaper change that does not reach the requirement is worth less than a more expensive one that does.

**Why not the Actor model**, which won the Epic 7 lens and which I agree is the better *whiteboard* design: it claims all eight AD-17 invariants preserved and silently drops the tier-2 envelope. `Registry::attach_memory` (`registry.rs:612-663`) is lookup → `ensure_terminal_for_memory_backing` → conflict check → dir create → `upsert_memory_backing`, and `start_inner` reads `registry.memory_backing(&name)` at `supervisor.rs:626`. Leave attach on a guard-free store handle while actors drive lifecycle and you get the AD-11 hot-swap the terminal guard exists to forbid. The Lattice proposal spotted this class and paid for it by deliberately putting `set_config`/`attach_memory`/`detach_memory`/`instance_status` under the cell. Separately, the Actor's silent-actor-death mode is an unbounded, silent billing under-count on a live billable agent — the single worst failure in the set under a ledger-first lens, and it is framed only as an orphan hazard.

### The grafts, named with their sources

| Graft | Source | Why |
|---|---|---|

| Mailbox / `Busy` backpressure | Actor — **deferred, not adopted** | Named in AD-18 as the successor if 7.6 lands with concurrent host load. Callers block on a cell here; that is the honest limitation. |

## 2. AD-18 draft (append to `ARCHITECTURE-SPINE.md` after AD-17)

### AD-18 — Per-instance serialization with a short-hold store gate, mechanically enforced
- **Binds:** every engine operation; supersedes AD-17's coarse-lock Rule while keeping its bounded-work rule verbatim; NFR-1, NFR-4; AD-5, AD-6, AD-7, AD-11, AD-13; Epic 7 stories 7.1–7.5; resolves AI-63(b)
- **Prevents:** the AD-17 bug class surviving its own fix. Per-instance locking, taken alone, re-scopes an unbounded operation's blast radius from twenty-five instances to one and thereby deletes the argument that has actually been enforcing AD-17 in review — "this stalls the whole fleet" ends a conversation; "this only stalls one instance" is precisely the rationalisation the rule exists to defeat. It also prevents the *second* failure the coarse model was masking: a partition that re-establishes atomicity only for the operations someone happened to enumerate, leaving the registry-lock-only tier — `register_with_adapter`'s row-then-home sequence (`registry.rs:328-385`), `attach_memory`'s terminal-state guard (`registry.rs:612-663`) racing `start_inner`'s `memory_backing` read (`supervisor.rs:626`), `set_config` racing start's two `effective_config` folds, `Registry::remove`'s running-guard — silently unserialized.
- **Rule:** engine state is serialized **per Agent Instance**, not per fleet. `EngineInner` holds four things: an `Arc<EnginePaths>` reachable with no lock at all; a `StoreGate` (the surviving `Mutex<Registry>`, whose guard is **never yielded to a caller** and is held for the duration of **one store call** and no longer); a `Mutex<HashMap<InstanceName, Arc<InstanceCell>>>` held only for an O(1) get-or-insert; and a lock-free `SupervisorShared` (backend, backoff, runtime handle, usage source — all already `&self`-shaped). **A cell is keyed by a well-formed instance NAME, not by a registered instance**, created on first reference and never evicted (a removed name goes `Retired`, a re-`register` flips it back), so `register`/`register_with_adapter` and `remove` take the cell for the whole row-plus-home sequence and a concurrent `start` can never observe a `registered` row with no Agent Home. **Every check-then-act sequence takes exactly one cell and holds it for the whole sequence** — `start`, `stop`, `pause`, `resume`, `send_input`, `remove`, `register`, `set_config`, `attach_memory`/`detach_memory`, `instance_status`, and the reaper's per-instance poll. Lock order is total and store-innermost — **cells-map > cell > store gate** — with two absolute rules: the store gate is never held while acquiring anything else, and **no code path ever holds two cells**. The domain layer stays lock-free: it receives `&StoreGate` and `&mut InstanceState` and cannot name a lock, which makes the six-frame enforcement chain (`ingest_usage` `:2561` → `enforce_budget` `:2634` → `apply_breach` `:2762` → `enforce_stop` `:2833` → `stop_with_cause` `:980` → `stop_inner` `:995`) unable to self-deadlock by construction rather than by discipline. **AD-17's bounded-work rule survives verbatim and is now mechanically enforced**, with three additions that are themselves binding. (i) A bound is not a budget: every lock scope declares a hold-time budget in code, and a `debug_assertions` overrun **panics** naming op, elapsed and budget — `DEFAULT_STOP_WINDOW` (30s) and `read_agent_log`'s 3×10MB are *bounded* and both blow NFR-4's <1s read budget, so "bounded" alone no longer discharges the rule. (ii) The ~17 inventoried sites move into `.ad17-debt.txt`, gated by a fourth grep-with-allowlist step in the existing `boundary` CI job (alongside AD-2 `ci.yml:240`, AD-4 `:270`, AD-8 `:308`); the entry count **may only fall**, a hit absent from the file fails the build, and a stale entry must be deleted rather than left. (iii) Sanctioned under-lock I/O lives in `bounded.rs`; raw `std::fs::read`/`read_to_string`/`remove_dir_all`/`create_dir_all` and bare `child.wait()` are refused anywhere lock-reachable. **Three further prohibitions, each derived from a defect found while deciding this.** (a) **Enforcement is instance-scoped or it is redesigned:** AD-7's single-writer becomes *sole writer per instance*, valid only because `record_usage_event` (`sqlite.rs:583`) is a single-statement autocommit insert and every enforcement read is `WHERE instance_id = ?` — a fleet-wide budget, a global concurrency cap, or any cross-instance ordering **breaks this partition and requires an explicit global section and a new proof; it may not be added incrementally**. (b) **Any deferred action carrying enforcement MUST be run-id guarded**, because `transition.rs:132` is `(Running, Stop) => Ok(Stopping)` — the transition table does *not* reject a stale Stop, so the "harmless no-op" reasoning that makes off-lock restart safe (`engine.rs:192-193`) does **not** transfer to breach enforcement. (c) **The usage cursor and its ingest may never be separated by a lock release**: advancing `usage_cursor` in one critical section and committing in another strands bytes on any failure between them — the H1 billing under-count class PR #126 closed. Event fan-out for FR-33/Story 7.2 is emitted at the transition site *while the cell is held* (which is what buys per-instance ordering for free) and **must be a non-blocking `try_send` with an explicit drop-or-lag policy** — a blocking send under a cell is this AD's own bug class at instance scope. Callers **block** on a cell rather than enqueueing; this is a recorded limitation, not an oversight — if AI-20's Story 7.6 daemon is ratified with concurrent host load, or if measured 7.5 p99 read latency exceeds budget under contention, the successor is a mailbox/actor per supervised instance, and **that measurement, not an argument, reopens this decision**.

## 3. Staged migration plan

Each step is independently shippable and independently revertible. The risk asymmetry is the point: **Steps 0–4 keep the coarse locks physically in place**, so no new interleaving is representable and a compile error is the only failure mode. Step 5 is a few hundred lines carrying nearly all the semantic risk.

### What must land before Epic 7 opens

**The decision itself is discharged by AD-18** — AD-17 requires the model *decided*, not implemented. But the gate exists to stop a third story walking into the class, and a ratified-but-unenforced AD does not do that. So:

- **Blocking Epic 7: Steps 0, 1, 2.** These carry zero interleaving risk, need no ratification beyond this document, and are what make an Epic 7 story compliant *by construction* rather than by the author remembering to read the spine. Roughly a week.
- **Step 3 and 4** should land alongside them if Epic 6's tail permits; they are mechanical and land the whole test churn at zero semantic risk.
- **Step 5 becomes Story 7.0**, first in Epic 7. Stories 7.1, 7.3 and 7.4 consume the public async API, whose signatures do not change in any step, so all three run in parallel with it.
- **Step 6 inside Story 7.5.** **Step 7 is debt paydown that can trail**, but must be scheduled before 7.5's benchmark is treated as ratifying NFR-4's placeholders.

## 4. Impact on the current sprint

**The premise in the brief is stale and I am correcting it on the record: Epic 5 is not the current epic, and story 5-1 is not blocked — it is merged.** 5-1 landed as PR #138 (`ff1f669`) and 5-2 as PR #139 (`e0e9f6c`). **Epic 6 is in progress** — 6-1 done, 6-2 (the real Hermes gateway) merged as PR #144 (`58d5a70`). Epic 7 is next, which is why this gate is imminent rather than two epics out.

Three concrete consequences:

1. **Nothing in Epic 5 or 6 is blocked by this decision, and nothing needs rework.** Story 5-1 was written to comply with AD-17's bounded-work rule by construction, and it did: `attach_memory`/`detach_memory`/`memory_status` are **registry-lock only**, with the reason documented in place at `engine.rs:869-874` ("REGISTRY LOCK ONLY (AD-17): … it cannot widen the fleet-wide stall"). That is exactly the discipline AD-17 was recorded to produce. Under AD-18 those three operations move *under the instance cell* — which is a **strengthening**, not a break: the coarse registry lock was silently providing `attach_memory`'s terminal-state guard (`registry.rs:612-663`) exclusion against `start_inner`'s `memory_backing` read (`supervisor.rs:626`), and AD-18 is the reason that exclusion survives a partition instead of being lost to it. No 5-1 code changes; only which lock its engine wrapper takes.

2. **Epic 5 did increase the debt in exactly one place, and it should be named.** Memory directories now live inside the Agent Home, so `Registry::remove`'s recursive `std::fs::remove_dir_all` (`registry.rs:561`) — already the worst single unbounded hold, run under **both** locks after a possible full ≤35s stop — is now O(a tree that grows with agent memory). Step 3's `remove_row` + free `delete_home` split is the fix; it is the highest-value single item in that step.

3. **PR #126 already tactically fixed the severest live instance and this decision does not revisit it.** `drain_usage_for` (`supervisor.rs:2393`) no longer does a whole-file read of a monotonically growing `agent.log` every 250ms per instance under both locks; `read_usage_tail` (`:266-296`) seeks to the cursor and reads only `[cursor, len)`. Two corrections carried forward into AD-18: it is an **incremental-read conversion, not a bound** — the per-pass cap is deliberately absent, because capping would strand a Terminal-drain remainder and reintroduce the H1 under-count — and the log itself is **still never rotated**, which is Step 7. #126 also added the post-kill rescue drain at `:1184`; **AD-18's prohibition (c) exists to protect exactly that fix**, and it is what refuted one of the four candidate designs.

## 5. What this does NOT decide

Named precisely, each with who owns it.

1. **Whether AI-20's Story 7.6 daemon is ratified, and with what concurrency profile.** "Daemon" appears nowhere in `epics.md` or the PRD; it is a *proposed* new story awaiting Islam's ratification. AD-18 fits Epic 7 as `epics.md` actually defines it (7.1–7.5: long-lived embedded lifetime plus event subscription). If 7.6 lands with hosts driving *concurrent* commands, callers blocking on a cell rather than enqueueing becomes the binding constraint and the actor/mailbox successor is likely in v1.x. **Product call, and it changes the successor's timing, not this decision.**

2. **NFR-4's numbers.** `prd.md:350` marks all three as placeholders for architecture to validate, and Story 7.5 provides the escape hatch ("or the measured values replace the budgets … via a documented update"). **AD-18 does not set them.** It does insist the AC be strengthened — as written, "Given a 25-instance Fleet fixture / When the benchmark suite runs / Then read commands complete <1s" contains nothing requiring supervision to be *active or contended*, so it can pass green on an idle fleet with the global lock fully intact and produce a false negative that argues against doing this work at all.

3. **Whether `fleet()` is a consistent fleet-wide snapshot.** Today `engine.rs:422-430` reads rows + live run ids under both locks as one point-in-time view. Under AD-18 it becomes N independently-timed per-instance reads, and `FleetTotals` can sum a combination that was never simultaneously true. `engine.rs:399` already frames the AC as a ≤2s *freshness* bound with no cache, and no FR demands cross-instance atomicity — but **this is a semantic downgrade that needs a ruling, not a design document's assertion that it is fine**, and Story 7.1's shared kt/host assertions must not encode the old guarantee.

4. **The `try_lock` degradation on live billing data.** `fleet_entry_for` needs `current_run_id` to call `run_usage_totals(name, run_id)`. Resolving it by `try_lock`-with-fallback makes a busy instance's *per-Run* token and dollar column contention-dependent — a listing taken during that instance's own stop silently reports zero rather than the true figure. The existing degrade policy (`engine.rs:434-439`) covers a read-back *failure*, not a lock-contention miss on a billing surface. **Needs an explicit product ruling: degrade, block, or mark the cell "unknown."**

5. **Data retention vs. billing evidence.** Usage rollups (Step 7) bound the enforcement scans only if raw `usage_events` rows can be aggregated and eventually pruned. That is a **cost-and-evidence call** — how long must per-event billing provenance survive? — not an architecture call. Same for `agent.log` rotation: a retention window is a product decision, and it is coupled, because an unrotated log filling a disk produces exactly the OS-level uninterruptible I/O wait that `KILL_CONFIRM_TIMEOUT` exists to bound.

6. **The public error surface Epic 7 must express.** Poisoning becomes per-instance under AD-18: one instance permanently unusable while twenty-four keep running — better availability, worse diagnosability. Today's 37 `.expect("… mutex poisoned")` sites must become a typed `EngineError`, the reaper must stop polling a poisoned cell, and `instance_status`/`fleet` must say something coherent about it. **That is Story 7.1/7.3 API design**, and under a daemon it is also an NFR-1 question (`"an Agent crashing never crashes the Engine or kt"` currently coexists with an engine that panics on a poisoned lock).

7. **Whether hand-editing a live instance's `config.toml` is a supported workflow.** `enforce_budget`'s live `effective_config` read (`supervisor.rs:2645`) fires on every fresh usage event and is what makes story 3-2's AC-B ("changes apply immediately") true for on-disk edits. Any caching of it — and something will want to cache it, because it is one to two TOML parses per event on the 250ms path — regresses that AC for hand-edits while preserving it for `kt agent config set`. **Ruling needed before anyone caches it.** Note the measured shape: the totals scans are already gated behind `if !token_armed && !dollar_armed { return; }`, so it is the *config read*, not the scans, that is unconditional.
