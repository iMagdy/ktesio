# Story 4.1: Send input to any running agent with one command

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want to send text input uniformly, with honest failure when an agent can't receive it,
so that interacting doesn't require per-agent knowledge. (FR-24)

## Acceptance Criteria

Verbatim from `epics.md` Story 4.1 (the **FIRST** story of Epic 4 — Talk To and Observe Any Agent Uniformly; epics.md lines 444-462) and PRD §4.6 FR-24 (prd.md lines 245-248). Epic 4's one-line thesis: *"One interaction surface: send, stream, script."* This story owns **send** only; streaming output/logs is 4.2 (FR-25), and `--json`/exit codes is 4.3 (FR-26).

> **CRITICAL SCOPING — read before AC-A.** This is a **greenfield-plumbing** story wearing a **seeded-declaration** disguise. Two things are ALREADY true from Epic 1 and must NOT be rebuilt: (1) `Capability::Interaction` exists as a full seed in the Capability Declaration model (`crates/ktesio-adapter-api/src/capability.rs:65-83`, added alongside `Capability::Pause` — the module doc literally says *"This story SEEDS the capability set (`pause`, `interaction`)"*, referring to whichever earlier story introduced it), and (2) BOTH the shipping `BuiltinMock` (`crates/ktesio-engine/src/adapter/builtin.rs:60-88`) and the `ktesio-conformance` `MockAdapter` (`crates/ktesio-conformance/src/lib.rs:51-85`) ALREADY declare `interaction: guaranteed` on Linux/macOS/Windows, and every existing manifest test fixture that declares `[capabilities.interaction]` already parses and projects correctly. **None of that needs building.** What is GENUINELY new: there is **no stdin plumbing at all** — both process backends unconditionally set `command.stdin(Stdio::null())` (`crates/ktesio-engine/src/backends/unix/mod.rs:142`; `crates/ktesio-engine/src/backends/windows/mod.rs:223`), the `AgentAdapter` trait has no interaction accessor, `SpawnSpec`/`ProcessBackend` have no stdin-write surface, and `kt`'s `AgentCommands` enum (`crates/kt/src/main.rs:105-179`) has no `Send` variant. This story builds the **routing**, reusing the **already-generic** capability-unsupported fail-fast machinery (`registry.effective_support`, `EngineError::CapabilityUnsupported`, `map_engine_error`'s `CapabilityUnsupported` arm) verbatim — zero changes needed there.
>
> **CRITICAL SCOPING #2 — the single-lifetime supervision boundary (read before AC-A).** `kt agent start` does not durably supervise a process across separate CLI invocations: a clean CLI exit runs `Engine`'s `Drop` (`crates/ktesio-engine/src/engine.rs:115-121`), which drops the `Supervisor`'s handle map, and the per-OS backend's `Drop` `SIGKILL`s the whole process group/job (documented, tested, and honestly noticed today at `crates/kt/src/cli/agent.rs:738-750`). This was investigated end-to-end by a ratified research spike (`research/technical-durable-agent-supervision-daemon-vs-detach-research-2026-07-06.md`, action item AI-20, `sprint-status.yaml` line ~206-209): **RECOMMENDS (c) document single-lifetime as v1 now + (a) engine-as-daemon as the durable path in Epic 7/v1.x; explicitly DO NOT build `--detach`** — because detach "severs stdin/stdout" and "cannot deliver Epic 4's send-input." **This story does not change that boundary and must not attempt to.** "One command" in FR-24 is honored at the SAME granularity `pause`/`stop`/`resume` already are: fully provable within one continuous `Engine` session (exactly how `crates/ktesio-engine/tests/pause.rs` proves pause — one `Engine::open()`, sequential calls), and at the CLI layer provable across separate `kt` invocations ONLY via the existing test-only cross-process harness `start_via_surviving_engine` (`crates/kt/tests/agent_cli.rs:43-59`) that the existing pause CLI tests already rely on for the exact same reason. A **new**, honest wrinkle this story must handle (not present for pause/stop, which only need a live *handle*, not a live *pipe*): a process **adopted** from a prior engine session (AD-5, story 1-6) has NO recoverable `ChildStdin` — Rust's `std::process` API cannot reconstruct a pipe file descriptor from a bare PID, on any of the three OSes, without an undocumented hack this project's own conventions already reject (see the Windows-pause `[ASSUMPTION]` at `backends/windows/mod.rs:40-55` for the established "no undocumented API" precedent). So `send` on an adopted-but-genuinely-running instance must fail **honestly and distinctly** from the capability-unsupported case (the adapter's declaration is NOT what's failing) — see AC-D below.

1. **AC-A (verbatim — the same send command works on both the mock adapter and a manifest adapter).** **Given** a running instance on the mock adapter and on a manifest adapter (stdin channel per AD-12) **When** I send a text input **Then** the adapter routes it to the agent's native input channel and the same command works on both. Concretely: "running" = `LifecycleState::Running` within the engine's supervising session (see scoping #2 above — mirrors every `pause`/`resume` test's setup, e.g. `crates/ktesio-engine/tests/pause.rs:112-118`). "the agent's native input channel" = for v1, the ONLY implemented channel is the spawned child's OS stdin pipe (AD-12: *"the adapter trait exposes an `InteractionChannel` (manifest kind default: stdin pipe in ...)"*) — Hermes' own native channel mapping is Epic 6 (`ktesio-adapters-hermes` is an 8-line stub today), explicitly out of scope. "the same command works on both" is trivially satisfiable and should be KEPT that way: both the native `BuiltinMock`/conformance `MockAdapter` and any manifest adapter are, in v1, spawned through the exact same `ProcessBackend`/`SpawnSpec` mechanism (AD-3 "two adapter kinds, one trait") — so `send` needs **zero per-kind branching**; one supervisor method serves both.

2. **AC-B (verbatim — unsupported interaction fails fast quoting the declaration).** **Given** an adapter declaring `interaction: unsupported` **When** I send input **Then** the command fails fast quoting the Capability Declaration. This is the **existing, already-generic** `CapabilityUnsupported` path: `registry.effective_support(&name, Capability::Interaction)` (`crates/ktesio-engine/src/domain/registry.rs:647-654` — already parametrized over `Capability`, not pause-specific) returning `SupportLevel::Unsupported` → `EngineError::CapabilityUnsupported` (`crates/ktesio-engine/src/domain/error.rs:209-222`) → `kt`'s `map_engine_error` (`crates/kt/src/cli/agent.rs:1410-1421`) → `AgentCapabilityUnsupported`, non-zero exit, diagnostic on stderr naming the capability + OS + level + pointing at `kt agent show`. **No new error-handling code is needed for this AC** — it is reused verbatim, the same way `pause`'s AC3 already exercises it. The check MUST run **before** any process I/O is attempted (fail fast — no partial send, no process signal, nothing persisted, mirroring `suspend_or_resume`'s ordering).

3. **AC-C (derived — sending requires the instance to actually be `running`).** Unlike a lifecycle verb, `send` is not itself a state transition, so it is not in the `LifecycleCommand`/transition-table (AD-15). A dedicated pre-flight check is needed: `send` on any instance NOT in `LifecycleState::Running` (registered/starting/paused/stopping/stopped/failed) fails with a new, clear `EngineError::NotRunning { name, state }` — checked **before** the capability-support read (mirrors the existing "transition gate before any side effect" convention throughout `supervisor.rs`). `Paused` is deliberately treated as **not** sendable in v1 (FR-24 says "a `running` Agent Instance" verbatim); this is a scoping choice, not a technical limitation — flagged as an assumption below.

4. **AC-D (derived, NOT in epics.md but essential for honesty — an adopted (not self-spawned) live instance fails distinctly from "unsupported").** Given an instance that is genuinely `running` (adopted from a prior engine session per AD-5/story 1-6 — e.g. via `start_via_surviving_engine` in tests, or in production after an engine crash+restart) but whose live stdin pipe cannot be recovered by this engine session, `send` fails with a **new, distinct** `EngineError::InteractionUnavailable { name, detail }` — **never** `CapabilityUnsupported` (the adapter's Capability Declaration truthfully says `interaction: guaranteed`; it is this engine session's reach that is limited, not the adapter's capability). The message must say so honestly and point at the underlying cause (no live channel held in this session; durable cross-invocation interaction needs a persistent engine session, planned for Epic 7/v1.x) — never silently succeed, and never misattribute the limitation to the adapter.

5. **AC-E (derived — the manifest's `[interaction]` channel is validated, not merely carried).** `Interaction.channel` is today a free-form `String` (`crates/ktesio-adapter-api/src/manifest.rs:114-121`), explicitly commented *"Free-form this story; the channel model firms up with the interaction epic"* — **this is that epic.** Firm it into a small closed enum (mirrors `SupportLevel`'s `as_str()`/`Display` seed-enum pattern), single variant `Stdio` this story, so an unrecognized value is rejected at **parse** time (like `MeteringSource`'s closed-enum handling) instead of silently accepted-and-ignored. The `[interaction]` table stays OPTIONAL (existing test manifests, e.g. `crates/ktesio-engine/tests/pause.rs`'s `write_pause_manifest`, omit it entirely while still declaring `[capabilities.interaction]`) and its absence still means "default to stdio" (AD-12's stated manifest default) — this is a **documentary/forward-honesty** change, not new branching logic: v1 has exactly one implemented channel, so the engine unconditionally pipes stdin for every spawned process regardless of what (or whether) `[interaction]` says.

6. **AC-F (derived — a trailing newline is appended so line-oriented agents receive a complete line).** `send`'s given text has exactly one `\n` appended if it does not already end with one, before being written to the child's stdin. Recorded as a Decision (not mandated by epics.md) because most agents read stdin line-by-line (`BufRead::read_line`); a raw byte-exact mode is explicitly out of scope this story.

### Why no new `AgentAdapter` trait method is needed (a deliberate minimalism, not an oversight)

The architecture spine's Capability→Architecture map lists "Interaction & logs (FR-24..26) | adapter `InteractionChannel` + engine capture | AD-12, AD-14" (`ARCHITECTURE-SPINE.md:242`), which could read as "the adapter trait needs an `InteractionChannel` accessor." Investigated and rejected for THIS story: in v1, **every** adapter that can actually run (native `BuiltinMock`, the conformance `MockAdapter`, and every manifest adapter) is spawned through the exact same `ProcessBackend`/`SpawnSpec` mechanism — there is no second, non-process-based channel implemented yet (Hermes' native channel is Epic 6; `ktesio-adapters-hermes` is an 8-line stub today, verified via `find crates/ktesio-adapters-hermes -name '*.rs' | xargs wc -l`). So "the adapter's `InteractionChannel`" IS, for every adapter that exists, "the child process's stdin pipe" — routing lives entirely in the supervisor/backend layer (mirrors exactly how `AD-12`'s log capture needs no adapter-trait accessor either: `SpawnSpec.log_file` is engine-computed, not adapter-declared). Adding a trait method now, with only one implementation ever exercised, would be speculative generality this codebase's stated conventions explicitly warn against (`adapter-api/src/lib.rs:31-36`: *"Keep the surface small and additively extensible; do NOT build negotiation or freeze the set here"*). If Epic 6's Hermes integration needs a genuinely different channel, it adds the accessor THEN, informed by a real second implementation — the same "seed, not freeze" discipline the whole crate already follows.

### The single-lifetime supervision boundary — the load-bearing constraint (read in full before writing `send_input`)

This is the single most consequential fact this story must design around, and it is NOT something to fix here. Full chain of evidence:

- **The mechanism:** `impl Drop for Engine` (`engine.rs:115-121`) aborts the reaper; the `Supervisor`'s `HashMap<InstanceName, Supervised>` then drops normally, dropping each `Supervised.handle` — `UnixProcess`'s `Drop` (`backends/unix/mod.rs:392-414`) `killpg`s the whole process group if it's still alive; `WindowsProcess`'s job-handle close (`backends/windows/mod.rs:125-146`) does the Windows equivalent via `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.
- **The consequence, already honestly documented:** `crates/kt/src/cli/agent.rs:738-750`'s doc comment on `start()` states plainly that a standalone `kt agent start` "stops the agent when this CLI process exits cleanly," and the CLI prints a one-line stderr notice to that effect (asserted by `start_prints_single_lifetime_notice_to_stderr_only`, `agent_cli.rs:557-605`).
- **The ratified research (AI-20, `research/technical-durable-agent-supervision-daemon-vs-detach-research-2026-07-06.md`):** explicitly names Epic 4 as "the point where a non-daemon answer visibly breaks" (line 167 of that doc) and states outright: *"Epic 4's send-input is not satisfied by detach"* and *"a detached agent has no live stdin for `kt agent send`"* (lines 71-72, 121). Its recommendation — **(c) document single-lifetime as v1 now, (a) engine-as-daemon deferred to Epic 7 (proposed Story 7.6), explicitly do NOT build `--detach`** — is what THIS story must live inside, not resolve. `sprint-status.yaml`'s AI-20 entry (open, medium severity) records this is "awaiting Islam's ratification" of 5 sub-questions, but those are explicitly scoped to Epic 7 planning and do not block this story.
- **What this means concretely for `send_input`'s design:** (1) it is fully deliverable and testable within ONE continuous `Engine` session — exactly the shape `crates/ktesio-engine/tests/pause.rs` already uses (one `Engine::open`, sequential `start`→`pause`/`resume` calls); (2) at the CLI layer, a genuine cross-invocation proof needs the SAME `start_via_surviving_engine` trick the pause CLI tests already lean on (a normal `kt agent start` would have already killed the process before a second `kt agent send` could reach it — this is not a regression to fix, it is the existing, ratified boundary); (3) it introduces a NEW wrinkle beyond pause/resume: even a genuinely-alive ADOPTED process (AD-5) has no recoverable stdin pipe, so `send` must fail there too, honestly and distinctly (AC-D) — pause/stop/poll do not have this problem because they act on the pgid/job/PID from OUTSIDE the process (no pipe needed), while `send` needs an actual open file descriptor this engine session holds.
- **Do not build any interim workaround** (a `--detach` flag, a `/proc`-based pipe-reopen hack, etc.) — the research explicitly rejected detach for exactly this reason, and the reopen hack would violate the "no undocumented API" convention already established for Windows pause.

### The three-level dispatch, and why it differs from pause's

`suspend_or_resume` (`supervisor.rs:832-908`) is the closest existing precedent — SAME name-resolve → transition-gate → capability-read → 3-way-dispatch shape — but two things differ meaningfully:

1. **No transition.** Pause/resume change `LifecycleState`; `send` never does. So `send_input` has no `next_state` call and emits no `TransitionEvent` — its pre-flight is a plain `state == Running` check (AC-C), not a transition-table lookup. This also means a NotRunning rejection is not "the uniform invalid transition" (`LifecycleError`/`EngineError::InvalidTransition`) — it needs its own variant, since there is no transition being attempted.
2. **Guaranteed and best-effort collapse to the same action.** Pause's guaranteed path does a REAL SIGSTOP; its best-effort path is a no-op-but-honestly-labeled transition. For interaction there is no OS-conditional difference in the underlying mechanism — writing bytes to a pipe works identically on all three OSes regardless of the declared level (unlike pause, which has a genuine Unix-vs-Windows primitive gap, AD-4). So `Guaranteed` and `BestEffort` both attempt the identical `write_stdin`; `BestEffort` exists purely so an adapter AUTHOR can honestly signal "I deliver the bytes, but I can't promise the agent meaningfully consumes them" — a declaration-level nuance, not an engine-mechanism one. A CLI-level qualifier note (mirroring `note_if_best_effort`, `agent.rs:855-878`) for a best-effort send is a nice-to-have polish item, not required by either epics.md AC.

### `map_engine_error`'s existing generic message reads slightly awkwardly for "interaction" — a known, accepted nit

`CapabilityUnsupported`'s message template is `"Agent Instance '{name}' cannot {capability}: ..."` (`error.rs:209-211`), which for pause reads naturally ("cannot pause") but for interaction reads as "cannot interaction" — grammatically odd but unambiguous. Recommendation: leave the SHARED generic path unchanged (it is exercised by both pause and interaction today, and by any future capability) rather than special-case the wording for one capability; this is flagged so a reviewer doesn't mistake it for an oversight. If polish is wanted later, the fix belongs in `Capability`'s `Display`/a verb-phrase method, not in the error-formatting call site.

### Fix Pass — Review of #79 (headless BMAD dev-story run, 2026-07-14/15)

An adversarial code review of this story's original implementation (commit `8b4e4a0`) empirically reproduced two safety-critical findings and three medium findings. This addendum documents the fix pass; it is a NEW commit on top of `8b4e4a0`, not an amendment.

**CRITICAL — `send_input`'s blocking write could freeze the ENTIRE engine forever.** The engine's `EngineInner` (`engine.rs`) holds ONE global `Mutex<Supervisor>` guarding every instance, not per-instance locking; `Supervisor::send_input`'s final step was a bare, unbounded `stdin.write_all(data)` performed WHILE that lock was held. The audit reproduced this empirically: a large payload to a non-draining instance blocked an unrelated instance's `send` on a separate thread, unblocking only because the stuck instance happened to have a bounded `--linger-ms` and self-exited — with a genuinely non-exiting stuck agent this freeze is permanent, and no `kt` command (not even `stop`, not even `list`) can recover, since all of them need the same lock.

*Fix.* Added `STDIN_WRITE_TIMEOUT = Duration::from_secs(5)` (`ports/process_backend.rs`) — a conservative, non-configurable bound (no new CLI flag/config surface; a resilience bound, not a user setting). Chosen because a healthy agent draining `send`'s realistic interactive-sized payload (a line or short paragraph) completes in low-single-digit milliseconds even on a loaded CI runner, so 5s leaves generous headroom for scheduler jitter while still keeping a stuck agent from wedging the engine for anything beyond a human-noticeable pause. Implemented the exact portable `std`-only pattern the review specified: `write_stdin_bounded` (new `pub(crate)` function in `ports/process_backend.rs`) takes ownership of the `ChildStdin` out of a new `StdinState` enum (`Live(ChildStdin)` / `NoPipe` / `TimedOut` — replaces the old bare `Option<ChildStdin>` field on `UnixProcess`/`WindowsProcess`) via `mem::replace`, moves it onto a spawned `std::thread` that performs the actual `write_all`+`flush`, and the caller waits on an `mpsc::channel`'s `recv_timeout(STDIN_WRITE_TIMEOUT)`. On success (or a genuine I/O error) within the bound, the `ChildStdin` is put back (`Live`) so a later `send` reuses the same pipe. On timeout, the thread is intentionally NEVER joined or aborted (no safe portable way to cancel a blocked `std::thread`) — it is abandoned, `state` is set to `StdinState::TimedOut`, and the new `BackendError::StdinTimedOut`/`EngineError::InteractionTimedOut { name, timeout_secs }` variants propagate. This is a DISTINCT error from `InteractionUnavailable` (which means "no pipe was ever recoverable" — no handle, adopted, or unsupported); `InteractionTimedOut` means "we had a live pipe, attempted the write, and it never came back." Every SUBSEQUENT `send` on the same instance checks the cheap, no-I/O `ProcessBackend::stdin_timed_out` accessor FIRST and fails immediately — no new attempted write, honest and permanent until the instance is stopped and started again (a fresh handle/pipe). `write_stdin_bounded`/`StdinState`/`STDIN_WRITE_TIMEOUT` are ONE shared implementation called identically from both `backends/unix/mod.rs` and `backends/windows/mod.rs` (not two separate OS timeout implementations — the mechanism has no OS-specific part). `kt`'s `map_engine_error` gained a matching `AgentInteractionTimedOut` diagnostic (`crates/kt/src/error.rs`) naming the bound and pointing at `kt agent stop && kt agent start` for a fresh channel.

**HIGH — unconditional `Stdio::piped()` on every spawned process was an untested, plausible regression.** Task 1 changed both backends to pipe stdin unconditionally for EVERY spawned process, including adapters declaring `interaction: unsupported` and native adapters that will never receive `send`. The audit confirmed via a standalone OS-level probe: a child that does a simple blocking read of one stdin line at startup (a common "sniff for piped input" real-CLI idiom) completes near-instantly under the old `Stdio::null()` default, but hangs indefinitely under the unconditional pipe — the engine holds the pipe's write end open for the process's whole supervised lifetime, so the child never sees EOF unless `send` is called. Since readiness here is just "the process didn't exit immediately," such an agent would be reported `running` while silently deadlocked, with no error signal anywhere.

*Fix.* Added `SpawnSpec.pipe_stdin: bool` (`ports/process_backend.rs`). The seam: `Supervisor::start_inner` (`domain/supervisor.rs`) now reads `registry.effective_support(&name, Capability::Interaction)` — the SAME per-OS Capability Declaration read `send_input`/`pause` already use — right alongside the existing `metering_source` read (a pure snapshot read, before any persisted state change, mirroring the file's existing "reject cleanly, no spurious state change" convention), and sets `pipe_stdin = matches!(level, Guaranteed | BestEffort)` on the constructed `SpawnSpec`. Both backends' `spawn()` now branch `command.stdin(if spec.pipe_stdin { Stdio::piped() } else { Stdio::null() })` — capability lookups stay OUT of `backends/` (which remains a dumb process executor); only the resolved bool crosses the port. This mirrors how the rest of the codebase already gates BEHAVIOR (not just callability) on declared capabilities (pause's SIGSTOP-vs-noop branching).
