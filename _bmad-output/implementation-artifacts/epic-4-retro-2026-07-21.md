# Retrospective — Epic 4: Talk To and Observe Any Agent Uniformly

**Run mode:** Party Mode (multiple BMAD persona perspectives synthesized into one artifact). Autonomous-with-evidence: assembled from `sprint-status.yaml`'s epic-4 story journals and action-item ledger, the three story files (`4-1`, `4-2`, `4-3` — Dev Agent Records, fix-pass addenda, deviation logs, mutation tables), the two squash commits (`6afac99`, `fb3d7fd`) and their thirteen constituent commits, GitHub epic issue #58 (and its closing summary), issues #79/#80/#81, PRs #117 and #119 (descriptions and CI history), live `gh run list` data for both feature branches, `epics.md`, `prd.md` §4.6/§7/§11, and `epic-9-retro-2026-07-14.md` for the follow-through audit. This is the project's **fifth** retrospective, and the first for an epic whose defining events were all **safety findings in review**, not delivery problems.

> Ground rule (Amelia): psychological safety first — we review systems and processes, never people. Every observation below is anchored to a story file, a commit, a GitHub issue/PR, a CI run, or the action-item ledger. Epic 4 shipped everything it promised and shipped it well. It is also, by a wide margin, the most dangerous epic this project has run: three CRITICAL engine-safety bugs reached the review gate, and **not one of them was found by the implementing agent's own passing, ≥95%-covered test suite.** That is the story of this epic, and this retro is mostly an attempt to say something *generalizable* about why — rather than to log three incidents and move on.

## 3. What went well (top themes)

### 3.1 The adversarial pass is now, empirically, the only control that catches this class of bug

Four findings, four different failure modes, one common origin:

| # | Story | Finding | Found by |
| --- | --- | --- | --- |
| 1 | 4-1 | `send_input`'s unbounded blocking `write_all` held the engine's single global `Mutex<Supervisor>` — one stuck agent freezes the **entire fleet forever**, unrecoverable (not even `stop` or `list` can take the lock) | Adversarial audit, **empirically reproduced** |
| 2 | 4-2 | Piping stdout/stderr through the engine coupled agent write-success to engine liveness — an engine crash could **SIGPIPE-kill the supervised agent itself** (a regression against the pre-story direct-to-file design) | Adversarial audit, **empirically reproduced through the real spawn path** |
| 3 | 4-2 | Removing that pipe removed its **incidental backpressure** — a fast writer can exhaust disk, enter uninterruptible I/O (immune to SIGKILL), and freeze the fleet **unboundedly** through `stop()`'s hold on the same global lock | **Independent verification of fix #2** |
| 4 | 4-3 | The story's own AC2 claim ("any unannounced change fails CI on all three OSes") was **false in four places**; the priced wire shape had **no freeze at all** | Adversarial pass, **by mutating code and watching tests pass** |

None of these were found by the implementing agent's tests, and it is worth being precise about why that is not a criticism of those tests. Each implementation was accompanied by a genuinely careful suite: 4-1's dev pass added 14 tests and audited every uncovered line by hand; 4-2's dev pass root-caused a 94.88% coverage dip to five concrete gaps and closed each with a targeted test; 4-3's dev pass *self-mutated three axes* and confirmed the gate caught all three. These are conscientious, high-quality passes. They found nothing because **a test suite written alongside an implementation inherits that implementation's model of what can go wrong** — and every one of these four bugs lives in the space the model did not contain.

> Charlie (Senior Dev): "The 4-3 detail is the one that convinced me. That dev agent *did* mutation-test its own gate — three mutations, all caught, all documented in the Debug Log. Then an adversarial pass ran five different mutations and four of them sailed through. Self-mutation confirms the tests you thought to write. Adversarial mutation finds the tests you didn't think to write. Those are not the same activity and one does not substitute for the other."

### 3.2 Verifying a fix independently — rather than trusting the fix's own tests — caught a brand-new CRITICAL

Finding #3 above deserves its own heading because of *how* it was found. The 4-2 crash-safety fix (`21af762`) was correct, thoroughly tested, and closed a real CRITICAL. Its own verification tests all passed. The reviewer nonetheless treated the fix as **a new design requiring a fresh adversarial pass**, rather than as a patch requiring confirmation — and discovered that the pipe being removed had been silently providing write backpressure that nothing in the design, docs, or tests had ever named. The resulting bug (`4484019`) was strictly *worse* than the one being fixed: 4-1's residual stall is bounded at ~5 s, while an OS-uninterruptible-I/O wait under the same global lock is unbounded and OS-determined.

This is the sharpest generalizable lesson in the epic, and §6.2 develops it.

### 3.3 Every fix converged on one honest, reusable shape — and the third fix was built by deliberately copying the first

4-1's fix and 4-2's second fix are structurally identical, and that is not an accident: 4-2's fix-pass brief explicitly instructed the implementer to mirror 4-1's proven `STDIN_WRITE_TIMEOUT`/`InteractionTimedOut` precedent rather than redesign the locking model. The resulting shape now appears three times in the codebase:

1. **Bound the operation** with a named, non-configurable resilience constant (`STDIN_WRITE_TIMEOUT`, `KILL_CONFIRM_TIMEOUT`) — a bound, not a user setting.
2. **Take the timeout as a parameter** so a deterministic test can pass 150 ms instead of waiting out the real 5 s (`write_stdin_bounded`, `confirm_death`).
3. **Introduce an honest, distinct error variant** (`InteractionTimedOut`, `StopUnconfirmed`) rather than reusing a nearby one or returning `Ok` — 4-2 explicitly closed a *pre-existing* dishonesty where the adopted-handle branch returned `Ok` even with the process still alive.
4. **No compounding on retry** — a cheap, non-blocking check that fails fast rather than starting a fresh wait cycle.
5. **Self-healing** — `stop()` retry *or* the crash reaper reconciles the row, whichever observes the exit first, so nothing is permanently stuck.
6. **A matching CLI diagnostic** naming the instance, the bound, the likely cause, and the remediation.

> Winston (Architect): "I'll take the compliment and the warning together. Convergence on one shape is real engineering maturity — the third instance was cheap because the first two paid for it. The warning is that the shape is a *mitigation* for an architectural property we haven't changed. We are getting very good at bounding the symptoms of the global lock. Doing that a fourth time should feel worse than it currently does."

### 3.4 Contract-shape decisions were escalated to the owner *before* dev froze anything

Story 4-3's create-story context carried a reasonable but wrong assumption: that `usage` had no standalone command and rode `list`/`show --json`. Islam corrected it during ratification, and `kt agent usage [<name>] [--json]` became a net-new first-class command — expanding the story's scope mid-flight. All three contract decisions (0–6 granularity over a minimal 0/1/2; standalone `usage`; NDJSON uniformly) were ratified **up front, before implementation**.

The counterfactual is what makes this matter. Had the assumption survived into implementation, `usage` would have shipped as an embedded field, then been frozen by the very key-set tests 4-3 was building — and correcting it afterwards would have been a **v1 compatibility break**, not a refactor. Asking before freezing is cheap; asking after freezing is a deprecation cycle.

> Alice (Product Owner): "This is the correct instinct and I want it stated as a rule, not a nice save. A story whose deliverable is *a promise not to change something* has to get its shape ratified before code exists. Otherwise the first implementation silently becomes the contract."

### 3.5 Residuals were disclosed in the artifacts rather than papered over

A consistent, and genuinely uncommon, pattern across all three stories: what could not be proven was written down as such, in the story file *and* the PR description, in the same paragraph as the claim it qualifies.

- **AI-59** — 4-1's fix bounds the stall but still holds the global lock through the whole 5 s wait, so an *unrelated* instance's `send` was measured at 4.31 s, resolving in lockstep. Logged as a deliberate, specified tradeoff with the full fix described, not as a shortfall discovered later.
- **Exit code 6 has no end-to-end assertion on any OS.** 4-3's AC2 wording was *rewritten* to say so rather than keeping the blanket claim the adversarial pass had just falsified.
- **The D-state scenario was never reproduced on the fixed code.** 4-2's ramdisk experiment honestly reported that a memory-backed ramdisk *cannot* reproduce uninterruptible I/O (zero write latency by construction — it returns `ENOSPC` instantly instead), and the fix pass declined to escalate to a real-disk experiment given the two prior disk-fill incidents. The mechanism was then proven deterministically instead, against a genuinely-alive process with a short timeout.
- **4-2's `BackendError::StopUnconfirmed` → `stop_unconfirmed = true` glue is unreachable by any test** — both halves independently tested, the 3-line wiring unexercised, documented as such.
- **Seven `_unix`-suffixed tests skip Windows**, now visible in the test list with a written rule that a `_unix` test may be an *additional* proof, never the sole guard.

> Dana (QA): "Compare this to a suite that reports green and says nothing. I would rather have a documented hole I can plan around than a clean report I can't trust. Four of those five residuals became action items in this retro precisely *because* they were written down."

### 3.6 Each hole-closing fix was verified by re-applying the exact mutation that exposed it

4-3's fix pass carries a six-row mutation table where every closed hole was re-broken and confirmed to fail the new test, then reverted and confirmed to pass again. The stated reasoning in the story file is worth preserving verbatim in spirit: *a hole-closing test that doesn't catch the thing that slipped through is theater.* One of those re-verifications (H3) additionally noted that all three nextest retries failed, establishing the new test as deterministic rather than a coin flip.

## 4. What was hard / what to improve (top themes)

### 4.1 HEADLINE: the single global `Mutex<Supervisor>` produced two CRITICALs in one epic, with unrelated triggers — this is architectural debt, not two bugs

Findings #1 and #3 share no code, no story, no trigger, and no author. One is a stdin write that never returns; the other is a process death that never completes. They are the same bug:

> **An operation with no upper bound on its duration is performed while holding the one lock that every instance's every operation needs.**

The engine's `EngineInner` holds exactly one `Mutex<Supervisor>` guarding all instances. Any unbounded operation under it is a fleet-wide denial of service waiting for a trigger. We have now found two triggers in a single epic, and the fix in both cases was to bound the *specific* operation — which is correct, minimal, and does not address the class.

Three consequences make this worth escalating rather than logging:

1. **The bounds compose the wrong way.** Each fix adds another window during which the whole fleet stalls. AI-59 measured it directly: an unrelated instance's `send` took 4.31 s, resolving in lockstep with the stuck instance's 5.01 s timeout. Two such bounds exist today (`STDIN_WRITE_TIMEOUT`, `KILL_CONFIRM_TIMEOUT`), each 5 s. A fleet operator does not experience "a bounded stall on one instance"; they experience "the CLI hangs."
2. **Nobody has swept for the rest.** We found #1 because 4-1 wrote under the lock and #3 because 4-2 changed how processes die. Both were found by someone looking at *that story's* diff. No one has enumerated every operation performed while the supervisor lock is held and asked which are unbounded. The next epic that adds a call under that lock has the same odds we just ran twice.
3. **Epic 7 makes it materially worse.** AI-59 already notes this: a persistent daemon or embedded host serving multiple clients turns "the CLI hangs for 5 s" into "every consumer of the engine hangs for 5 s," and the single-invocation CLI's forgiving lifetime stops masking it.

> Charlie (Senior Dev): "Two independent CRITICALs from one structural property inside one epic is not bad luck, it's a generator. And I want to name the trap in how we responded: both fixes were *good* fixes. Minimal, tested, honest, disclosed. That's exactly what makes the pattern easy to keep repeating — nothing about doing it a third time will feel wrong either."

**This is AI-63, and it is the highest-severity item this retro produces.**

### 4.2 Test-suite blind spots are one class with five faces, not five incidents — and one instance is still open

4-3's adversarial pass named four holes; 4-2 shipped a fifth of the same family. Read together they are one meta-failure — *the suite tested what the code does, not what the contract promises* — with five recurring, nameable, sweepable shapes:

| Pattern | Instance | Why the suite couldn't see it |
| --- | --- | --- |
| **Fixture monoculture** | Every freeze fixture used `registered_mock()` with no Rate, so `skip_serializing_if` omitted **all** dollar fields. The priced `UsageView`/`FleetTotals`/`BudgetView` shapes — the metered, cost-controlled, revenue-relevant half of the contract, i.e. the entirety of Epic 3 — had **zero** freeze. Adding a field populated only in `with_dollars()` passed all 69 tests | An `Option` field that no fixture populates does not exist on the wire, so freezing the wire freezes nothing about it |
| **Silent OS self-skip** | Runtime `if OsId::current() == Windows { return; }` reports **PASSED**. CI showed green on Windows for assertions that never ran — and two of those tests were the **sole** guards for real contract surfaces | Worse than `#[ignore]`, which at least reports as skipped. The matrix looks complete and isn't |
| **Unpinned link** | `classify(TimedOut) == 6` was unit-tested; `main`'s wiring was proven for codes 0–4; **nothing pinned that the timeout path produced that diagnostic type.** Severing `map_engine_error`'s arm silently demoted the documented `6` to `1` with the suite green | Testing both ends of a chain does not test the chain |
| **Untested mode combination** | The suite had exactly one `--follow` invocation, in human mode. Making every follow batch emit human text into a stream the caller parses as NDJSON passed all 33 logs tests | Each flag was covered alone; the product of the flags was not |
| **Tautological assertion** | `assert_eq!(line.schema_version, LOG_SCHEMA_VERSION)` compared the field to the constant it was stamped from — bumping the constant could not fail it | The assertion is true by construction, so it can never be false |

The **unpinned link** pattern is not closed. Story 4-2 documented, accepted, and shipped an instance of exactly it: `BackendError::StopUnconfirmed`'s wiring into `stop_unconfirmed = true` inside `stop_inner` is unreachable by any test, with both halves independently well-tested and only the 3-line glue unexercised. That is structurally identical to 4-3's H1, and it is the glue for a CRITICAL fix. Nobody connected the two at the time — 4-2's instance was recorded before 4-3's adversarial pass gave the pattern a name.

> Dana (QA): "Fixture monoculture is the one that scares me most, because it isn't about Epic 4. The unguarded half was Epic 3's — budgets, cost caps, dollar labels, the thing the product charges people money over. It went unfrozen not because anyone skipped it but because the default fixture is unpriced and `skip_serializing_if` is silent. That will recur anywhere we freeze a shape with optional fields, which is everywhere."

**This is AI-64 (make adversarial mutation mandatory for contract-freeze stories, with a maximal-fixture rule) and AI-66 (sweep the existing suite for all five patterns, starting with the known open instance).**

### 4.3 Fixing one safety bug created the next one — and the mechanism it removed was load-bearing for something undocumented

The 4-2 sequence is the single most instructive thing in this epic:

1. Pipe stdout/stderr through the engine → attribution works. **Also** couples agent liveness to engine liveness. → **CRITICAL**.
2. Remove the pipe, restore direct-file writes → crash-immunity restored, proven empirically. **Also** removes the pipe's incidental write backpressure. → **CRITICAL**, and strictly worse than the first.

Nothing was careless here. The pipe's backpressure was never designed in, never documented, never tested, and never mentioned in any story — it was a property the OS happened to provide, that the system happened to depend on, that nobody knew was load-bearing until it was gone. The generalizable rule is not "review fixes carefully" (everyone already agrees) but something sharper and actionable:

> **When a fix removes or replaces a mechanism, the removed mechanism takes its undocumented guarantees with it. The fix therefore needs its own full adversarial pass, with an explicit charter: *what was the old mechanism providing incidentally, that nothing names?*** That is a different question from "does the fix work," and only the first question would have found this.

The corollary is a scoping rule for review effort: a fix that changes a **value** (a timeout, a threshold, a deadline — 4-2's `6463ec8`, `cba24be`, `b42cd23`) can be verified against its own tests. A fix that changes a **mechanism** (pipes → direct files, channel → mutex, blocking wait → polling loop) is a new design and inherits a new design's review burden.

**This is AI-65.**

### 4.4 CI and coverage: a fourth epic merged over red, a new failure mode, and a gate that reported a false number

Three distinct problems, worth separating because they have different fixes:

- **AI-60 (mitigated, never root-caused).** A *third* distinct resource-fragility symptom on the free-tier coverage runner, after #101's OOM and #109's ubuntu-adoption hang: real-IO child-process round trips stall completely, a different test failing each rerun, never reproducible locally under identical tarpaulin config. Mitigated with a whole-job retry (deliberately *not* a per-test retry — this repo has a concrete lesson from 4-2's H1 where a per-test retry would have silently absorbed a real, reproducible data-loss race). The retry budget was **exhausted twice** (2/2, then 3/3), each time with the same small cluster of tests failing together within a single attempt, which is not what independent per-attempt bad luck looks like. AI-60's own text says the next step is a **runner-tier escalation to Islam, not another attempt-count bump** — and both Epic 4 PRs then merged with the gate red.
- **AI-61 (root-caused precisely, fixed).** A latent **Epic-3-origin** margin bug surfaced here: budget/cost breach-stop tests raced their own 30 s deadline against the 30 s `DEFAULT_STOP_WINDOW` that `enforce_stop` always forces through. On Unix, SIGTERM kills the unhandled `fake_agent` instantly so the window is never consumed; on Windows there is no graceful-shutdown signal implemented, so the full 30 s *always* elapses — a 30 s deadline against a 30–35 s critical path is a coin flip **by design**. Traced against the pre-`4484019` diff to prove it was not an Epic 4 regression. This is a good outcome and a warning: a latent cross-OS margin bug sat undetected in `main` for an entire epic, and surfaced only because Epic 4 happened to run CI harder.
- **AI-62 (fixed, and the most alarming of the three).** The coverage merge script silently skipped any crate with no `lcov.info`. When `ktesio-engine`'s tarpaulin run failed under AI-60's flakiness, it produced no `lcov.info`, was silently excluded, and the gate computed 95% against only the four much smaller crates — landing at an **identical 68.2042% on all three attempts**. The gate then reported *"merged coverage 68.2% is below 95%"*: a plausible, precise, entirely false statement about a workspace-wide coverage shortfall, when the truth was "the largest crate is missing from this measurement." It was caught because **Islam noticed the number didn't match the mechanism** while it was being explained to him.

> Charlie (Senior Dev): "AI-62 is the one to carry forward. A gate that fails loudly costs you a rerun. ### 4.6 Process cost: repeated interruptions, and two disk-fill incidents that then constrained verification

Two distinct operational costs, with different lessons.

**Interruptions.** This epic saw repeated host-process interruptions and agent watchdog stalls forcing restarts (4-2's own gate notes mention re-running the full suite after a mid-verification session interruption, "to be certain nothing regressed"). What mitigated it, and worked:

- **Work persisted on disk continuously** — story files, Dev Agent Records, and commits were written as work proceeded, so a killed agent lost momentum but never lost state. This is the same property Epic 9's retro credited (AI-57) for surviving a ~10-hour usage-limit exhaustion with zero rework.
- **The orchestrator verified tree state against git rather than trusting agent reports** — after a restart, the question answered was "what does `git log`/`git status` say happened," not "what did the agent say it did." This matters specifically because a watchdog-killed agent's last report is, by construction, from before it stopped.

What would help next time: AI-57 (already open, still unwritten) should be extended from "resume a usage-limited subagent" to the broader case of *any* agent that stops mid-flight, with "re-derive state from git, not from the last report" as an explicit step rather than a reflex someone happened to have.

**Disk-fill incidents.** 4-2's empirical verification consumed roughly 86 GB and then 55 GB of the host disk before the write bound was found and fixed — both cleaned up, neither reaching a dangerous state, but a real cost incurred twice. The mitigation adopted afterward (an absolute constraint never to touch the real disk again; a disposable 100 MB ramdisk instead) was correct, and it then turned out to make the target phenomenon **impossible to reproduce** — a ramdisk has zero write latency by construction, so it can only ever return `ENOSPC` instantly and never produces the writeback throttling that underlies real uninterruptible I/O. The team correctly chose safety plus a deterministic proof of the *mechanism* (`confirm_death` tested directly against a genuinely-alive process with a short timeout) over an unsafe reproduction of the *phenomenon*.

That is the right call, and it leaves an honest residual: **the D-state scenario has never been reproduced against the fixed code.** The fix is sound by construction — independently traced down to `Child::try_wait()` and confirmed non-blocking regardless of *why* a process won't die — which is a stronger argument than "it worked once in a test," but it is an argument rather than an observation.

## 6. Strategic / forward-looking findings

### 6.1 The global supervisor lock deserves an architecture decision, not a third mitigation

Per §4.1. The concrete ask has two parts, and the first is cheap:

**(a) Sweep, then decide.** Enumerate every operation performed while `EngineInner`'s `Mutex<Supervisor>` is held and classify each as bounded or unbounded. This is a mechanical, one-sitting audit that produces the actual size of the problem. We currently do not know whether there are two such operations or twelve.

**(b) Choose an architecture, with the answer from (a) in hand.** The options, roughly in cost order: keep bounding per-call (cheapest, composes badly, we've done it twice); per-instance write locks; a dedicated writer/actor task per supervised process, with the supervisor lock guarding only bookkeeping. AI-59 already identifies Epic 7's daemon/persistent-session work as the natural home, and that remains right — but Epic 7 should inherit a *decision*, not a discovery.

**Escalation to Islam.** This is the retro's primary architecture concern. It may warrant an explicit AD in `ARCHITECTURE-SPINE.md` (the current lock model appears to be an implementation fact rather than a recorded decision), and it may warrant a dedicated resilience story rather than waiting for Epic 7.

### 6.2 Make mutation testing standard for contract-freeze stories, and reading insufficient

The comparison inside a single story is the argument. On 4-3, the **primary review read the gate** and correctly, positively verified a great deal — all 22 diagnostics map correctly, `main()`'s downcast wiring is sound, `usage` reuses `list`/`show`'s exact computation so the numbers cannot drift, NDJSON is compact at all three call sites. It found no CRITICAL or HIGH, and it was *right* about everything it asserted. The **adversarial pass mutated the gate** and found that 4 of 5 mutations went undetected, including a total absence of freeze on the priced wire shape.

Reading a gate tells you what it checks. Only mutation tells you what it *misses*, and a compatibility gate's entire value proposition is the set of things it will catch. Proposed rule: **any story whose deliverable includes a frozen contract (wire shape, `schema_version`, exit code, adapter contract) must include an adversarial mutation pass by a reviewer who did not write the gate, and every closed hole must be re-verified by re-applying its original mutation.** Add a maximal-fixture rule alongside it: freeze fixtures must populate every optional field, because `skip_serializing_if` makes an unpopulated field invisible to the freeze.

This is **AI-64**. Note the cost is well-characterized — 4-3's fix pass was one focused session and added 11 tests.

### 6.3 Scope fix-pass review by whether the fix changes a value or a mechanism

Per §4.3. A concrete, cheap triage rule for review effort:

- **Value change** (timeout, threshold, deadline, constant) → verify against the fix's own tests. Epic 4 had three of these (`6463ec8`, `cba24be`, `b42cd23`) and all three were fine.
- **Mechanism change** (pipes → direct files, channel → mutex, blocking wait → polling loop) → **a new design.** Full adversarial pass by an independent reviewer, with the explicit charter: *what invariant was the removed mechanism providing incidentally that nothing names?*

Epic 4 contains both the failure case and the success case for this rule, which is why it is worth writing down now. This is **AI-65**.

### 6.4 Sweep the existing suite for the five named blind-spot patterns

Per §4.2. The five patterns are now named, and four of the five have a worked example of what the fix looks like (maximal fixtures; the `_unix` suffix convention plus "never the sole guard"; pinning the link explicitly; exercising flag combinations; pinning literals rather than constants). The sweep should start with the one known open instance — 4-2's `BackendError::StopUnconfirmed` glue, which is the unpinned-link pattern guarding a CRITICAL fix — and then look for the same shapes across Epics 1–3's suites, with fixture monoculture as the highest-value target given that Epic 3's priced surfaces were the ones found unguarded. This is **AI-66**.

### 6.5 The coverage gate needs a decision: fix it or demote it honestly

Per §4.4. Four of five epics merged over red coverage. AI-60's own closure text asks for a runner-tier escalation rather than another attempt-count bump, and that escalation has not yet happened. The options are a larger-RAM runner (a cost decision only Islam can make — this is AI-36's original option, resurfacing in a new guise), further diagnosis of why the same test cluster fails together within a single attempt (a persistently-degraded runner instance and un-reset state between same-job attempts both remain open, undiagnosed possibilities), or an honest demotion of coverage to a non-blocking, informational job. What should not continue is a required gate that is reliably overridden, because it trains everyone to read "coverage red" as "coverage red again." This is **AI-67**.

### 6.6 PRD §7's deprecation policy is still an open assumption — and Epic 4 just shipped a surface governed by it

Epic 4 declared the 0–6 exit-code table and the frozen `--json` key-sets to be **v1 compatibility surfaces governed by PRD §7**. PRD §7's own policy text still carries `[ASSUMPTION: policy mechanics pending Islam]`, and §7 requires announcement in release notes — which, per §4.7, has not happened for any of Epic 4's surface.

So the project now has shipped, test-enforced frozen contracts pointing at a deprecation policy that is explicitly unresolved, with no announcement having been made. Nothing is broken today; the exposure is that the first time someone needs to change one of these surfaces, the rules for doing so do not exist yet. Worth resolving before Epic 6 freezes the Adapter Contract v1 (Story 6-6), which is the same problem at a much higher stake. **This is an escalation to Islam** and is folded into AI-68.
