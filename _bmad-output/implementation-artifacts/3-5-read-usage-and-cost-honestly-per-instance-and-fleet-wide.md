### Derived / consequence criteria (make explicit; enforced by tests)

3. **The Fleet-WIDE aggregate is a `FleetTotals` — total tokens (input/output) + total derived dollars across ALL instances (AC-A — FR-22 "Fleet-wide"; the greenfield).** A `FleetTotals` struct (record the module — RECOMMENDED `domain::fleet`, sibling to `FleetListing`/`FleetEntry`/`UsageView`) carrying: `total_input_tokens: u64` + `total_output_tokens: u64` (cumulative across every instance, every Run), `total_dollars: Option<Micros>` (the summed derived cost — see AC5 for the `Option`/label rule), and the `estimate_label: Option<EstimateLabel>`. Derive `Serialize`/`Deserialize` (snake_case integer micros — NO `$` string, NO `f64` — AD-8/AD-14). It is computed PURELY from the `Vec<FleetEntry>` (sum `usage.cumulative_input_tokens`/`cumulative_output_tokens`; sum `usage.cumulative_dollars` where present) using saturating integer arithmetic — so the aggregate is a pure function `FleetTotals::from_entries(&[FleetEntry]) -> FleetTotals`, unit-testable with NO engine/IO and cross-OS by construction. Record: tokens are ALWAYS summable (every instance has a real token total, `0` if never metered — 3-1); dollars are summable only across instances that HAVE a derived cost (a Rate) — an instance with no Rate contributes `0` dollars to the aggregate but does NOT make the aggregate absent (see AC5/AC6). NO per-scope (per-run) Fleet aggregate is required by the AC — the Fleet-wide total is CUMULATIVE (a "per-run" total is meaningful per-instance, not across instances that are each in different Runs); record this decision (RECOMMENDED cumulative-only Fleet aggregate; a per-instance per-run scope stays a per-instance concern).

4. **Zero-not-absent: an unmetered / no-Rate instance contributes an honest `0`, never a fabrication or an omission (AC-A, AC-B — the honesty crux; AD-8, FR-23, SM-C3).** THE load-bearing honesty rule of the aggregate. When summing the Fleet: (i) a never-metered instance has a genuine all-zero `UsageTotals` (3-1's "truthful zero" — the ledger literally holds zero tokens for it), so it contributes `0` tokens — it is COUNTED (present in the sum), not skipped (skipping would silently understate nothing here, but the DISCIPLINE is that every instance is in the sum, so the count of instances and the token total are mutually consistent). (ii) A no-Rate instance contributes `0` dollars to `total_dollars` — but this `0` must NOT be presented as "this instance cost `$0.00`" (it cost an UNKNOWN dollar amount — there is no Rate to derive it); the aggregate handles this by the AC5 rule (the presence of ANY no-Rate-but-metered instance makes the Fleet dollar total a PARTIAL estimate that must say so — see AC5). (iii) NEVER fabricate: no instance is assigned a made-up token count or a `$0.00` cost it did not incur; NEVER omit: no metered instance is silently dropped from the token sum. Record the exact rule as a testable invariant: `FleetTotals::from_entries` over N instances sums exactly N token contributions (each ≥ 0), and the dollar total is the sum of ONLY the instances with a derived cost, with the label/partial-ness flag reflecting whether any metered instance lacked a Rate. Unit-test: an empty Fleet → all-zero totals, dollars honestly absent/`None` (nothing to estimate); a Fleet of one → the aggregate equals that instance's totals; a mixed Fleet (one Rate'd, one no-Rate-but-metered, one never-metered) → tokens sum ALL three, dollars sum only the Rate'd one AND the total is flagged partial/estimated because a metered instance had no Rate.

5. **The mixed / estimated / partial Fleet dollar total is LABELED honestly — never presented as exact (AC-B — AD-8, FR-23, SM-C3; the crux).** The Fleet-wide `total_dollars` must be honest about three kinds of imprecision, and the rule is: **if ANY component is estimated, the total is estimated; if the total omits a metered instance's real-but-unpriced consumption, it says so.** Concretely: (i) v1 EVERY derived dollar is `estimated` (3-3), so any non-empty `total_dollars` carries `estimate_label = Estimated` — there is no path to a `reconciled` Fleet total in v1 (record this: the `reconciled` arm is a forward seam, unreachable until reconciliation ingestion ships). (ii) If the Fleet MIXES metering sources (some `self-reported`, some `engine-observed`), the dollar total is STILL a single `estimated` figure — both sources are estimates, so mixing them does not make it MORE dishonest, but the aggregate MUST NOT imply the sources are provider-confirmed actuals (they are not); the visible per-instance provenance (AC7) lets the reader see the mix. (iii) **Partial-ness** (the subtle one): if the Fleet contains a metered instance with NO Rate, its real token consumption has an UNKNOWN dollar cost that the aggregate CANNOT include — so `total_dollars` is a LOWER BOUND, not the true total. Record the honest presentation (RECOMMENDED: a flag/marker on `FleetTotals` — e.g. `dollars_partial: bool` or an `Option<Micros>` that is `None` when NO instance has a Rate and a labeled value with a "partial" note when SOME-but-not-all metered instances have Rates) so the human view can render "≈ $X.XX (estimated; N instances unpriced)" and `--json` carries the flag. Do NOT chase precision into presenting the partial sum as the exact Fleet cost (SM-C3 — "estimate precision theater"; honesty labels outrank precision). Record the exact chosen shape + the human phrasing. NEVER: a Fleet dollar total rendered WITHOUT its label; a partial total rendered as if complete; a `$0.00` Fleet total when instances are metered-but-unpriced (that is "unknown", surfaced as absent/partial, not zero).

### The honest-aggregation rules (the crux — define exactly)

**The deliverable is TWO surfaces + FOUR honesty rules. **Key design decision 1 — the aggregate is PURE over the already-composed entries; one read pass, saturating integers, no float (THE efficiency + correctness crux).** `FleetTotals::from_entries(&[FleetEntry]) -> FleetTotals` is a PURE function over the `Vec<FleetEntry>` the `fleet()` read already built (`engine.rs:409`) — it issues NO new ledger query (the per-instance totals are already read), uses `UsageTotals`-style saturating `u64` adds for tokens and `Micros::saturating_add` for dollars (NO `f64`, NO un-saturated sum — a runaway Fleet must not wrap or drift), and is engine-`domain`-side (AD-1/AD-2). Because it is pure, its exhaustive honesty tests (empty / one / mixed / all-Rate'd / saturation / zero-not-absent) are cheap and cross-OS by construction — the bulk of coverage lives here, mirroring how 3-3 put the money-math coverage in the pure `cost_micros` tests. This keeps 3-5 the LIGHTEST Epic-3 story: the greenfield is one pure function + one document field + one human footer.

**Key design decision 2 — the honest-aggregation rules are the crux: LABEL what mixes/estimates, COUNT the honest zero, SAY SO when partial (AC4, AC5, AC7 — AD-8/FR-23/SM-C3).** A naive `sum()` would be dishonest in three ways this story must prevent. (i) **Label the estimate:** every v1 dollar is `estimated`, so any non-empty Fleet dollar total is `estimated` — the aggregate carries the label as data and renders it through the one currency module; there is NO `reconciled` Fleet total in v1 (the arm is an unreachable forward seam). (ii) **Count the honest zero, don't fabricate/omit:** a never-metered instance contributes a genuine `0` tokens (it IS in the sum — the ledger truly holds zero for it, 3-1's "truthful zero"); a no-Rate instance contributes `0` dollars but is NOT claimed to have cost `$0.00` (its dollar cost is UNKNOWN). (iii) **Say so when partial:** if a metered instance has NO Rate, its real token consumption has an unknown dollar cost the aggregate cannot include — so the Fleet dollar total is a LOWER BOUND, flagged `dollars_partial` and rendered "≈ $X.XX (estimated; M unpriced)" (record the exact phrasing), never as the exact Fleet cost (SM-C3 — honesty outranks precision).
