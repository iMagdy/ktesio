# Story 2.2: Map unified config to each agent's native mechanism

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want documented unified keys delivered into the agent's native config (files, env, flags) by its adapter, with agent-native extras under an explicit `agent.*` pass-through,
so that I configure agents without learning per-agent formats. (FR-12)

## Acceptance Criteria

Verbatim from `epics.md` Story 2.2 (the SECOND story of Epic 2 — config). The two headline ACs are the adapter-mapped delivery of a documented unified key into the agent's native mechanism, proven on BOTH the mock adapter and a manifest adapter (AC-A), and the `agent.*` verbatim delivery + "unvalidated" marking in effective-config output (AC-B). The derived criteria below make the adapter-declared mapping, the three native delivery targets, the exact point in the start path where the mapping is applied, and the seams for 2-3/2-4 explicit and testable.

> **CRITICAL SCOPING (read before AC-A):** This story delivers the **unified→native config MAPPING** — the adapter-declared mapping of documented unified keys into the agent's native mechanism (config FILE / ENV vars / CLI FLAGS), applied at START, proven on the mock adapter AND a manifest adapter; plus `agent.*` verbatim delivery and the minimal "unvalidated" marker in effective-config output. It BUILDS ON story 2-1's resolver: it CONSUMES the resolved [`EffectiveConfig`](crates/ktesio-engine/src/domain/config.rs) (values + per-leaf `SourceLayer`) and hands the values to the adapter to place into the launch. It does NOT re-open the layered model, the precedence rules, or write-time validation (all 2-1, done). It does NOT deliver: the full effective-config PROVENANCE rendering + the persisted `EffectiveConfig` snapshot at start — that is **2-3 (FR-13)** (2-2 only needs the minimal `agent.*`-unvalidated marker, reusing 2-1's `SourceLayer`/pass-through seam); and **secrets** (`secret:` resolution, `SecretString`, masking) — that is **2-4 (FR-14, AD-10)** (a `secret:` value in 2-2 stays opaque text delivered as-is into the native mechanism, un-resolved and un-masked). Build NONE of those here. Where the mapping must leave a seam for a later story (a value that 2-4 will later resolve/mask before it reaches the native mechanism; a provenance tag 2-3 will render/persist), note it as a seam and stop.

1. **AC-A (documented unified key → native mechanism, both adapter kinds).** **Given** a documented unified key (e.g. model selection) **when** the instance starts on the mock adapter AND on a manifest adapter in tests **then** the key lands in the agent's native mechanism per the adapter's mapping. The mapping mechanism is DECLARED by the adapter (the manifest adapter declares it in `adapter.toml`; the native/mock adapter declares it in code), and APPLIED at start (as the launch spec is built), so the SAME unified key resolves into whatever native shape each adapter declares — a config file entry, an environment variable, or a command-line flag — WITHOUT the operator learning the per-agent format.

2. **AC-B (`agent.*` verbatim + unvalidated marking).** **Given** keys under `agent.*` **when** the instance starts **then** they are delivered verbatim (the exact key-tail + value, no rewriting, no known-key validation — the 2-1 bypass) into the agent's native mechanism, and rendered as **unvalidated** in effective-config output. 2-2 delivers the verbatim placement AND the minimal unvalidated MARKER on `agent.*` leaves in `kt agent config get`; the full per-value source-layer rendering + the persisted snapshot remain 2-3.

### Derived / consequence criteria (make explicit; enforced by tests)

3. **The mapping is a first-class, adapter-DECLARED contract (AD-9 + Adapter Contract).** A unified key does not map itself — the ADAPTER declares how each documented unified key becomes native. For a **manifest** adapter this is a NEW declarative `[config]`-style mapping section in `adapter.toml` (a per-unified-key rule naming the native TARGET: a `file` entry, an `env` var name, or a `flag`); its serde types + validation live ONLY in `ktesio-adapter-api` (AD-3 — the engine defines no schema, it consumes the parsed form). For a **native** adapter (mock, and later hermes) the mapping is expressed in code (a mapping accessor on the adapter / a native mapping table), because a native adapter carries no `adapter.toml`. Both kinds produce the SAME uniform mapping shape the start path applies (AD-3 "two kinds, one trait"). Record the exact declared shape (the mapping-rule model + the three target kinds).

4. **Three native delivery targets: config FILE, ENV vars, CLI FLAGS (FR-12 verbatim mechanisms).** The mapping resolves each unified key to exactly one of three native mechanisms: **(a) a config FILE** — the engine renders a native config artifact into the Agent Home (a file the agent reads at start; the engine is the sole writer, path authority AD-6/AD-9); **(b) an ENV var** — the key is placed in the spawned process's environment (`StartLaunch.env`); **(c) a CLI FLAG** — the key is appended to the launch arguments (`StartLaunch.args`). At minimum the documented `model` key must be provable via one target on the mock adapter and one target on a manifest adapter (AC-A). Record which target each of the two proving adapters uses and why (the recommended split keeps coverage honest: e.g. mock → env, manifest → flag or file).

5. **The mapping is APPLIED at start, from the resolved effective config, at ONE seam (AD-9 "start resolves…").** At start the engine ALREADY resolves the four layers into an [`EffectiveConfig`] (2-1) — 2-2 threads that resolved config into launch-spec construction. The mapping runs at the SAME point `resolve_start_launch` builds the `StartLaunch { exec, args, env }` (`crates/ktesio-engine/src/adapter/mod.rs`), so the launch the [`SpawnSpec`](crates/ktesio-engine/src/ports/process_backend.rs) carries already reflects the mapped native config, BEFORE `supervisor.rs::start_inner` spawns (`crates/ktesio-engine/src/domain/supervisor.rs` ~190-228). A unified key with no mapping declared by the adapter is delivered nowhere silently — record whether an unmapped documented key is a no-op or a typed error (RECOMMENDED: a documented key the adapter does not map is a no-op, since not every adapter supports every unified key; a mapping rule that names a target is what makes it land).

6. **`agent.*` pass-through is delivered verbatim through the SAME mapping seam, but bypasses known-key mapping (AC-B, 2-2 consumes 2-1's seam).** A resolved leaf under `agent.*` (2-1's [`PASS_THROUGH_PREFIX`]) is delivered to the native mechanism VERBATIM: the key-tail after `agent.` and its value, with NO rewriting and NO known-key mapping lookup. Record the verbatim delivery target for pass-through (RECOMMENDED: pass-through keys map to env/flags by a documented default convention, OR require the adapter to declare a pass-through target shape — record the choice; the value is delivered as-is either way). This reuses 2-1's `is_pass_through` boundary; 2-2 adds only the DELIVERY of pass-through, not a new namespace.

7. **`agent.*` leaves are rendered as "unvalidated" in effective-config output — the MINIMAL 2-3 seam (AC-B).** `kt agent config get` (2-1's read) marks each `agent.*` leaf as **unvalidated** (a per-row marker / annotation), so the operator sees which values skipped known-key validation. This is the ONLY effective-config-output change 2-2 makes; it REUSES 2-1's `SourceLayer` seam and the `agent.*` boundary (a leaf is "unvalidated" iff its dotted key `is_pass_through`). 2-2 does NOT render the per-value SOURCE LAYER and does NOT persist the `EffectiveConfig` snapshot at start — both remain 2-3 (FR-13). Record that the marker is derived from the pass-through prefix, not from a new persisted field.

8. **Both adapter kinds prove the mapping in tests (AC-A — the non-negotiable coverage).** The mapping is proven end-to-end on BOTH kinds, mirroring FR-12's "reference Adapter and a mock second Adapter": **(1) the MOCK/native adapter** — the engine's builtin `mock` (`crates/ktesio-engine/src/adapter/builtin.rs`) gains a code-declared mapping for the documented `model` key; a start test asserts the mapped native target carries the value; **(2) a MANIFEST adapter** — a test manifest with a `[config]` mapping section declares the documented `model` key → a native target; a start test (reusing the `fake_agent` fixture + `resolve_start_launch`, story 1-4/`crates/ktesio-conformance/src/lib.rs`) asserts the value lands in the declared native mechanism. The `agent.*` verbatim delivery is proven on at least one kind. Record the two adapters + the target each proves.

9. **Output discipline + honest scoping notes (AD-12).** The `agent.*`-unvalidated marker rides `kt agent config get`'s STDOUT (part of the result table); any note pointing to 2-3 for full provenance stays on STDERR (2-1's existing `CONFIG_PROVENANCE_EPIC3_NOTE` convention). No source-layer column, no snapshot, no secret masking — 2-2 renders none of them and MUST NOT fabricate a source label or mask a value it does not resolve. The mapping surface introduces no new interactive prompt (FR-34).

### The mapping design (the story's core value — define exactly)

**Two things are the deliverable: an adapter-DECLARED mapping, and the APPLICATION of that mapping at start.**

| Concern | Mechanism | Surface |
| --- | --- | --- |
| **Adapter declares the mapping (AC3)** | A mapping-rule model (`ktesio-adapter-api`): unified key → `ConfigTarget::{File, Env, Flag}`. ### Findings by severity

1. **[MEDIUM] [in-scope] [testable/low-risk] — False documentation + missing drift guard: the builtin↔conformance mock `config_mapping()` parity test was never added.** The File List and `docs/testing.md` both claim `crates/ktesio-engine/tests/registration.rs` was "extended … to assert the two mappings are identical (guarding the fixture against drift)." Verified false: `registration.rs` is untouched by this diff and contains no `config_mapping` assertion (`conformance_mock_fixture_matches_builtin_shape` compares only the Capability Declaration + inertness). The two `model → env MODEL` declarations (`adapter/builtin.rs:106`, `ktesio-conformance/src/lib.rs:109`) are only *independently* unit-tested, so nothing catches a future drift. `docs/testing.md:41` now ships a statement about a test that does not exist — a `check_docs`-passing but factually wrong claim. **Fix:** add the promised `assert_eq!(builtin.config_mapping(), fixture.config_mapping())` (or per-key compare) to `conformance_mock_fixture_matches_builtin_shape`, OR correct the File List + `docs/testing.md` to not claim it.

2. **[LOW→MEDIUM] [follow-up] [low-risk] — Native (code-declared) `File` targets bypass path-safety validation.** `is_safe_relative_path` is enforced only via `Manifest::validate` (the manifest arm). `adapter::resolve_config_mapping`'s native arm (`adapter/mod.rs:316`) returns `native_config_mapping(kind).unwrap_or_default()` with no `validate()`, and `apply_config_mapping` then `home.join(rel_path)` on it ("a native mapping is trusted"). Latent only — the sole shipping native adapter (`mock`) declares an env target — but the next native adapter (`hermes`, epic 6) declaring `ConfigTarget::file("../x", …)` would write outside the Agent Home (AD-6 violation). **Fix:** call `mapping.validate()` in the native arm too, or re-check each `File` placement path inside `apply_config_mapping` before joining. Asymmetric trust between the two kinds is a trap given AD-3's "two kinds, one shape."

3. **[LOW] [follow-up] [low-risk] — `is_safe_relative_path` is too lenient + its doc comment is inaccurate (cross-platform).** Independently confirmed the check accepts `.`, `a//b`, `a/./b`, `./a`, and Windows drive paths `C:\x` / `C:x` as "safe" (it rejects only a leading `/`/`\`, a literal `..` segment, and UNC `\\…`). Consequences: (a) the comment at `config.rs:271-276` claims "a Windows drive/UNC absolute would fail the same relative-only intent" — **false** for `C:x`/`C:\x`; on a Windows host `home.join("C:\\x")` discards the home. Today this is contained (no manifest ships a `C:` path and the Windows CI gate only compiles the backends), but the reassuring comment is wrong. (b) `path = "."` passes validation then fails the write with a low-level `IsADirectory` detail rather than a clear validate-time rejection; `a//b`/`./a` write to non-canonical in-home locations. **Fix:** reject empty and `.` segments and any drive-letter/`:` prefix in `is_safe_relative_path` (still path-agnostic `std`, no OS-cfg), and fix the comment. Note: Windows path portability is now a live CI gate — worth closing even though no in-home escape is reachable today.

4. **[LOW] [follow-up] [low-risk] — Pass-through / config env delivery can silently shadow a base-launch env var, order-dependently, with no diagnostic.** `apply_config_mapping` runs AFTER `resolve_start_launch` has seeded `launch.env` from the manifest `[lifecycle.start].env`, and delivers via `BTreeMap::insert` (last-write-wins). So (a) a mapped known-key env target or an `agent.<TAIL>` pass-through **overwrites** a same-named base-launch env var — a sensible "operator config beats adapter default" precedence, but undocumented and untested; (b) an `agent.FOO` tail and a known-key target named `FOO` collide, with the winner decided by effective-config key sort order, silently. Not a security boundary (the operator already controls the manifest and the whole config in this single-tenant runner; `agent.PATH`/`agent.LD_PRELOAD` are accepted by 2-1's `validate_write` but are equivalent to the operator editing `[lifecycle.start].env`). It is a least-surprise/robustness gap. **Fix:** document the precedence in the seam doc; consider warning when a config write shadows an existing `launch.env` key. Add a test that applies onto a launch pre-seeded with a colliding env var + a colliding `--flag` (current tests only apply onto `empty_launch()`).

5. **[LOW] [follow-up] [low-risk] — Multi-file apply is not atomic, and the module doc overstates the guarantee.** `apply_config_mapping` writes accumulated `File` targets sequentially (`adapter/mod.rs:401-403`); if a later file fails, an earlier rendered file is already on disk in the Agent Home. Start-*state* atomicity is genuinely correct (all config/apply failures reject BEFORE the `starting` transition — verified; the throwaway `launch`/env/args are dropped), but the doc claim "never a half-written home" (`adapter/mod.rs:267-268`) holds only for a single file. Self-healing (a later successful start re-writes by path), hence LOW. Separately, `write_config_file` uses a raw `std::fs::write` (create-truncate, not temp+rename), so a crash mid-write leaves a truncated native config file. **Fix:** temp-file + rename for the write; soften or qualify the doc claim.

6. **[NIT] [testable/low-risk] — Loose substring assertion in a CLI test.** `config_get_known_key_only_shows_no_unvalidated_marker` asserts `stdout.contains("validated")`, which is also a substring of `"unvalidated"`; the companion `!contains("unvalidated")` keeps the aggregate correct, but the positive assertion is imprecise. Minor test-craft only.
