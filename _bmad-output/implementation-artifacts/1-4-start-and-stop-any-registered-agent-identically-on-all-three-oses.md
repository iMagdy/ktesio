## Story

As an Operator,
I want `start` and `stop` to behave the same for every agent,
so that lifecycle knowledge transfers across agents and platforms. (FR-5, FR-6, FR-8 core)

## Acceptance Criteria

*(Verbatim from epics.md Story 1.4; AC numbering added for task traceability.)*

1. **Given** a registered Agent Instance (mock or manifest) and the tokio-based supervision core (AD-13; exact tokio version pinned and recorded at adoption) **when** I start it **then** the adapter launches it with the Agent Home's effective config applied, state transitions `registered→starting→running` per the data-driven transition table (AD-15), and each transition emits an event with prior state, new state, cause, timestamp.
2. **And** a failed launch lands in `failed` with the adapter's diagnostic preserved and no zombie process.
3. **When** I stop a running instance **then** graceful shutdown is requested via the adapter and escalates to forced termination after the configurable window (default 30s), the escalation is recorded in the instance log, and no process of the instance survives — verified on Linux, macOS, and Windows (Unix process groups / Windows Job Objects per AD-4, NFR-2).
4. **And** invalid transitions (e.g. stop on `stopped`) return the same error class for every adapter (FR-8).

### Acceptance criteria — engineering interpretation (binding for dev)

- **AC1 — tokio adoption + async engine (AD-13, Islam-APPROVED in this story).** The engine internals go async on tokio (multi-thread runtime). The Embedding Interface exposes async methods PLUS a thin `blocking()` facade; `kt` uses the facade. **ZERO behavior change to existing kt commands** (register/remove/list/show): every existing test (525 at 1-3 completion) must stay green. The async refactor is mechanical but touches all 1-2/1-3 engine code — call it out and keep the diffs behavior-preserving. See Dev Notes "Async refactor + blocking facade (the exact shape)".
- **AC1 — "effective config applied" SCOPE BOUNDARY (FR-5).** FR-5 says start applies effective config + Skill Set + Memory Backing + budgets. **Skill Set (Epic 8), Memory Backing (Epic 5), and budgets (Epic 3) do not exist yet.** So 1-4 applies ONLY what exists: **the adapter/manifest's config** — for a manifest adapter, the `[lifecycle.start]` `exec`/`args`/`env` template (from 1-3's `OpTemplate`); for the native builtin/mock, its equivalent. State this boundary in the executor doc. Do NOT stub Skill Set / Memory / budget wiring speculatively.
- **AC1 — "each transition emits an event" SCOPE BOUNDARY (FR-8).** Full host event SUBSCRIPTION is story 7-2. **For 1-4 an "event" = a RECORDED/emitted state transition** (prior state, new state, cause, timestamp), NOT the host subscription API. Minimum viable: an in-engine transition-event type (an AD-14 seed struct with `schema_version`) that is (a) recorded to the instance log (AC3 needs a log to record the escalation into anyway) and/or (b) returned/observable so tests can assert it. Do NOT build the bounded-channel subscription bus (7-2). State this boundary. See Dev Notes "What an 'event' is this story".
- **AC1 — state transition `registered→starting→running` (AD-15).** Driven by the DATA transition table (state × command → state | error), not ad-hoc `if`s. `starting` is entered on the `Start` command; `running` on adapter-ready. The transition is persisted to the `agent_instances.state` column (1-2's store) AND emits the transition event. See Dev Notes "The transition table (as data)".
- **AC2 — failed launch → `failed`, diagnostic preserved, NO zombie.** If the adapter's launch fails (exec not found, spawn error, immediate non-zero exit during startup), the instance lands in `failed` with the adapter's diagnostic **preserved verbatim** (surfaced to `kt` and recorded), and **no orphan/zombie process** remains (on Unix, reap the child / kill the process group; on Windows, close the Job Object). Prove it with a manifest whose `exec` does not exist and with a fixture that exits non-zero on start.
- **AC3 — stop graceful→forced, window default 30s configurable, recorded, NO survivor (cross-platform).** `stop` on `running` transitions `running→stopping`, requests graceful shutdown via the backend, and if the process has not exited within the window, escalates to forced termination; then `stopping→stopped`. The escalation is **recorded in the instance log** (AD-12 seed: a per-instance log file). **No process of the instance survives** — verified on all 3 OSes: **Unix** = SIGTERM to the process group → SIGKILL to the group after the window (kills the whole tree, catching child processes the agent spawned); **Windows** = graceful request → `TerminateJobObject` (kills every process in the Job). The window is per-instance configurable with a 30s default (`[ASSUMPTION]` on the config surface — see Dev Notes).
- **AC4 — invalid transitions return the SAME error class for every adapter (FR-8).** `stop` on `stopped`, `start` on `running`, `resume` on `running`, etc. return ONE uniform error class (e.g. `LifecycleError::InvalidTransition { from, command }`) regardless of adapter kind — because the rejection comes from the shared transition table in the engine core, never from per-adapter code. Prove it fires identically for the native builtin and a manifest adapter.
- **SCOPE — what this story does NOT do (explicit).** NO pause/resume execution (1-5; `Paused` stays unreachable — the table may name `paused` as a target but no command reaches it this story). NO crash detection / Restart Policy / orphan adoption (1-6; the `running→failed` "crash detected" edge and `on-failure` restart are 1-6 — but the `starting→failed` "launch error" edge IS this story). NO write-ahead spawn records / AD-5 (that is 1-6's orphan-adoption mechanism; 1-4 supervises within a single engine lifetime). NO budgets/metering (Epic 3). NO Skill Set / Memory (Epics 5/8). NO `--json` on read commands (1-7). NO config layering (Epic 2).

### The transition table (as data) — AD-15

Model the table as an exhaustive function over the two enums (this IS "data" per AD-15 — a total match is a table; no external data file needed):

```
enum LifecycleCommand { Start, Stop /* Pause, Resume = 1-5; not wired here */ }

// Pure, no I/O. The supervisor calls this, then persists + emits.
fn next_state(from: LifecycleState, cmd: LifecycleCommand)
    -> Result<LifecycleState, LifecycleError>
{
    use LifecycleState::*; use LifecycleCommand::*;
    match (from, cmd) {
        (Registered, Start) => Ok(Starting),
        (Stopped,    Start) => Ok(Starting),   // restart of a stopped instance (FR-5: registered/stopped)
        (Running,    Stop)  => Ok(Stopping),
        // starting→running (adapter ready) and starting→failed (launch error) and
        // stopping→stopped are driven by the supervisor on process events, NOT by a
        // command — represent them as separate supervisor-side transitions or as
        // additional table rows keyed by an internal event, document which.
        (from, cmd) => Err(LifecycleError::InvalidTransition { from, command: cmd }),
    }
}
```
- **Command-driven vs event-driven edges.** `Start`/`Stop` are OPERATOR commands. `starting→running` (adapter ready), `starting→failed` (launch error), `stopping→stopped` (process exited) are SUPERVISOR reactions to process events, not commands. `[ASSUMPTION]`: model the command-driven edges in `next_state`, and the event-driven edges as explicit supervisor transitions (each still emitting the AD-14 event + persisting). Alternatively fold both into one table keyed by a `LifecycleTrigger { Command(..) | Event(..) }` — either is fine; DOCUMENT the shape you pick. The AC4 uniform-error requirement only bites on COMMAND rejections (stop on stopped, start on running), so the command table must be total and return the single `InvalidTransition` class.
- **AC4 proof:** the SAME `InvalidTransition` is returned for the native builtin and a manifest adapter because the rejection is in `next_state` (engine core), before any adapter code runs. Test both adapters hitting `stop` on `stopped` and `start` on `running`; assert identical error class.
- **Exhaustive test:** iterate representative `(state, command)` pairs; assert the reachable ones map correctly and all others return `InvalidTransition`. Cheapest coverage in the story.

### ProcessBackend port + per-OS module layout — AD-4 `[ASSUMPTION on names]`

```text
crates/ktesio-engine/src/
  ports/process_backend.rs   # ProcessBackend trait, SpawnSpec, ProcessHandle, StopOutcome, BackendError (hexagonal; NO cfg here)
  backends/
    mod.rs                   # #[cfg(unix)] mod unix; #[cfg(windows)] mod windows;  + `fn current() -> impl ProcessBackend` factory. THE cfg boundary.
    unix/mod.rs              # UnixBackend: spawn into a process group; SIGTERM→SIGKILL via nix. #[cfg(unix)].
    windows/mod.rs           # WindowsBackend: Job Object per instance; graceful→TerminateJobObject via windows-sys. #[cfg(windows)].
```
- **The port trait (in `ports/`, cfg-free):**
  ```
  pub trait ProcessBackend {
      fn spawn(&self, spec: &SpawnSpec) -> Result<ProcessHandle, BackendError>;
      fn stop(&self, handle: &ProcessHandle, graceful_window: Duration) -> Result<StopOutcome, BackendError>;
      // (poll/is-alive may be needed for the starting→running readiness check + stopping→stopped detection)
  }
  ```
  `[ASSUMPTION]`: whether `spawn`/`stop` are async or sync on the trait. Recommend **sync trait methods** that the async supervisor calls via `spawn_blocking` for the OS syscalls, with the graceful-window WAIT done in the async supervisor (`tokio::time::timeout`) rather than a blocking sleep inside the backend — that keeps the backend a thin syscall wrapper and the timing in tokio. Alternatively make `stop` async. Tag the choice. Either way the OS syscalls (setpgid, killpg, Job Object calls) are the only OS-specific code and live only in `backends/`.
- **`SpawnSpec`**: `{ exec: PathBuf/String, args: Vec<String>, env: BTreeMap<String,String>, working_dir: PathBuf (the Agent Home), /* stdout/stderr capture targets = the instance log seed */ }`. Built from the manifest `OpTemplate` (1-3) or the native builtin.
- **`ProcessHandle`**: holds the OS identity — on Unix the child PID + the process-group id; on Windows the process handle + the Job handle — plus a **start-time fingerprint** (capture it now; it is 1-6's PID-reuse-safe adoption key, cheap to grab at spawn). Keep the OS-specific fields inside `backends/` (e.g. an opaque handle the port exposes); the supervisor holds it without naming OS types.
- **Why NOT tokio's built-in process groups:** tokio's `Command::process_group` and related process-group support wrap std APIs that are **unstable** and require `--cfg tokio_unstable` (verified 2026-07-04; the `nix-installer` project documents exactly this constraint). We must NOT depend on `tokio_unstable`. So: spawn the child (via `std::process::Command`/`tokio::process::Command`) and set the process group / assign the Job Object using `nix` (Unix) / `windows-sys` (Windows) directly, in `backends/`. This is the reason `nix` and `windows-sys` are consequential new deps of AD-4 (see "New dependencies + versions").
- **The rest of the engine is cfg-free.** The supervisor names `ProcessBackend` (the trait) and gets the concrete via `backends::current()`. No `#[cfg]` anywhere but `backends/`. The OS-cfg CI gate ALREADY allows `^crates/ktesio-engine/src/backends/` — you are filling the home it was built for. (Note: the gate is a text grep — keep doc comments free of `cfg(...)`-shaped tokens with OS words, per 1-2/1-3 near-misses.)

### What an "event" is THIS story (FR-8 scope boundary)

FR-8 says "every transition emits an event"; FR-33/story 7-2 owns the host event SUBSCRIPTION API (ordered per-instance delivery, bounded channels, slow-subscriber policy). **For 1-4, "event" = a recorded/emitted state transition** — NOT the subscription bus. Concretely, 1-4 delivers:
