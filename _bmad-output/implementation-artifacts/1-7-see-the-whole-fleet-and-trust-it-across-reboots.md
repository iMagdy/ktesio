# Story 1.7: See the whole Fleet — and trust it across reboots

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want a Fleet listing that reflects reality and state that survives engine restarts and machine reboots,
so that I can always answer "what is running and in what state." (FR-4, FR-10)

## Acceptance Criteria

Verbatim from `epics.md` Story 1.7 (the TRUST story). The three headline ACs are the Fleet listing (AC-A), reboot durability + reconciliation (AC-B), and the ≤1s usage-loss bound (AC-C); the derived criteria below make the `--json` schema shape, the 2-second freshness mechanism, the reboot-reconciliation path, the honest metering-seed columns, and the durability test explicit and testable.

> **CRITICAL SCOPING (read before AC-A):** Budgets/caps and the Usage Ledger are **Epic 3 (metering)** — they DO NOT exist in Epic 1. AC-A's "budget/cap status" and "Usage Ledger totals" columns are therefore rendered as **honest seeds** (`—` / `n/a`, with a one-line note that metering arrives in Epic 3), NOT fabricated numbers. Likewise AC-C's "usage data" durability: Epic 1 has no usage data, so AC-C is satisfied by the EXISTING AD-6 per-event-transaction mechanism that already protects lifecycle state / registrations; the story VERIFIES that durability and DOCUMENTS that the ≤1s bound applies to usage once Epic 3 lands. This mirrors how story 1-5 handled "there is no metering yet in Epic 1" and how 1-6 seeded the (empty) restart columns.

1. **AC-A (Fleet listing).** **Given** several Agent Instances in different Lifecycle States **when** I list the Fleet **then** each row shows **name, Agent kind, Lifecycle State, budget/cap status, and Usage Ledger totals**, reflects any transition **within 2 seconds**, and is available as **human-readable AND `--json`**.

2. **AC-B (reboot durability + reconciliation).** **Given** a machine reboot while instances were running **when** the engine starts and I list the Fleet **then** every **registration, budget, and ledger total is intact** and previously-running instances show **`stopped`/`failed` per orphan reconciliation** — never lost.

3. **AC-C (≤1s usage-loss bound).** **And** a crash of the engine itself loses **at most 1 second of usage data** (AD-6 per-event transactions).

### Derived / consequence criteria (make explicit; enforced by tests)

4. **The listing columns are complete AND honest (AC-A + scoping).** `kt agent list` renders, per instance: **Name**, **Kind** (the Agent kind), **Lifecycle State**, **Restarts** (already present from 1-6), **Budget/cap** and **Usage** columns, and the **Agent Home**. Because metering is Epic 3, the **Budget/cap** and **Usage** cells render a single honest placeholder (`—`, or `n/a`) and the command prints ONE stderr note (AD-12: notice → stderr) that budget/cap status and Usage Ledger totals arrive with metering in Epic 3. The columns are PRESENT (so the shape is stable for Epic 3 to fill) but NEVER show a fabricated number. `kt agent show <name>` likewise surfaces the same budget/usage seed rows in its runtime-status block. No number is invented; a `—` is the truthful Epic-1 value.

5. **`--json` is added to `list` (and `show`), serializing the AD-14/AD-12 shape (AC-A).** A `--json` flag is added to `AgentCommands::List` and `AgentCommands::Show` (it exists TODAY only on the unrelated `skills` `list`/`show` — the Agent subcommands take no `--json` yet). With `--json`, the command writes a single machine-readable JSON document to **stdout** and NOTHING else to stdout (AD-12: result → stdout, diagnostics/notes → stderr; the Epic-3 metering note still goes to stderr). The document is an array (for `list`) / object (for `show`) whose per-instance object carries at least `{ name, kind, state, restart_count, restart_policy, budget: null, usage: null, agent_home }` plus a top-level `schema_version` (AD-14: `kt --json` serializes the SAME versioned serde structs the Host event stream will publish). `budget`/`usage` are explicit `null` (the honest Epic-1 seed — a typed absence, not `0`). The JSON is stable, snapshot-testable, and re-parseable.

6. **The 2-second freshness bound is met by reading live state on every listing (AC-A).** "reflects any transition within 2 seconds" is satisfied structurally: each `kt agent list` / `--json` invocation opens the engine and reads the CURRENT persisted Lifecycle State + restart count from the one SQLite store (AD-6) at call time — there is no cache to invalidate, so a transition committed before the listing is always reflected (latency is a single DB read, far under 2s). For a long-lived embedding (a Host holding one `Engine`), the same freshness holds because the crash-detection reaper commits state transitions to the store as they happen (250ms poll, story 1-6) and the read path always hits the store. The story documents this mechanism; the freshness assertion is exercised by a test that transitions an instance (e.g. start → the reaper marks a crash `failed`) and asserts a fresh listing reflects the new state.

7. **Reboot durability is real and reconciled through the EXISTING orphan-adoption path (AC-B).** A machine reboot = every prior agent process is gone (PIDs do not survive a reboot) AND the engine process is gone. On the next `Engine::open`, the story-1.6 `Supervisor::adopt_orphans` reconciliation runs over the persisted write-ahead spawn records: since NO fingerprint can match a live process after a reboot, EVERY previously-`running`/`paused` instance reconciles to **`failed`** ("orphan not found on engine restart") — honestly, never left implying supervision (AI-8). All durable state — registrations (`agent_instances`), lifecycle state, restart policy + restart count (`agent_runtime`), and (once Epic 3 lands) budgets + ledger — survives byte-intact because it lives in the one SQLite DB (AD-6), not in volatile memory. This story ADDS NO new reconciliation logic; it VERIFIES the 1-6 path covers the reboot case and documents that a reboot is the "all processes gone" special case of engine-crash recovery.

8. **Durability test: reopen over the same state dir loses nothing (AC-B / AC-C).** An integration test proves the guarantee end-to-end by SIMULATING a reboot (a true reboot is infeasible in CI): register several instances in different states, start one via the SURVIVING-engine subprocess harness (reused from 1-6 `tests/adoption.rs` — an engine-1 subprocess starts the agent then `exit`s WITHOUT dropping the engine, so the child survives + re-parents to init), then either kill ALL agent processes (fabricating "every process gone" = the reboot condition) or just drop/reopen the engine over the SAME state dir. Assert: (a) every registration is still present with its name/kind/home intact; (b) the previously-running instance is reconciled to `failed` (reboot condition) — never lost or left `running`; (c) the restart policy + count persisted for each instance are unchanged; (d) no orphan process remains. AC-C is asserted structurally by the store's per-event-transaction property (AD-6: WAL, `synchronous=NORMAL`, one transaction per state mutation) plus a documented note that the ≤1s bound governs Usage Ledger writes once Epic 3 adds them — Epic 1 persists lifecycle state per-event, so the loss window is already ≤1s (in practice a single committed transaction).

9. **CLI surface + output discipline (AD-12).** `kt agent list [--json]` and `kt agent show <name> [--json]` honor the output discipline: the human table / JSON document → stdout; the Epic-3 metering-seed note and any read-back diagnostic → stderr. No new interactive prompt (FR-34). The human `list` remains the default; `--json` is opt-in. The empty-Fleet case still prints its guidance (to stderr for `--json`, so `--json` stdout is always valid JSON — an empty array).

### The binding architecture decisions (spine, FINAL)

- **AD-6 (SQLite is the one state store; per-event transactions; ≤1s durability).** *Rule (verbatim, relevant clause):* "all registry, lifecycle, budget, and Usage Ledger state lives in one SQLite database (rusqlite, bundled SQLite, WAL, `synchronous=NORMAL`) under the engine state dir. Usage Ledger = append-only `usage_events` + rollup aggregates; **one transaction per usage event (durability loss bound ≤1s, superseding the PRD's ≤5s placeholder)**." This is THE load-bearing decision for AC-B and AC-C. In Epic 1 the durable state is registrations + lifecycle state + the `agent_runtime` write-ahead records (restart policy/count) — all already persisted through the `StateStore` in per-event transactions. Reboot durability (AC-B) is a direct consequence: nothing lives in volatile memory. The ≤1s loss bound (AC-C) already holds for lifecycle state (per-event commit); it EXTENDS to the Usage Ledger the moment Epic 3 adds `usage_events` with its per-event transaction. `store/sqlite.rs` already sets `journal_mode=WAL` + `synchronous=NORMAL` and is schema v2. [Source: ARCHITECTURE-SPINE.md#AD-6]
- **AD-5 (write-ahead spawn records; orphan adoption on start).** *Rule (verbatim):* "before exec completes, persist {instance id, PID, process start-time fingerprint}. On engine start, reconcile every record against live processes: fingerprint match → adopt supervision; no match → mark `failed` with last-known cause." Story 1-6 IMPLEMENTED this (`Supervisor::adopt_orphans`, called from `Engine::open`). A machine reboot is the DEGENERATE case of that path: after a reboot NO process survives, so every write-ahead record fails to match → every previously-`running`/`paused` instance reconciles to `failed`. AC-B's "previously-running instances show `stopped`/`failed` per orphan reconciliation" is EXACTLY this path — `stopped` for the cleanly-stopped instances (whose records were cleared on clean stop) and `failed` for the ones that were still running at reboot. This story REUSES the path; it adds no new reconciliation. [Source: ARCHITECTURE-SPINE.md#AD-5; `supervisor.rs::adopt_orphans`, `engine.rs::open`]

The `--json` document is command OUTPUT → stdout and MUST be the only thing on stdout in `--json` mode; the Epic-3 metering-seed note and any read-back diagnostic go to STDERR. This is the same discipline 1-4/1-5/1-6 seeded (results on stdout, notices on stderr). [Source: ARCHITECTURE-SPINE.md#AD-12]

The Fleet `--json` output is a SEED for the story-7-2/7-3 Host event stream: it must be a versioned serde struct (carry `schema_version`) so `kt --json` and the future Host stream do not drift into two dialects. Reuse the `AgentInstance`/`LifecycleState`/`RestartPolicy` serde types (already derived) and the event schema-version constant. [Source: ARCHITECTURE-SPINE.md#AD-14; `event.rs`]

The Fleet view type is a domain/engine type re-exported at the crate root. `ktesio-conformance` (the `fake_agent` for the durability test) stays a DEV-dependency of `kt`/`ktesio-engine` (boundary-gate-excluded).

### THE Fleet-listing + reboot design (the story's core value — define exactly)

**Two mechanisms are the deliverable; both are thin extensions.**

| Concern | Mechanism | Surface |
| --- | --- | --- |
| **Fleet listing (human + `--json`), ≤2s fresh** | `kt agent list [--json]` opens the engine and reads live state — `Engine::fleet()` composes the existing `Registry::list()` + per-instance `instance_status()` (state + restart count/policy) into a `FleetEntry` per instance. Human → a `ui::print_table` with the metering-seed columns; `--json` → one `serde_json` document to stdout (AD-12/AD-14). Freshness is structural: every listing reads the store, so any committed transition is reflected immediately (single DB read ≪ 2s). | Human table OR JSON array on stdout; Epic-3 metering note on stderr. |
| **Reboot durability + reconciliation** | Nothing lives in memory: registrations, lifecycle state, restart policy/count all persist in the one SQLite DB (AD-6). On the next `Engine::open`, the 1-6 `Supervisor::adopt_orphans` reconciles every write-ahead record; after a reboot NO process matches, so every previously-`running`/`paused` instance → `failed` (honest, AI-8), while cleanly-stopped instances stay `stopped` (records cleared on clean stop). | The reopened Fleet lists every instance intact, previously-running ones `failed`, cleanly-stopped ones `stopped`; no orphan survives. |

**Why `--json` must be a versioned serde struct (AD-14).** The Host event stream (story 7-2/7-3) and `kt --json` are contractually ONE schema. Emitting an ad-hoc JSON blob here would fork the dialect. So the Fleet view type derives `Serialize`, carries a `schema_version`, and reuses the already-`Serialize` `AgentInstance`/`LifecycleState`/`RestartPolicy` — the same structs the event log serializes. `budget`/`usage` are `Option`-typed `null` seeds so adding the real types in Epic 3 is an additive, forward-compatible schema change (consistent with 1-5's/1-6's additive-schema note).
