# Story 4.2: Attach to live output and read retained logs

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want to stream a running agent's output and read what it said while I was detached,
so that observation is uniform and nothing is lost. (FR-25, NFR-5)

## Acceptance Criteria

Derived from `epics.md` Story 4.2's single compound AC (Epic 4, lines 463-474) plus AD-12's capture/rotation/attribution rule (`ARCHITECTURE-SPINE.md:107-110`) and NFR-5 (`prd.md:351`), broken into testable pieces (mirroring how 4.1 expanded its two epics.md bullets into six ACs). Epic 4's thesis: *"One interaction surface: send, stream, script."* 4.1 built **send**; this story builds **stream** (both halves: live attach and retained read); `--json`/exit codes is 4.3, explicitly out of scope here (it reads FROM what this story builds).

> **CRITICAL SCOPING — read before AC-A.** This is a **capture-path rework** wearing a **"just add a read command"** disguise. Investigate before writing code: today's `agent.log` (`registry.agent_output_log_path`, `crates/ktesio-engine/src/domain/registry.rs:985-987`) is populated by connecting the spawned child's stdout **and** stderr directly to the **same** OS file handle (`Stdio::from(file)` for both, via `file.try_clone()` — `crates/ktesio-engine/src/backends/unix/mod.rs:134-155`, mirrored exactly in `backends/windows/mod.rs:215-236`). This is raw, kernel-mediated passthrough: **no engine code reads a byte of it while the process runs**, so there is **zero visibility into which stream produced which byte**, no per-line timestamp, and no rotation (confirmed — nothing in-tree rotates anything; `supervisor.rs:984,1696,2299` all say "rotation... is Epic 4"/"deferred to Epic 4"). Attribution and rotation **cannot be retrofitted onto this design** — the AC's `agent-out`/`agent-err`/`engine` labels and the 10MB×3 bound require the engine to become an active party in the capture path (piped stdout/stderr, read in the engine, re-written attributed+rotated), not a passive fd-forwarder. This is the genuinely new plumbing, analogous in scale to 4.1's stdin-piping build — see "What already exists vs. what's genuinely new" in Dev Notes.
>
> **CRITICAL SCOPING #2 — this story does NOT hit 4.1's single-lifetime wall, and does NOT need a daemon (read before AC-B).** 4.1's `send` needed a **live stdin pipe FD**, which only the originating engine session holds — an adopted (crash-surviving) instance can never recover it, forcing the new `InteractionUnavailable` error (4.1 AC-D). Reading/following output needs only the **log file's path**, which `registry.agent_output_log_path`-style helpers compute **deterministically from the instance name alone**, recoverable in **any** engine session regardless of adoption status. This asymmetry is not a new insight this story invents — it is the **already-ratified conclusion of the AI-20 research spike** that governed 4.1: *"a detached agent has no live stdin for `kt agent send`, and its output only lands in the rotated log files (readable, but not a live stream from a fresh CLI)... attach-to-output **degrades to tailing a log**"* (`research/technical-durable-agent-supervision-daemon-vs-detach-research-2026-07-06.md:121`). "Live attach" in v1 **is** tailing a log — a polling re-read of a growing file — never a push-streamed pipe relay, and it needs **no** subscription/event-bus mechanism (Story 7-2 "Subscribe to engine events with stable schemas," `epics.md:629-640`, is entirely `backlog` — not even a stub exists in `engine.rs` today; confirmed via `grep -n "subscribe\|broadcast\|Stream\b" engine.rs` returning nothing). **This is not a blocking product-decision collision** (unlike, hypothetically, if attach required a persistent daemon AI-20 deferred to Epic 7) — it is a buildable engineering task with direct precedent to mirror (below).
>
> **CRITICAL SCOPING #3 — do not corrupt Epic 3's metering ingestion (read before Task 1).** `Supervisor::drain_usage_for` (`supervisor.rs:1701-1738`, story 3-1/AD-7) **already** reads `agent.log` today, byte-for-byte, scanning raw lines for a `KTESIO_USAGE {json}` sentinel prefix — this is Epic 3's adversarially-reviewed, "billing money" ingestion path. If this story changes `agent.log`'s **format** (e.g., wraps every line in a JSON envelope for attribution), `drain_usage_for`'s sentinel parser breaks silently — a cross-epic regression this story must not cause. The recommended default (Dev Notes) is to leave `agent.log` **byte-identical to today** and introduce a **new**, separate rotated+attributed file that reader threads write to **in addition to** (not instead of) the legacy file — zero changes to Epic 3's code.

1. **AC-A (verbatim-derived — read retained logs, ordered + timestamped + attributed).** **Given** an instance whose output was captured to the Agent Home (while running, whether or not anyone was attached) **When** I read retained logs (`kt agent logs <name>`, recommended verb — see Assumption 1) **Then** every currently-retained line returns in emission order, each carrying an RFC 3339 UTC timestamp (`crate::time::now_rfc3339`, `crates/ktesio-engine/src/time.rs:20` — reused, not reinvented) and exactly one attribution label (`agent-out` | `agent-err` | `engine`, matching AD-12's literal tokens). Works identically for a `running`, `paused`, `stopped`, or `failed` instance (a snapshot as of read time when `running`); a `registered`-but-never-started instance returns an honest empty result, not an error (mirrors `read_events_from`'s existing "missing file → empty vec" precedent, `supervisor.rs:2313-2320`).

2. **AC-B (verbatim — live attach streams both agent streams with the same attribution).** **Given** a running instance actively emitting output on both stdout and stderr **When** I attach (`kt agent logs <name> --follow`) **Then** newly emitted lines from **both** streams appear incrementally as the agent emits them (not merely a final snapshot when the command eventually exits) — proven by an assertion that new lines are OBSERVED mid-stream, not just present in a post-hoc dump — carrying the same per-line timestamp+attribution as AC-A, in the order the engine observed them.

3. **AC-C (derived — follow terminates honestly, no hang).** **Given** a `--follow` session against an instance that transitions out of `running` (stop, crash, pause) **When** the transition is observed (via a periodic `instance_status` poll, not a log-content guess) **Then** follow performs one final drain (no line emitted before the transition is lost) and exits cleanly with a status-appropriate note — a `paused` instance is not "gone," so follow ends with an honest "paused, no further output until resumed" note (not an error) rather than hanging forever waiting for output that will not arrive while suspended.

4. **AC-D (derived — rotation bound, fixed, honestly partial).** The new attributed capture is bounded: each generation caps at 10MB, at most 3 generations retained (current + 2 rotated predecessors) — a **new, fixed, non-configurable** engine constant (no unified-config key this story), mirroring `STDIN_WRITE_TIMEOUT`'s precedent (4.1 fix pass, `ports/process_backend.rs`) of a hardcoded resilience bound rather than a user setting. `kt agent logs` never errors due to rotation; a read that spans a rotation boundary honestly returns whatever the current 1-3 retained generations hold — never a claim of the agent's entire lifetime history. (The PRD's FR-25 consequence line says "bounded retention, **configurable**," `prd.md:253`, while AD-12 and epics.md's testable AC both state a fixed "10MB × 3" with no config knob — Assumption 2 resolves this tension in AD-12/epics.md's favor, matching 4.1's precedent of following the testable AC over looser PRD prose.)

5. **AC-E (derived — capability-independent, unlike `send`).** **Given** an adapter declaring `interaction: unsupported` **When** it runs and produces output **Then** that output is still captured, attributed, and readable via `kt agent logs` — log capture (AD-12) is unconditional and capability-independent (mirrors the existing unconditional `log_file: Some(agent_log_path)` at every spawn, `supervisor.rs:528`, unaffected by 4.1's `pipe_stdin` capability gate on the **stdin** direction only). Only `send` (writing **to** the process) is gated on `Capability::Interaction`; reading **from** its captured output never is.

6. **AC-F (derived — no adapter/manifest/contract surface change).** This story adds no new manifest section, no new `Capability` variant, and no `CONTRACT_VERSION` bump (stays `"0.4.0"`, set by 4.1) — capture, attribution, and rotation are entirely engine-owned, mirroring 4.1's "no new `AgentAdapter` trait method" finding verbatim: `SpawnSpec.log_file` is engine-computed, not adapter-declared, and that remains true for its attributed/rotated replacement.

7. **AC-G (derived — order is append order, never a timestamp re-sort).** `crate::time::now_rfc3339` has **whole-second** resolution (`time.rs:32-39` — no sub-second field). Multiple lines emitted within the same wall-clock second carry **identical** timestamps. Read/follow code must preserve on-disk **append order** as the sole ordering authority and must never sort or interleave-by-timestamp — a naive re-sort would silently reorder same-second lines. (A concrete, testable trap: emit several same-second lines across both streams and assert the read order matches emission order, not a stable/unstable timestamp sort.)

8. **AC-H (derived — attach works from a fresh engine session; no daemon, no subscription bus).** **Given** an instance that is genuinely `running` but was adopted from a prior, non-cleanly-exited engine session (AD-5, per 4.1 AC-D's scenario) **When** a **new**, separate `kt agent logs <name> --follow` invocation runs against it **Then** it streams correctly using only the deterministically-computed log path and periodic `instance_status` DB reads — no live handle, subscription, or daemon required. This is the direct, testable expression of CRITICAL SCOPING #2 above, and the one AC in this story that plays the same "genuinely novel edge case" role AC-D played in 4.1 (there, the answer was a hard failure; here, by contrast, it is expected to **work**, which is precisely the asymmetry worth proving).

### Why "live attach" needs no daemon and no subscription bus (the load-bearing distinction from 4.1)

4.1's `send` was fundamentally blocked by the single-lifetime boundary for one precise reason: it needed to **write** to a resource (the child's stdin pipe) that only exists as a live OS file descriptor inside the ONE engine process that spawned the child — a pipe FD cannot be reconstructed from a bare PID on any OS, by design (4.1's AC-D). Reading output has no equivalent obstacle: `registry.attributed_output_log_path(name)` (Task 5) is a **pure function of the instance name**, computable identically in every engine session, adopted or not. The only thing that must remain true for `--follow` to observe NEW content is that **some** process is still appending to the file — and that is a property of the AGENT process being alive and its capture threads running (in WHICHEVER engine session originally spawned it and has not yet exited), not a property of the ATTACHING session. This is precisely the AI-20 research spike's own conclusion, reached before this story existed: *"a detached agent has no live stdin for `kt agent send`, and its output only lands in the rotated log files (readable, but not a live stream from a fresh CLI)... attach-to-output degrades to tailing a log"* (`research/...-2026-07-06.md:121`). "Degrades" describes the gap between this and a true push-streamed daemon relay (Epic 7's eventual answer) — it does not describe a functional shortfall against THIS story's AC, which only asks for streaming with reasonable latency, fully satisfied by a few-hundred-millisecond poll of a local file.

**Why no `Stream`-typed public API either:** `Engine`/`Blocking` currently expose exactly one shape for every method — async request/response, paired with a blocking facade call (AD-13). Introducing a genuine `impl Stream<Item = LogLine>` (or a blocking `Iterator`) would be the FIRST departure from that shape, ahead of Story 7-2's formal subscription bus, and would freeze a novel API surface this early increases the risk of a second, incompatible streaming shape when 7-2 lands. `read_agent_log_since(name, cursor) -> (Vec<LogLine>, next_cursor)` keeps the existing shape, is trivially driven in a loop by `kt`'s CLI (Task 6) or by any Host embedding the engine (satisfying FR-31/FR-32's "every capability through the library alone" spirit without inventing a new API family), and does not foreclose 7-2 later superseding/extending it with real push delivery.

### The metering-collision this story must not create (CRITICAL SCOPING #3, restated with the recommended fix)

`Supervisor::drain_usage_for` (story 3-1, AD-7 — the ADVERSARIALLY-REVIEWED "billing money" ingestion path, hardened across multiple rounds for saturate-safety and no-double-count) reads `agent.log` **today**, splitting on `\n` and matching a `KTESIO_USAGE {json}` sentinel **at the start of each raw line**. Any change that wraps captured lines in a JSON envelope (the natural-seeming way to add per-line attribution) would silently break this parser — the sentinel string would still be present, but no longer at the start of a physical line, nested instead inside an escaped `"text":"..."` field. **Recommended default (Assumption 3):** keep writing `agent.log` in its exact current raw format (Task 2/3 — the reader threads append the SAME unmodified line to it that the OS kernel used to write directly), and introduce a **new**, separate file (`logs/output.log`, rotated) that additionally carries the attributed/timestamped JSON-Lines view. This costs a second, cheap local-disk write per line and a small amount of duplicated on-disk content, in exchange for **zero** changes to Epic 3's already-hardened code and test suite. The alternative — teaching `drain_usage_for` to parse the new envelope's `text` field instead — was considered and rejected as the default: it is a strictly riskier change (touching a billing-critical path this story has no other reason to touch) for a marginal disk-space saving; Task 8's `legacy_agent_log_is_byte_identical_to_pre_story_content` test is the automated proof this boundary holds.

### Order is append order, never a timestamp sort (AC-G)

`crate::time::now_rfc3339` resolves to the **second** (`time.rs:32-39` — no fractional-second field; this is a deliberate, documented minimalism: *"No date/time crate is on the approved dependency list... the need is tiny"*). A busy agent can easily emit several lines within one wall-clock second, all carrying identical `at` values. Every piece of code that renders or tests ordering (the writer thread, `read_agent_log`, `kt agent logs`'s renderer) must treat on-disk **append order** as the sole source of truth and must never re-sort by `at` — a compare-and-sort implementation would be a silent, hard-to-notice correctness bug (same-second lines could render in a different order each run, non-deterministically, since a stable sort on equal keys preserves input order but an UNSTABLE one — e.g. a naive `sort_by_key` misuse — would not). Flagged explicitly because it is exactly the kind of subtle bug that would pass casual review (timestamps LOOK monotonic) and only surface as an intermittent test flake.

### Rotation ownership and the single-writer-thread design (why a channel, not a shared mutex)

Three distinct sources can produce a `LogLine` for the same instance: the stdout reader thread, the stderr reader thread, and the supervisor's own transition-time `engine`-attributed writes (Task 4) — potentially from three different OS threads. Rotation (rename current→`.1`→`.2`) and the append that follows it must be atomic with respect to each other, or two threads could both decide to rotate at once, or one could append to a file the other just renamed away. Rather than a shared `Mutex` guarding the rotate-and-append sequence (workable, but introduces lock contention/ordering to reason about across three call sites), Task 2 recommends the classic Rust single-writer-via-channel pattern: all three sources hold a clone of the SAME `mpsc::Sender<LogLine>`; exactly one background thread owns the file handle(s) and performs every rotation-check-then-append serially, draining the channel. This eliminates the lock entirely (no two threads ever touch the file), is a well-understood idiom, and mirrors (in spirit, not literally) the existing single-choke-point discipline this codebase already applies to money (`record_usage_event`, `BudgetEvaluator::evaluate` — each proven-single-call-site by a source-level grep audit in `tests/metering.rs`/`tests/budget.rs`). A future reviewer might expect a `Mutex<File>` instead; this section exists so that expectation is addressed head-on rather than silently deviated from.

### Why no manifest/capability/contract change (AC-F)

Mirrors 4.1's own "why no new `AgentAdapter` trait method" reasoning verbatim: in v1, every adapter that can actually run is spawned through the identical `ProcessBackend`/`SpawnSpec` mechanism, so "the adapter's output" IS, for every adapter that exists, "the spawned child's stdout/stderr" — there is no second, non-process-based output source to declare in a manifest. `Capability::Interaction`'s doc comment already frames the capability as "Send input to / read output from the agent" (`capability.rs:68-69`), which could be misread as implying reading output should ALSO be gated by `Capability::Interaction`'s support level — investigated and rejected (AC-E): AD-12's capture is unconditional TODAY (the existing `log_file: Some(...)` at every spawn has never been conditional on any capability), and gating READS on a capability that governs a completely different concern (bidirectional interactivity) would make an `interaction: unsupported` adapter's crash diagnostics unreadable, which is precisely backwards from NFR-5's observability intent. No `CONTRACT_VERSION` bump follows from any of this — the adapter-facing contract is untouched.

### Assumptions & open items logged (headless run)

1. **CLI shape `kt agent logs <name> [--follow|-f]`** (one verb + a flag, not two separate verbs like `attach`/`logs`) is a RECOMMENDATION, not mandated by epics.md (which uses the words "attach" and "read retained logs" descriptively, not as command names). ### Fix Pass — Crash-Safety Redesign (review of #80, 2026-07-18/19)

Two independent adversarial reviews of the original implementation above (commit `61bbdfd`) found problems sharing ONE root cause, requiring a substantial rework of this story's write-side capture path (the read-side API — `LogLine`/`LogStream`/`read_agent_log`/`read_agent_log_since`'s core contract — was kept stable, per the fix-pass brief's constraint).

**Root cause (Finding A, CRITICAL, adversarially reproduced empirically):** the original implementation connected the spawned child's stdout/stderr to `Stdio::piped()` unconditionally, with the ENGINE holding the pipes' read ends (consumed by reader threads). This coupled the agent's write-SUCCESS to the engine's LIVENESS for the first time: an engine crash (SIGKILL/panic/OOM — anything skipping `Drop`) closes the engine's fd table, vanishing the pipe's sole read-end reference, so the agent's NEXT `write()` gets `EPIPE` — killing a default-SIGPIPE-disposition process (the common case for non-Rust/non-Python agents) within milliseconds, and permanently blinding capture for a SIGPIPE-immune one. A direct regression against NFR-1 (an engine crash must never be able to kill, or permanently blind observability into, a process it supervises).

**Investigation findings (before designing the fix):**
1. **`agent.log`'s actual write path as of `61bbdfd`:** confirmed by reading `spawn_reader_thread` directly — `agent.log` (the LEGACY file) was ALSO fed by the SAME piped-reader-thread mechanism as the new attributed capture, NOT a direct kernel passthrough. The regression applied to BOTH files, not just the new one.
2. **The `KTESIO_USAGE` sentinel:** confirmed STDOUT-ONLY by convention (`docs/manifest.md:104`, `docs/architecture.md:52`, `ports::usage_source`'s doc comments, `fake_agent.rs`'s emitter) — nothing ever emits it on stderr. This meant `agent.log` did not need to preserve true cross-stream byte-level interleaving to keep `drain_usage_for` correct; it only needed the STDOUT portion to be synchronous/zero-hop.
3. **Other `agent.log` readers:** grepped broadly — only `drain_usage_for` (billing) and a handful of tests (checking specific line presence, never exact whole-file ordering) depend on its content.

**The fix — direct-file capture restored, attribution/rotation become a file-tailer:**
- `SpawnSpec` gained a THIRD capture-path field, `stderr_log_file: Option<PathBuf>`, paired 1:1:1 with the existing `log_file`/`attributed_log_path` (all three `Some` together in production, gated by a `debug_assert!` in both backends — L6).
- Both backends' `spawn()` now redirect the child's stdout DIRECTLY to `log_file` (`agent.log`) and stderr DIRECTLY to the new `stderr_log_file` (`agent-stderr.log`) via `Stdio::from(file)` — the SAME crash-immune, kernel-mediated mechanism this codebase used before story 4-2 ever piped anything, just applied per-stream instead of combined. `agent.log` is now STDOUT-ONLY (a deliberate, documented change from combining both streams — CRITICAL SCOPING #3's byte-identity guarantee is about FORMAT/content-presence, not literal interleave order, and no reader needs stderr there); stderr is captured separately.
- `drain_usage_for` (Epic 3, billing) now reads `agent.log` with ZERO hop latency — the SAME guarantee as before story 4-2 ever existed. This closes H2 (below) at the root, not just narrows it.
- Attribution + rotation (`output.log[.N]`) now come from a per-instance background TAILER thread (`ports::process_backend::spawn_tailer_thread`) that incrementally re-reads the two crash-immune raw files (cursor-based, mirroring `read_agent_log_since`'s existing idea) and re-attributes+rotates their content — a DERIVED, best-effort VIEW that can lag or stop entirely on an engine crash WITHOUT harming the agent's own writes at all.
- `ProcessBackend::log_sender` (returning a bare `mpsc::Sender<LogLine>`) was renamed `log_capture` (returning a new `LogCapture` handle) throughout the engine, backends, and supervisor.

**H1 (primary review, HIGH, confirmed via a caught nextest flake) — a SECOND async hop, found while re-verifying the fix:** the original design's Task-4 engine-attributed lines (`transition_with_log_sender`) ALSO went through a channel-fed background writer thread — unrelated to the piped-stdout regression, but its OWN "fire and forget, never joined" nature meant a caller that starts an instance and exits immediately (`kt agent start`'s own documented single-lifetime model; also this story's/4.1's crash-adoption test harnesses) could race that writer thread's own schedule, losing the just-enqueued "engine: ... -> running" line if the process ended before the writer thread was ever scheduled — this is PRECISELY what `logs_reads_retained_output_after_the_instance_stops` flaked on. Closing H2 at the root (direct-file `agent.log`) did NOT fix H1, since engine lines never went through `agent.log` at all. Fix: `output.log`'s writer-thread-plus-channel was REMOVED ENTIRELY. `LogCapture::send_engine_line` and the tailer's own catch-up now both call `append_attributed_lines` DIRECTLY and SYNCHRONOUSLY, serialized by ONE shared `Mutex` (guarding both the tail cursors and the rotate-then-append sequence — the same non-negotiable "two threads must never race a rotation" property the original single-writer-thread design existed to guarantee, via a lock instead of a channel; the original story's own Dev Notes anticipated exactly this alternative: *"a future reviewer might expect a `Mutex<File>` instead"*). By the time `send_engine_line` returns, the line is durably on disk — no background thread left to race a caller that exits immediately after.
- **A second, independent performance finding surfaced by this fix pass's OWN empirical crash-kill experiment** (spawning `yes`, a real OS process with zero write-backpressure since it targets a direct file, not a pipe): a single `send_engine_line`/tailer catch-up pass over a large backlog of TINY lines took ~15.7s in an unoptimized debug build (and ~1s even in `--release`) — far too slow for a call that may run while the engine-wide supervisor lock is held, and (during investigation) briefly caused tens of GB of local disk usage before the bound was fixed. Root-caused to TWO compounding costs: (a) one `write()` syscall per line (fixed by batching a whole pass into ONE in-memory buffer + ONE `write_all` call), and (b) unbounded per-line `LogLine`/JSON-serialization work for a backlog of arbitrarily many tiny lines (fixed by a NEW `MAX_TAIL_LINES_PER_PASS` bound (2000), alongside the existing `MAX_TAIL_BYTES_PER_PASS` (4MB) — bytes alone does not bound tiny-line work). A permanent regression test (`tail_new_lines_stays_fast_against_a_huge_backlog_of_tiny_lines`) asserts one pass over a ~2M-tiny-line backlog completes in under 2s.

**H2 (primary review, HIGH, plausible extension) — resolved as a direct consequence of the root fix:** `drain_usage_for`'s pre-kill synchronous read of `agent.log` no longer has ANY reader-thread hop to race, since `agent.log` reverted to a direct, synchronous, kernel-mediated write target. Re-verified: `legacy_agent_log_is_byte_identical_to_pre_story_content` (and the whole suite) pass consistently; `drain_usage_for`/`plan_drain` were not modified.

### Fix Pass — Bound `stop()`'s Post-SIGKILL Wait (review of #80 follow-up, CRITICAL, 2026-07-19)

Independent verification of the crash-safety fix pass above found a NEW, distinct CRITICAL finding sharing its root cause: removing agent output capture's pipe (to fix the SIGPIPE-kill bug) also removed the pipe's INCIDENTAL backpressure. A fast writer with no reader now writes at raw disk I/O speed (empirically ~1.1-2 GB/s), can exhaust available disk space, and the writing process can then enter an OS-level UNINTERRUPTIBLE I/O wait (Linux `D` state; macOS `U`/`Us` per `ps aux`) — a state immune to EVERY signal, including SIGKILL, until the underlying I/O resolves at the kernel/storage layer. `ProcessBackend::stop`'s escalation phase, on both backends, called a BARE, UNBOUNDED `Child::wait()` (Unix, spawned) after SIGKILL — assuming SIGKILL is always near-instant — with NO deadline at all; `stop()` runs while the caller holds the engine-wide `EngineInner::supervisor` lock, so one stuck instance could freeze every other instance's `start`/`stop`/`pause`/`resume`/`send` and the crash-detection reaper for an OS-determined, UNBOUNDED duration (worse than 4.1's already-bounded `STDIN_WRITE_TIMEOUT` residual). The (separate) Windows adopted-handle branch and Unix adopted-handle branch already had an informal 5s poll bound, but silently returned `Ok` even when the process was still alive afterward — a latent, pre-existing dishonesty this fix pass also closes.

**The fix — mirrors 4.1's `STDIN_WRITE_TIMEOUT`/`InteractionTimedOut` precedent exactly, per the brief's explicit instruction not to redesign the locking model:**
- New `KILL_CONFIRM_TIMEOUT: Duration = Duration::from_secs(5)` (`ports/process_backend.rs`, beside `STDIN_WRITE_TIMEOUT`) — a hardcoded, deliberately non-configurable resilience bound (same rationale as 4.1's: a normal process is reaped within low-single-digit milliseconds of SIGKILL, so 5s is generous headroom, not a user-facing setting).
- New `BackendError::StopUnconfirmed { timeout_secs }` and `EngineError::StopUnconfirmed { name, timeout_secs }` — mirrors `StdinTimedOut`/`InteractionTimedOut`'s shape exactly. Both backends' `stop()` escalation phase was rewritten: the OLD `match handle.child.as_mut() { Some(child) => child.wait()... None => while pid_is_alive... }` branch (Unix) / unbounded `child.wait()` (Windows, after `TerminateJobObject`/`TerminateProcess`) was replaced by ONE unified, NON-BLOCKING polling loop via the existing `reap_if_exited()` (already non-blocking on BOTH the spawned — `try_wait`/`WaitForSingleObject(_,0)` — and adopted branches on both OSes), bounded to `KILL_CONFIRM_TIMEOUT`, extracted into a small, timeout-PARAMETERIZED `confirm_death(handle, timeout)` helper in each backend — mirroring `write_stdin_bounded`'s own "timeout as a parameter, tested directly with a short value" testability precedent, rather than hardcoding the bound inline (which would have forced any deterministic test to wait out the real 5s).
- **LifecycleState decision:** no new variant. A `stopping`-and-unconfirmed instance stays `Stopping` — the EXISTING state already honestly means "stop requested, graceful shutdown in progress"; inventing a new variant was explicitly discouraged by the brief and unnecessary.
- **No compounding + self-healing:** a NEW `Supervised::stop_unconfirmed: bool` field (default `false`; set to `true` only in `stop_inner`'s `BackendError::StopUnconfirmed` arm) lets BOTH a retry `stop()` call and the crash reaper (`poll_once`) recognize this EXACT scenario — deliberately narrower than "any `stopping` row with a held handle" (which would also fire for `poll_once_ignores_an_exit_during_a_requested_stop_not_a_crash`'s pre-existing, externally-forced-`stopping` scenario, which must NOT change behavior — see below). `stop_inner` gained a branch, checked BEFORE the ordinary `next_state` transition gate: if the instance is `stopping` and its handle is `stop_unconfirmed`, perform a single CHEAP, NON-BLOCKING `ProcessBackend::poll` (never `ProcessBackend::stop`) — if the process is now confirmed dead, finalize `stopping -> stopped` right there (self-healing); if still alive, fail fast with the SAME honest error, no new signal, no new wait (no compounding). `poll_once` gained the identical, narrowly-gated reconciliation for the case where the reaper's OWN routine poll observes the exit first (whichever of the two happens first resolves the row — it is never permanently stuck).
- Wired into `kt`'s CLI diagnostics: new `AgentStopUnconfirmed` (`kt/src/error.rs`) + a `map_engine_error` arm (`kt/src/cli/agent.rs`) naming the instance, the bound, the likely cause (an OS-level I/O wait / disk pressure), the instance's actual (non-terminal) state, and pointing at retrying `stop` — mirroring `InteractionTimedOut`'s existing diagnostic pattern.
- `docs/architecture.md:128`'s stale "captured to a **separate file**" (singular) — dating from before the crash-safety fix pass split capture into `agent.log`/`agent-stderr.log`/`output.log` — corrected to describe the current three-file reality (small, independent doc fix requested alongside this finding).

**Self-verification bug, caught by the EXISTING test suite (not a new test) — recorded per this story's established convention of documenting what the full regression run catches:** the first draft of the Unix rewrite accidentally DROPPED the `signal_group(handle.pgid, Signal::SIGKILL)` call itself while restructuring the escalation block (a copy/rewrite slip, not a logic error in the new polling loop). This was caught IMMEDIATELY by the pre-existing `stop_escalates_to_forced_kill_when_graceful_window_elapses` test, which failed with the new `StopUnconfirmed` error instead of the expected `forced: true` — a `sh -c 'trap "" TERM; sleep 60'` process that should die in milliseconds from SIGKILL instead ran for the full 5s bound. Root-caused via a temporary debug print showing `reap_if_exited` reporting `Alive` on every poll, then confirmed via a manual `os.fork`/`setsid`/`killpg` Python reproduction that the SAME construct dies in ~0ms when SIGKILL is actually sent — proving the bug was the missing call, not the new bound-enforcement logic. Fixed by restoring the SIGKILL call before the new `confirm_death` loop. Flagged here because it is exactly the kind of narrow, easy-to-miss regression a full-suite run (not a scoped diff read) catches — the same lesson this story's ORIGINAL Debug Log already drew from a different mistake.

**Required empirical proof (all performed; see the constraints on never touching the real disk again):**
1. **Ramdisk-based reproduction attempt (safety-first, per the mandatory brief):** a dedicated, disposable 100MB `hdiutil`/`diskutil`-created HFS+ ramdisk (`/Volumes/KTRAMDISK`), fully detached and confirmed gone after every experiment; the real host disk was never at risk (verified free space before/after every run: 85Gi → 82Gi, the difference fully accounted for by an mingw-w64 install for Windows cross-compile-checking and normal Rust build-artifact growth, NOT by any agent-log data, which stayed 100% inside the memory-backed ramdisk). **Empirical finding: a memory-backed ramdisk does NOT reproduce genuine uninterruptible I/O wait.** A raw `yes > ramdisk-file` filled a 98MB-usable ramdisk in ~0.3s and exited immediately with a clean `ENOSPC` ("No space left on device") — no hang.
