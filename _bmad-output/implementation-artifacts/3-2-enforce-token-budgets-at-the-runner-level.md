# Story 3.2: Enforce token budgets at the runner level

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want per-run and cumulative Token Budgets whose breach triggers the configured Breach Action,
so that token consumption is bounded even when I'm not watching. (FR-18, FR-21 pipeline)

## Acceptance Criteria

Verbatim from `epics.md` Story 3.2 (the SECOND story of Epic 3 — Cost Governance; it builds DIRECTLY on 3-1's ledger). The three headline ACs are: a Token Budget set on a running instance, when metered consumption **reaches** it, causes the `BudgetEvaluator` (invoked **inside the ledger commit path**, AD-7) to emit a `BreachDecision` and the supervisor to execute the Breach Action — default `pause` (ratified) — within **one metering interval**, and a **breach event is always recorded regardless of action** (AC-A); budgets are **inspectable and changeable while `running`, applying immediately** (AC-B); and the Breach Action is **per-instance configurable among `pause`/`stop`/`warn`** (AC-C). The derived criteria below make the `TokenBudget` domain shape (per-run + cumulative scopes), the `BudgetEvaluator` inserted at 3-1's evaluator-ready choke point, the `BreachDecision`/`BreachAction`, the breach-event wire struct, the budget + Breach-Action config keys read through the Epic-2 config system, the live-changeability guarantee, the lifecycle enforcement (reusing Epic 1's `stop`/`pause`), and the Fleet-detail `budget` surfacing (making the `None` seed real for tokens) explicit and testable.

> **CRITICAL SCOPING (read before AC-A):** This is the **SECOND** metering story. 3-1 delivered **capture → ledger** (the `self-reported` `UsageEvent` → the append-only `usage_events` write with replay dedup → the Run span → `usage` in Fleet detail) and left the ledger commit path as **ONE evaluator-ready choke point** (`Supervisor::ingest_usage`, `crates/ktesio-engine/src/domain/supervisor.rs:1292`, with the exact 3-2 hook documented at ~line 1309). **3-2 delivers ENFORCEMENT and NOTHING WIDER: TOKEN budgets only.** It introduces: (1) a `TokenBudget` domain type carrying per-run + cumulative token ceilings; (2) a `BudgetEvaluator` invoked INSIDE the 3-1 commit path (right after the ledger write, in the same path — the AD-7 "inside the same commit path" rule) that turns the just-committed totals into a `BreachDecision`; (3) a `BreachAction` (`pause`/`stop`/`warn`) the supervisor executes by driving the agent through Epic 1's EXISTING `stop`/`pause` lifecycle (no new state, no new transition-table edge — AD-15); (4) an **always-recorded** breach event (AD-14 wire struct) emitted regardless of action, carrying an honest breach cause (AD-12/AD-14); (5) the budget value + the Breach-Action value read through the **Epic-2 config system** (`EffectiveConfig`), inspectable + changeable while `running` and applied immediately; and (6) `budget` surfaced in Fleet detail — making 3-1's honest `None` seed real for TOKENS. It is **EXPLICITLY OUT OF SCOPE** to build: **DOLLAR caps + `Rate` ($/1M) + dollar derivation + `EstimateLabel` + the currency-rendering module (3-3 — 3-2 enforces on TOKEN COUNTS ONLY and renders NO dollar figure, AD-8)**, `engine-observed` loopback metering (3-4), and the full per-scope/headroom/Fleet-wide usage-&-cost READ surface (3-5 — 3-2 surfaces only the budget + remaining tokens in Fleet detail). 3-2 is token-count enforcement at the runner.

1. **AC-A (verbatim — budget breach drives the Breach Action inside the commit path; a breach event is always recorded).** **Given** a Token Budget set on a running instance **when** metered consumption reaches the budget **then** the `BudgetEvaluator` (inside the ledger commit path, AD-7) emits a `BreachDecision` and the supervisor executes the Breach Action — default `pause` (ratified) — within one metering interval, and a breach event is always recorded regardless of action. The evaluator runs INSIDE the 3-1 commit choke point (`Supervisor::ingest_usage`), immediately after `record_usage_event` returns `Inserted`, in the SAME code path — so the enforcement race can never open between "usage recorded" and "budget checked" (AD-7 "inside the same commit path"). The evaluator reads the just-committed per-run + cumulative totals (the 3-1 `usage_totals`/`run_totals` reads) and the resolved `TokenBudget`, and returns a `BreachDecision` (`WithinBudget` | `Breached { scope, action }`). On `Breached`, the supervisor executes the Breach Action by driving Epic 1's lifecycle: `pause` → `Supervisor::pause` (`supervisor.rs:612`), `stop` → `Supervisor::stop` (`supervisor.rs:512`), `warn` → no lifecycle change. The breach event is recorded **regardless** of the action (even for `warn`, even if the pause/stop itself is best-effort or errors — record the Decision that the breach event is committed BEFORE/independently of the lifecycle side-effect). "Within one metering interval" is the FR-21 latency bound (ledger-breach → lifecycle-action ≤ metering interval + 1s): because the evaluator is in the same synchronous commit path as the ledger write, the interval is effectively the ingestion cadence — record this and make the test assert the committed lifecycle STATE (not a wall clock). Decide + record the **threshold semantics** — RECOMMENDED **reaches = `≥`** ("consumption reaching the budget" is `cumulative_tokens >= budget`, not strictly greater), so a budget of exactly N tokens breaches when the ledger total hits N.

2. **AC-B (verbatim — budgets are inspectable and changeable while `running`, applying immediately).** **And** budgets are inspectable and changeable while `running`, applying immediately. The budget is a per-instance CONFIG value read through the Epic-2 config system (`EffectiveConfig`), NOT a value frozen at start. Record the Decision: the evaluator reads the CURRENT resolved budget on EACH ingestion (a live read from the resolved config / the registry-persisted instance config), so a budget changed while `running` takes effect on the very next `UsageEvent` — no restart, no re-arm (FR-18 "changes apply immediately"). "Inspectable" = the budget is visible in Fleet detail (AC-F) and readable via the existing config-show surface. Record HOW the budget is set/changed while running (RECOMMENDED: it rides the existing Epic-2 per-instance config write path — `kt agent config set <key> <value>` / the `EffectiveConfig` the supervisor already resolves — so 3-2 adds config KEYS, not a new mutation command). NOTE the honest boundary: changing the budget applies to FUTURE evaluations only; it does NOT retroactively un-breach or re-breach already-committed usage (mirrors 3-3's no-retroactive-repricing discipline).

3. **AC-C (verbatim — the Breach Action is per-instance configurable among `pause`/`stop`/`warn`).** **And** the Breach Action is per-instance configurable among `pause`/`stop`/`warn`. The Breach Action is a per-instance CONFIG value (same Epic-2 config surface as the budget), defaulting to **`pause`** (the ratified shipped default — PRD FR-21, `[FIXED — pause default ratified by Islam 2026-07-02]`). Record the three semantics precisely: **`pause`** drives `running → paused` via `Supervisor::pause` (honoring the adapter's pause Capability Declaration — guaranteed/best-effort/unsupported — exactly as story 1-5 established; a best-effort pause still records the breach + the best-effort qualifier, an unsupported pause records the breach and surfaces that pause could not be honored WITHOUT faking it); **`stop`** drives the instance to a terminal `stopped` via `Supervisor::stop` (graceful → forced escalation, story 1-4); **`warn`** performs NO lifecycle transition — it ONLY records the breach event (the agent keeps running). Record the parse/validation of the config value (an unknown Breach-Action string is rejected at config-write time with a clear diagnostic, reusing the Epic-2 `validate_write` path — never silently defaulted).

### Derived / consequence criteria (make explicit; enforced by tests)

Either/both may be unset (an unset scope never breaches). NO dollar field, NO `Rate`, NO `EstimateLabel`, NO headroom-rendering — those are 3-3/3-5; a `TokenBudget` this story is token-count ceilings only. Record whether it derives `Serialize` for the Fleet-detail `budget` surfacing (AC-F) and/or the breach-event payload (AC10). Decide + record the **enforced scope**: RECOMMENDED enforce BOTH scopes on every evaluation (per-run breach checks `run_totals(name, run_id)`; cumulative breach checks `usage_totals(name)`), so a run-scoped ceiling bounds a single Run's span and the cumulative ceiling bounds the instance's lifetime — the breach reports WHICH scope tripped (`BreachScope::{PerRun, Cumulative}`).

5. **The `BudgetEvaluator` — pure token math, invoked inside the commit path (AC-A — AD-7 the governing seam).** Introduce a `BudgetEvaluator` (record the shape — RECOMMENDED a pure function / small struct `BudgetEvaluator::evaluate(totals_run, totals_cumulative, &TokenBudget) -> BreachDecision`, NO I/O, NO lifecycle, NO ledger — pure comparison so it is trivially unit-testable and cross-OS by construction). Record the `BreachDecision` type (RECOMMENDED an enum `WithinBudget | Breached { scope: BreachScope, action: BreachAction, limit: u64, observed: u64 }` carrying enough to build the breach event + honest cause). The evaluator itself performs NO enforcement — it DECIDES; the supervisor ACTS (keep the decision/effect split so the decision is unit-testable without a running agent). Record the ordering: on a `DuplicateReplay` (3-1 dedup) the evaluator is NOT run (nothing new was committed, so no new breach can occur) — evaluate ONLY on `Inserted`.

6. **The Breach Action executes via Epic 1's existing lifecycle — NO new state, NO new transition edge (AC-A, AC-C — AD-15).** The supervisor executes a `Breached` decision by calling the EXISTING lifecycle ops: `pause` → `Supervisor::pause`, `stop` → `Supervisor::stop`, `warn` → nothing. 3-2 does NOT add a lifecycle state and does NOT modify the AD-15 transition table (`registered starting running paused stopping stopped failed`) — a budget breach is a NEW CAUSE for existing `running → paused` / `running → stopping → stopped` transitions, not a new edge. Record the mechanism: `ingest_usage` currently takes `&self`; to drive `pause`/`stop` (which take `&mut self`) it must become `&mut self` (record this signature change + that the ingestion call site at `supervisor.rs:~1267` already holds `&mut self` via the supervision loop, so the change is local). Record the honest pause/stop semantics carry-over: a `pause` Breach Action on an adapter that declares pause `unsupported` records the breach + surfaces that pause could not be honored (story 1-5's fail-fast-with-declaration-quoted discipline) — it does NOT silently fall through to a fake pause NOR auto-escalate to stop (record this Decision explicitly; a breach with an unsupported pause is a recorded breach whose action could not be applied, surfaced honestly).

7. **A breach event is ALWAYS recorded, regardless of action (AC-A — AD-14, AD-12; FR-21 "breaches are always recorded as events regardless of action").** Every `Breached` decision records a breach event even when the action is `warn` (no lifecycle change) and even if the `pause`/`stop` side-effect is best-effort or fails. ### The enforcement design (the story's core value — define exactly)

**Five things are the deliverable: a `TokenBudget`, a pure `BudgetEvaluator` inside the commit path, a `BreachDecision`, the supervisor executing a `BreachAction` via Epic-1 lifecycle, and an always-recorded breach event.** The unifying tension: the budget must be checked EXACTLY where the ledger is written (AD-7 "same commit path") so no race opens; the check must read the CURRENT budget (live-changeable, AC-B); and the enforcement must reuse the existing lifecycle honestly (a best-effort/unsupported pause is surfaced, never faked — story 1-5) while ALWAYS recording the breach (FR-21).

| Concern | Mechanism | Surface |
| --- | --- | --- |

**Key design decision 1 — cumulative AND per-run (both enforced).** FR-18 defines two scopes; AD-7 defines "per-run" as exactly the Run span (`starting`→terminal). RECOMMENDED enforce BOTH on every evaluation: the per-run breach checks `run_totals(name, current_run_id)`, the cumulative breach checks `usage_totals(name)`. Either ceiling may be unset (`None` → never breaches that scope). The `BreachDecision` reports WHICH scope tripped (`BreachScope::{PerRun, Cumulative}`) so the breach event + the `BudgetExceeded` cause are honest about the reason. Precedence when both are set and both would trip on the same event: RECOMMENDED report per-run first (the tighter, run-local bound), but record that the ACTION is the same regardless of scope (the configured `BreachAction`), so precedence only affects the reported scope label, not the enforcement. A restart (story 1-6) opens a NEW Run with a fresh per-run tally (3-1's Run semantics), so per-run never bleeds across a crash/restart — the cumulative keeps climbing across Runs.

**Key design decision 2 — `pause` default, `stop`/`warn` configurable (the ratified default, honest lifecycle).** The Breach Action defaults to `pause` (PRD FR-21 `[FIXED — ratified by Islam 2026-07-02]`). RECOMMENDED semantics: **`pause`** drives `running → paused` via `Supervisor::pause`, honoring the adapter's pause Capability Declaration EXACTLY as story 1-5 established — a guaranteed pause suspends; a best-effort pause records the breach + the best-effort qualifier; an UNSUPPORTED pause records the breach and surfaces that pause could not be honored (the declaration quoted) WITHOUT faking a pause and WITHOUT silently escalating to stop (record this Decision — a breach whose action cannot be applied is surfaced honestly, not papered over; escalation-to-stop-on-unsupported-pause is a possible FUTURE policy, explicitly deferred). **`stop`** drives `running → stopping → stopped` via `Supervisor::stop` (graceful→forced, story 1-4) — a hard terminal stop for the runaway. **`warn`** performs NO lifecycle transition — it records the breach event and the agent keeps running (the lightest guardrail: visibility without interruption). The action is a per-instance config value (AC-C), validated at write time.

**Key design decision 3 — threshold is `≥` (reaches = at-or-over).** The AC + FR-18 say consumption "reaching" the budget triggers the action. RECOMMENDED interpret "reaches" as `≥`: a budget of exactly N tokens breaches when the committed cumulative (or per-run) total is `>= N`, NOT strictly `> N`. Rationale: a budget of N means "you may consume up to N" — hitting N exactly is the ceiling, and the honest guardrail fires AT the ceiling, not one token past it. Because the evaluator runs on the JUST-COMMITTED total (post-insert), the first event that carries the total to `≥ N` triggers the breach — the agent does not get to overshoot within the same interval. Record this precisely so the boundary test (a total landing exactly on N) asserts a breach.

**The always-recorded-breach ordering (AC7 — the FR-21 invariant + the NFR safety note).** FR-21: "breaches are always recorded as events regardless of action"; the NFR safety note: the engine "never silently drops an Agent's in-flight work without recording that it did." RECOMMENDED order inside the enforcement block: (1) build + record the breach event FIRST (or otherwise independently of the lifecycle side-effect), THEN (2) attempt the `pause`/`stop`. So a pause that is best-effort, unsupported, or errors NEVER loses the breach record — the breach is a fact about the ledger crossing the ceiling, independent of whether the lifecycle lever could be pulled. A `warn` records the event and stops there. Enforcement is best-effort to the RUN: a lifecycle error is a diagnostic (engine log / stderr), never a supervisor crash (3-1's "ingestion must never crash the supervisor" extends to enforcement).

### Test robustness (retro-driven — read before writing a single test)

**3-2 drives a real agent PAST a budget and asserts a lifecycle transition — the same cross-OS-fragile shape the Epic-2 retro flagged. 3-1's harness pattern is the template; do NOT regress to wall-clock races.**

- **The failure mode to avoid (retro AI-35/38).** The Epic-2 retro found agent-spawning tests using the "spawn a real agent + poll a dump file on a wall clock" `_live` pattern were cross-OS-fragile — 4 were gated Linux-only because the timing raced on macOS/Windows. Do NOT build the enforcement tests as "start the agent, sleep N ms, assert it paused." That is the pattern that got gated off two of three OSes.
- **The robust pattern to USE (inherited from 3-1).** Drive the budgeted instance through the **surviving-engine harness `start_via_surviving_engine`** (`crates/kt/tests/agent_cli.rs:43`) so the instance is genuinely `running` under a real supervising engine. Gate progress on a **readiness handshake + committed-STATE polling**: emit a known usage total over the budget via `fake_agent --emit-usage`, then POLL THE COMMITTED LIFECYCLE STATE (query the store / `kt agent show --json`) until it reaches `paused` (or `stopped` for the `stop` action), asserting on durable committed state — NOT a timing-sensitive side file, NOT a wall-clock sleep. The evaluator runs synchronously inside the ingestion path, so the transition is committed as soon as the breaching event is ingested; the test waits for the STATE, which is deterministic. For `warn`, assert the state stays `running` AND a breach event is recorded (poll the event/committed record, not a duration).
- **Run the 3-OS CI matrix EARLY (retro AI-37).** The evaluator is a pure function, the config parse is pure `std`, and `fake_agent --emit-usage` is already pure `std` (3-1) — there is NO legitimate reason for an enforcement test to be OS-gated. If a test seems to need Linux-only gating, that is a signal the harness is wall-clock racing — FIX the harness, do not gate the OS. Run the Linux/macOS/Windows matrix on the FIRST PR (AI-37). Record the Windows posture of every enforcement integration test explicitly (all pass on all three).
- **Determinism levers.** Keep the emitted token totals fixed sentinels so the breach point is exact (`budget = N`, emit an event carrying the total to exactly `N` for the `≥` boundary test, and one carrying it to `N-1` for the no-breach case). For the per-run vs cumulative distinction, set only one scope at a time. For the live-change test (AC-B), start under a high budget, confirm no breach, lower the budget via the config path, emit one more event, and poll for the transition. The unit tests for the evaluator itself are pure and instant — put the bulk of the boundary/scope coverage THERE (cross-OS by construction) and reserve the integration tests for the end-to-end wiring.
