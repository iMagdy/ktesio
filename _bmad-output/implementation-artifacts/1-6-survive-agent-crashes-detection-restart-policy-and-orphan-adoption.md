# Story 1.6: Survive agent crashes — detection, restart policy, and orphan adoption

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want crashes detected and handled by policy, and no orphan processes ever left behind,
so that unattended agents are safe to run. (FR-9, NFR-1)

## Acceptance Criteria

Verbatim from `epics.md` Story 1.6 (the SURVIVAL story). The two headline ACs are the crash-detection + restart-policy loop (AC-A) and the write-ahead + orphan-adoption recovery (AC-B); the derived criteria below make the transition-table edges, durability, the engine-kill test, and the CLI surface explicit and testable.

1. **AC-A (crash detection + restart policy).** **Given** a running Agent Instance whose process exits without a requested stop **when** the engine detects the exit **then** the instance is marked `failed` with the exit cause, and the Restart Policy applies: `never` stays failed; `on-failure` restarts with exponential backoff (1s base, ×2, 60s cap) and a visible restart count; crash-looping stops after 5 consecutive failures with the reason stated (AD-15 defaults, per-instance configurable).

2. **AC-B (orphan adoption / engine-crash recovery).** **Given** spawn write-ahead records (AD-5: instance id + PID + process start-time fingerprint persisted before exec completes) **when** the engine itself crashes and restarts **then** records matching a live fingerprint are adopted back under supervision, non-matching records are marked `failed` with last-known cause, and no agent process is left unsupervised (verified by an engine-kill integration test).

### Derived / consequence criteria (make explicit; enforced by tests)

3. **Transition-table additions (AD-15).** The crash + restart edges join the pure transition table story 1-4/1-5 built. `running --> failed` (`crash detected`) is applied by the supervisor as an EVENT-driven edge (a process-exit reaction, NOT an operator command — like `starting→running` / `stopping→stopped`); it never rejects. `failed --Start--> starting` (`failed → starting: restart policy / start`) becomes a VALID command row so a `failed` instance is restartable both by the policy executor and by an explicit `kt agent start` (FR-5 already lets `start` apply to registered *or* stopped; this extends it to `failed`). Every still-invalid `(state, command)` pair keeps returning the ONE uniform `LifecycleError::InvalidTransition { from, command }` (the same class 1-4 built, identical for every adapter, from the shared table before any backend code runs). The table stays pure + exhaustively unit-tested.

4. **Restart Policy is data, per-instance configurable (AD-15).** A `RestartPolicy` domain value with the three modes `never` | `on-failure` | (retained for symmetry, default per AD-15 defaults) drives the executor: on a detected crash of an `on-failure` instance, restart with exponential backoff **1s base, ×2 per consecutive failure, capped at 60s**; expose a **restart count** that increments per restart and resets on a clean run; after **5 consecutive failures** stop retrying and leave the instance `failed` with the reason STATED (crash-loop). `never` leaves the instance `failed` immediately with the exit cause, no restart. Defaults are the AD-15 defaults; the policy + thresholds are per-instance configurable (the config *plumbing* may be a seed — see Dev Notes / AC-9 — but the values are read from a per-instance source, not hard-wired at the call site).

5. **Crash cause is captured and recorded (AD-14/AD-6).** The `failed` transition carries the exit cause in a `TransitionCause` (recommended `Crashed { detail }` / wire tag `crashed`, carrying the exit code or signal detail) so the log/`--json`/7-2 consumers can match on it — distinct from the existing `launch-error` (a startup failure) and `stop-*` causes. Each restart transition (`failed→starting`) records the restart count and the backoff it waited. Every transition is persisted BEFORE the next side effect (per-event transaction, AD-6) so the durable state leads and the loss window stays ≤1s.

6. **Write-ahead spawn records + start-time fingerprint (AD-5).** Before `spawn` returns a supervised handle (i.e. before exec is considered committed), persist a write-ahead record `{ instance id, PID, process start-time fingerprint }` durably (AD-6, one transaction). The fingerprint is a value that distinguishes THIS process from a future PID-reuse (process start-time / creation-time). If no start-time source exists on the `ProcessBackend` yet, ADD one (see Dev Notes — this is a real gap). Clear/settle the record on a clean stop so a normally-stopped instance is not later mistaken for an orphan.

7. **Orphan adoption on engine start (AD-5, AC-B).** On `Engine::open` (or an explicit reconcile step it calls), reconcile EVERY write-ahead record against live processes: **fingerprint matches a live PID → adopt** the process back under supervision (re-populate the in-memory handle map so `stop`/`pause`/`poll` work on it, state stays `running`/`paused`); **no match (PID gone, or PID reused by a different process whose start-time differs) → mark `failed`** with the last-known cause, and ensure NO agent process of that instance is left unsupervised. This is the HONEST reconciliation: a persisted `running`/`paused` row is only kept as supervised if a matching live process is actually adopted (AI-8). **No spawn without its record committed first** (AD-5 rule).

8. **Engine-kill integration test (AC-B, NFR-1).** An integration test proves the whole guarantee end-to-end: start an instance, simulate an engine crash (drop/kill the engine WITHOUT a graceful stop so the child process survives — the child is spawned into its own group/job and outlives the parent), then open a NEW engine over the SAME state dir and assert: the live child is ADOPTED (row still `running`, handle re-held, and a subsequent `stop` actually terminates it), while a record whose process is gone is reconciled to `failed`. The test must leave no orphan process behind (asserted).

9. **CLI surface (AD-12).** `kt agent list` / `kt agent show <name>` (or `kt agent status`) SURFACE the restart count and, for a `failed` instance, the failed cause + the active restart policy — honoring the output discipline (AD-12: result → stdout, diagnostics → stderr). `kt agent start <name>` restarts a `failed` instance (AC3). If per-instance policy config is a seed this story, the CLI still reads/prints the effective policy from wherever it is stored. No new interactive prompt (FR-34).

### THE crash / restart / adoption design (the story's core value — define exactly)

**Nail these three mechanisms — they are the deliverable.**

| Concern | Mechanism | State change | Surface |
| --- | --- | --- | --- |
| **Crash detection** | The supervisor's periodic `poll_once` calls `backend.poll(handle)` (the SAME `poll` 1-4 uses in `watch_startup`, already reaping + reporting `ProcessStatus::Exited { code }`). An exit for an instance the store still shows `running`/`paused` (no `stopping` in flight) is an UNREQUESTED crash. | `running → failed` (event-driven edge, applied by the supervisor — NOT a command; never rejects) | `TransitionCause::Crashed { detail }` (exit code / signal) on the per-instance event log (AD-14). |
| **Restart policy** | `RestartPolicy` (Task 2) read per-instance. `never` → stay `failed`. `on-failure` → wait `BackoffSchedule::delay_for(n)` (1s·2ⁿ⁻¹, cap 60s), then re-run the start path; increment the **restart count**; after **5** consecutive failures STOP with the crash-loop reason stated. A clean run resets the count. | `failed → starting → running` per restart | Restart count + waited backoff recorded in the `failed→starting` event; visible via `kt agent list`/`show` (AC9). |
| **Orphan adoption** | On `Engine::open`, reconcile every persisted write-ahead `SpawnRecord {instance id, PID, start-time fingerprint}` (AD-5) against live processes via `backend.adopt(&fingerprint)`. Fingerprint match → re-hold the handle (adopt). No match (PID gone or start-time differs) → `failed` with last-known cause. | adopt: state unchanged (`running`/`paused`); no-match: `→ failed` | The engine-kill test (AC8) proves no orphan survives; a phantom `running` row is reconciled to `failed`, never left implying false supervision (AI-8). |

**The write-ahead ORDERING is the safety property (AD-5).** In `start`, the spawn record MUST be committed (persisted, AD-6 transaction) BEFORE the process is treated as supervised — concretely, persist `{instance id, pid, fingerprint}` right after `spawn` returns a live handle and before (or atomically with) the `starting→running` transition. If the engine dies in the window between `spawn` and the record commit, the child is a true orphan with no record — this is why "no spawn without its record committed first" is absolute. On a clean `stop`, CLEAR the record so a normally-stopped instance is never later adopted or failed.

**Why `running→failed` is event-driven, not a command (AC3).** Mirror 1-4/1-5: `starting→running`, `starting→failed`, `stopping→stopped` are applied directly by the supervisor when the process event happens; they are not rows in the command table (which only rejects operator COMMANDS with the uniform `InvalidTransition`). `running→failed` (crash) joins that event-driven set.
