## 3. What went well (top themes)

### 3.1 The honesty thread became a durable, load-bearing pattern — "surfaced, not silent"
This is the standout of the epic. "Honest state over convenient lies" started as FR-7's framing and hardened into an engineering discipline that runs through four stories:

- **1-5 introduced it** (the "honesty story"): pause dispatches on the *effective per-OS* declaration into guaranteed / best-effort / unsupported, and a best-effort pause emits a machine-readable `pause-best-effort` event cause **plus** a stderr qualifier — never a silent success (1-5 Dev Notes, "surfaced not silent").
- **1-6 made it a system invariant (AI-8):** orphan adoption keeps a persisted `running`/`paused` row **only if** a live process with a matching start-time fingerprint is actually adopted; otherwise it reconciles to `failed`. "Never imply a supervision that is not real."
- **1-6's honest adoption then EXPOSED a latent lie in 1-5** — see §4.1. The pattern was self-correcting.
- **1-7 pushed honesty into the type system:** budget/usage columns are `Option<MeteringSeed>` where `MeteringSeed` is an **uninhabited enum**, making "there is no metering in Epic 1" a *compile-time* guarantee that the value is always `null` — never a fabricated `0`.

> Dana (QA): "The uninhabited-enum trick is the one I'll steal for other teams. You can't accidentally ship a `0` where the honest answer is 'none yet' — the type won't let you compile it. That's the difference between a comment saying 'don't fake this' and the compiler enforcing it."
>
> Islam (Project Lead): *[the through-line worth naming: honesty moved from prose → runtime surface (1-5) → system invariant (1-6) → compile-time guarantee (1-7). That's a maturation, not a repetition.]*

### 3.2 Adversarial / independent review paid for itself — in both directions
The review process was empirically valuable *because it was falsifiable both ways*:

- **It refuted false findings.** 1-5's independent review raised two HIGH adversarial findings about a "SIGSTOP + SIGTERM hang" (a paused process supposedly can't be stopped without SIGCONT first). Both were **empirically REFUTED by reproduction** — a SIGSTOP'd process *is* terminated by SIGTERM, so `stop`-from-`paused` does not hang, and `stop()` was correct as-is (1-5 Dev Agent Record). The review didn't just wave the findings through or reflexively "fix" them; it reproduced and disproved them.
- **It caught real subtle hazards.** 1-6's review found **AI-10** (HIGH): an adopted `UnixProcess` checked liveness with `kill(pid,0)` but verified the start-time fingerprint *only at adoption*, never on subsequent reaper polls — so a recycled PID within a ~250ms poll window would read as alive and a crash would be missed. Windows was immune (real HANDLE), making it a Unix/Windows asymmetry. It also found **AI-11** (the remove-orphan NFR-1 counterexample). Both fixed in `721c6d9` with review-hardening (read-failure → alive+retry, so a live agent is never false-failed).

> Charlie (Senior Dev): "The ROI signal is the *ratio*. The review disproved two HIGH findings and confirmed two real ones. A review process that only ever confirms findings is a rubber stamp; one that only ever refutes is theater. This one did both, with reproduction. That's worth the cost."

### 3.3 The brownfield foundation landed without breaking the shipping product
1-1 restructured a single-crate shipping CLI into a 5-crate workspace with **zero behavior change** (368/368 tests byte-identical), kept the crates.io package name `ktesio` for FR-39 continuity, and armed the CI boundary + OS-cfg + semver gates *before* any engine code existed. 1-4's async refactor (adopting tokio across all 1-2/1-3 code) hit an explicit **zero-behavior-change checkpoint** (525 tests green, `kt` output byte-identical) *before* start/stop was exercised. The gates that were armed empty in 1-1 (boundary, OS-cfg) then silently protected every subsequent story.

> Winston (Architect): "Arming the boundary and OS-cfg gates in 1-1 while they were *green-on-nothing* is the highest-leverage thing in the epic. By the time 1-3 wanted an `engine → conformance` edge that would have leaked into `kt`'s graph, the gate forced the honest answer (a dev-dependency + a shipping builtin mock) instead of a boundary violation nobody would have noticed for months."

**Honorable mentions:** per-OS-behavior-as-data (testable on every CI OS, not just the matching runner); the disciplined scope boundaries (every story stated what it did *not* build and pointed at the future story that would); coverage never dipped below 95% despite the hardest supervision code arriving late.

## 4. What was hard / what to improve (top themes)

### 4.1 A deferred "harmless no-op" was actually a latent lie that only surfaced two stories later
1-5 made a conservative call (Decision #4): a *guaranteed* pause when the engine held **no in-memory process handle** was treated as a best-effort no-op — the state row transitioned to `paused` while no signal was sent. It was flagged as "cross-lifetime / 1-6 territory, unreachable in 1-5." It was **not** unreachable through the CLI: each `kt` command is a separate short-lived engine, and a clean `kt agent start` SIGKILLs its child on `Drop`, so by the next `kt agent pause` the process was already dead. The `paused` transition on a dead `running` row was a **phantom** — exactly the kind of convenient lie the honesty thread exists to prevent. It stayed green in 1-5 *only because* pre-adoption pause didn't check liveness. 1-6's honest adoption then correctly reconciled that dead row to `failed`, breaking three 1-5 CLI tests and revealing the phantom (1-6 Completion Notes, "CLI-regression root cause").

**Lesson:** when a story defers a correctness concern as "unreachable," the unreachability claim deserves the same evidence bar as a test. Here the phantom was reachable via the ordinary CLI usage pattern; the "cross-lifetime, cannot happen in 1-5" framing was too optimistic. The fix (start via a surviving-engine subprocess so pause hits a genuinely live adopted instance) was the honest one, but it cost a diagnosis cycle.

> Charlie (Senior Dev): "'Unreachable in this story' is a promise about the whole system, not about the diff. We should treat a deferred no-op the way we treat a `// TODO: safety`: name the exact reachability assumption and, if it's reachable through any shipped surface, either fix it or write the test that proves the deferral is safe."

### 4.2 The daemon/detach product discovery — Epic 1's controls don't survive between CLI commands
The single most strategic finding of the epic (see §6): `kt agent start` does **not** persist an agent across separate `kt` invocations. The single-lifetime supervisor holds handles in memory and both backends **kill the process group/job on handle `Drop`** (1-4's deliberate anti-orphan safety net). Orphan adoption (1-6) rescues the **engine-crash** case (the child re-parents to init and is adopted on next `open`), but a *clean* CLI exit intentionally kills the child. So `kt agent start foo` in one shell, then `kt agent stop foo` in another, cannot reattach — the process is already gone. This was surfaced honestly (1-4 added a stderr notice; 1-6 had to reword it — F-Med-2 — because the first wording over-promised cross-command durability). This is not a bug in Epic 1; it is a **product-shape gap**: the CLI as shipped is single-lifetime, and a daemon/detach-on-clean-exit is future work (Epic 7 territory — see §6).

### 4.3 Toolchain friction: the local default toolchain cannot build the project
Discovered in 1-2: `rusqlite 0.40.1` → `libsqlite3-sys 0.38.1` uses the `cfg_select!` macro, unstable in the machine's default `stable` (**1.94.1**) and stabilized only in **1.96.1**. Every gate in every story therefore had to run `cargo +1.96.1` (or `+stable` when that resolved to 1.96.1). It was handled well — 1-2 pinned `rust-version = "1.96.1"` at the workspace, added a CI `msrv` job, and verified `1.94.1` now fails *legibly* (clean rust-version message, not a cryptic E0658). But it was **recurring friction**: it shows up as an explicit caveat in the Dev Agent Record of 1-2, 1-3, 1-4, 1-5, 1-6, and 1-7, and it compounded on macOS where tarpaulin additionally needs `--engine llvm` (1-6/1-7). It is now captured in project memory, but a fresh contributor or a fresh agent session will re-hit it until the environment default is aligned.

> Dana (QA): "Six stories each re-explaining 'run with `cargo +1.96.1` and, on macOS, `--engine llvm`' is six chances to get it wrong. The knowledge is durable now, but the *default* isn't. A `rust-toolchain.toml` would make the right toolchain automatic instead of a thing everyone has to remember."

### 4.4 Process resilience under session limits and API stalls
The run hit real infrastructure friction: the dev-story workflow was **cut off mid-completion twice** (session limits), and create-story hit **transient API stalls**. Recovery worked and is worth codifying: (1) verify true state from disk via the local gates rather than trusting in-memory progress; (2) resume the agent with story context intact; (3) an incremental-write strategy for the very large story files (1-4 is 93KB, 1-3 67KB). The story files themselves became the durable state that made resumption possible — but their size is also a mild cost (they push against read limits; this retro had to page 1-3 and grep 1-4 rather than read them whole).

> Amelia (Developer): "The recovery pattern is the lesson, and it's a good one: disk is the source of truth, gates are how you re-derive state, and the story file is the memory. We should write that down as the standard away-mode recovery drill."

**Also noted:** several stories were executed in **Away Mode** (Islam away for stretches) with autonomous review-triage and conservative deferral of scope-expanding findings — this worked, and the deferred findings were logged as action items rather than silently dropped. The one place it bit (§4.1) was an over-confident "unreachable" call, not a dropped finding.

## 6. Strategic / forward-looking findings

### 6.1 Daemon/detach is a product decision the roadmap must place (flagged for Islam)
As detailed in §4.2: the shipped `kt` is single-lifetime. For an "operate my laptop fleet" product (PRD UJ-1/UJ-2), an operator will reasonably expect `kt agent start foo` and a later `kt agent stop foo` to work across shells. Today they don't. Options, roughly in increasing weight:
- **(a)** A background daemon / `kt`-managed engine service that owns the supervisor across commands (the CLI becomes a thin client of a persistent engine).
- **(b)** Detach-on-clean-exit: a `--detach` flag that deliberately does *not* kill the group on `Drop`, relying on the 1-6 write-ahead record + adoption to reattach on the next command.
- **(c)** Document the single-lifetime boundary as the intended v1 behavior and defer durable cross-command supervision.

This intersects Epic 7 (embed the engine — a Host holding one long-lived `Engine` already gets durable supervision; the daemon is essentially "kt embeds the engine as a service"). **Recommendation:** treat this as an explicit Epic 7 concern (or a dedicated pre-Epic-7 story), and in the meantime keep the honest stderr notice. It is a genuine open product question, not an engineering oversight.

### 6.2 Sequencing the 14 open action items into future stories
The epic exits with 14 open items (all severity `low` except none remaining high/med after AI-10/AI-11 closed). They cluster cleanly — recommend folding by natural owner rather than a dedicated cleanup story:

- **CI / automation (AI-2, AI-3):** the `test_automation.py` `-p ktesio` prefix-pin tightening and the semver cache-key content-hash. → fold into the next CI-touching story, or the first Epic 7 publish story (7-4) where the semver gate actually arms.
- **Adapter manifest polish (AI-5, AI-6):** metering error-attribution keys on the span not the vocabulary; `contract_version` strict-triple vs lenient. → **Epic 6-6** (contract freeze / version negotiation) is the exact owner for AI-6; AI-5 folds into any manifest-touching story.
- **Supervisor pause/persist ordering + qualifier honesty (AI-9):** the guaranteed-pause persist-order and the no-in-custody qualifier. → revisit if an Epic 3 (metering-on-pause) or Epic 7 (event stream) story makes one ordering clearly preferable.
- **Crash-detection edge cases (AI-12, AI-13, AI-14):** persistent-poll-error swallowing, adopted-non-zero-exit cause cosmetics, start_time=0 sentinel fail-closed. → fold into the first Epic 3/Epic 7 story that touches the reaper hot path (AI-14's fail-closed is the one worth doing soonest — it's a correctness-adjacent sentinel).
- **Fleet read shapes (AI-15, AI-16):** `show --json` O(N) scan + silent status degradation; `fleet_entry_for` N+1 read. → harmless at Epic-1 fleet sizes; fold into Epic 7-5 (the NFR-4 benchmark story) where fleet-size performance is actually measured, or the first story that grows the fleet.

**Recommendation:** do **not** create a "tech-debt cleanup" story. These are all correctly-deferred, low-severity, and have natural future owners; a cleanup story would fragment context. Track them where they are (the `action_items` ledger already surfaces open ones) and let the owning story pull each in.

### 6.3 Two spine refinements are precedent worth keeping
1-3's review discovered two invariants under implementation pressure and fed them **back into the spine** (Islam-ratified 2026-07-04, no ADs renumbered): the **AD-4 read-time projection clause** (persist the full per-OS declaration; project onto the running OS at *read* time so the state dir is portable) and the **adapter-kind charset convention** (`^[a-z0-9][a-z0-9_-]*$`). This "discovered-invariant → spine refinement" loop kept the architecture document a living contract rather than a stale plan. Keep doing it.
