# Story 2.4: Keep secrets out of everything

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want secret values referenced indirectly and never logged, echoed, or serialized unmasked,
so that my API keys are safe by construction. (FR-14, NFR-6)

## Acceptance Criteria

Verbatim from `epics.md` Story 2.4 (the FOURTH and FINAL story of Epic 2 — config + secrets). The three headline ACs are the `secret:NAME` indirection resolved through the env + 0600-file resolvers into a `SecretString` (whose `Display`/`Debug` redact) that reaches the adapter as the REAL value but is masked in effective-config output (AC-A), the no-leak PROOF that secrets never appear in engine/CLI logs, event payloads, or `--json` output (AC-B), and the explicit `--reveal` acknowledgment as the ONLY way an unmasked secret enters machine-readable output (AC-C). The derived criteria below make the `secret:NAME` classification, the two resolvers (incl. the 0600 permission check + its cross-OS handling), the `SecretString` newtype (redacting `Display`/`Debug` + no-accidental-serialize), the masking at the story-2-3 display choke point + the snapshot + event payloads, the no-leak test matrix, and the `--reveal` flag explicit and testable.

> **CRITICAL SCOPING (read before AC-A):** This story delivers the **secrets no-leak guarantee IN FULL** — it is the LAST Epic 2 story, so there is NO further deferral: FR-14 + NFR-6 must be complete after it. It BUILDS ON 2-1 (the resolver + `ResolvedValue::display()`), 2-2 (config delivered into the adapter's native mechanism at start via `apply_config_mapping`), and 2-3 (which deliberately routed ALL value display — human table, `config get --json`, the persisted `effective-config.json` snapshot — through the ONE [`ResolvedValue::display()`](crates/ktesio-engine/src/domain/config.rs) choke point **specifically so 2-4 adds masking in one place**). 2-4 adds: (1) `secret:NAME` CLASSIFICATION of a resolved value; (2) a `SecretResolver` port (AD-10) with two v1 impls — process **env** and the engine **secrets file (mode 0600)**; (3) the `SecretString` newtype whose `Display`/`Debug` redact and which is guarded against accidental `Serialize`/logging; (4) MASKING at the 2-3 display choke point (so the human table + `--json` + the snapshot mask a secret-classified value AT ONCE) + a guarantee that no secret reaches event payloads; (5) the `--reveal` flag as the SOLE explicit acknowledgment that lets an unmasked secret value into machine-readable output; and (6) a no-leak TEST MATRIX proving a real resolved secret never appears in logs, events, `--json`, or the snapshot unless `--reveal` is passed. The subtlety this story MUST get right: the resolved secret reaches the ADAPTER as the REAL cleartext value (2-2's `apply_config_mapping` places it into env/flag/file) while being masked EVERYWHERE it is displayed/logged/serialized — display and delivery diverge, and the `SecretString` type is what keeps them honest. It does NOT re-open the layered model / precedence / write-time validation (2-1), the native mapping mechanics (2-2), or the provenance rendering + snapshot plumbing (2-3) — it makes the value that flows through them secret-aware.

1. **AC-A (verbatim — `secret:NAME` resolves to a masked-everywhere `SecretString` that still reaches the adapter).** **Given** config referencing `secret:NAME` with the env and 0600-file resolvers (AD-10) **when** the instance starts **then** the resolved value reaches the adapter, lives only in a `SecretString` newtype whose `Display`/`Debug` redact, and is masked in effective-config output. The classification is: a resolved leaf VALUE whose string form has the `secret:` prefix is secret-classified (the reference syntax is `secret:NAME`, where `NAME` is the lookup key handed to the resolver). At start, in `supervisor::start_inner`, the `secret:NAME` reference is RESOLVED (env first, then the 0600 secrets file — record the order as Decision) to a `SecretString` holding the real cleartext, which `apply_config_mapping` places into the adapter's native mechanism (env/flag/file) AS THE REAL VALUE (the agent gets a usable key); but every DISPLAY of that leaf (the human table, `config get --json`, and the persisted `effective-config.json` snapshot) shows a MASK, not the cleartext, because all three route through the single 2-3 [`ResolvedValue::display()`](crates/ktesio-engine/src/domain/config.rs) choke point which 2-4 makes secret-aware.

2. **AC-B (verbatim — a test proves secrets never appear anywhere they must not).** **And** a test proves secrets never appear in engine/CLI logs, event payloads, or `--json` output. This is the NO-LEAK TEST MATRIX (the security heart, NFR-6 "safe by construction"): with an instance configured with a `secret:NAME` value resolving to a known sentinel cleartext (e.g. `s3cr3t-sentinel`), assert the sentinel appears in NONE of — (a) the engine's own log + the per-instance `instance.log` transition-event lines; (b) any `TransitionEvent` / `TransitionCause` payload (AD-14) — including launch-error/crash `detail` strings; (c) `kt agent config get <name> --json` and the human table; (d) the persisted `effective-config.json` snapshot. The masked/redacted form appears instead. The sentinel DOES reach the adapter's native mechanism (proving the value is usable) — asserted separately from the no-leak surfaces.

3. **AC-C (verbatim — machine-readable cleartext only under explicit `--reveal`).** **And** machine-readable output includes a secret value only under an explicit `--reveal` acknowledgment (AD-12). `kt agent config get <name> [<key>] --json` (and, if it also reveals, the human read) masks secret-classified values by default; passing `--reveal` (an explicit operator acknowledgment) is the ONLY path that emits the unmasked cleartext in machine-readable output. Record precisely: `--reveal` affects ONLY the on-demand `config get` read surface — it NEVER un-masks the persisted snapshot, the logs, or the event payloads (those are always masked, no flag un-masks them). Without `--reveal`, `--json` carries the masked form; with it, the real resolved value (resolving `secret:NAME` for the read, or echoing the stored reference — record which per Decision).

### Derived / consequence criteria (make explicit; enforced by tests)

4. **`secret:NAME` classification is a single, tested predicate (AC-A — the reference syntax).** A leaf is secret-classified iff its resolved string value begins with the `secret:` prefix followed by a non-empty `NAME` (mirror 2-1's `is_pass_through` non-empty-child discipline — a bare `secret:` with no name is NOT a secret reference; record whether it is an error or an ordinary opaque string). The predicate + a `secret_name(value) -> Option<&str>` extractor (the `NAME` after the prefix, the resolver's lookup key) live in the engine's `domain::config` beside `is_pass_through`/`pass_through_tail`, tested there. This classification governs BOTH resolution (at start) and masking (at display) so the two never disagree — a value is secret for masking exactly when it is secret for resolution.

5. **The `SecretResolver` port with two v1 impls: env + 0600 secrets file (AC-A — AD-10).** Introduce a `SecretResolver` port (the AD-10 seam `ports/mod.rs` reserves) with v1 resolvers: (a) **process env** — `secret:OPENAI_KEY` resolves to `std::env::var("OPENAI_KEY")`; (b) **engine secrets file (mode 0600)** — a file under the state dir (record path via `EnginePaths`, e.g. `<state base>/secrets.toml`) whose `NAME=value` entries resolve the reference. Record the resolution ORDER (RECOMMENDED: env FIRST, then the file — env is the operator's ad-hoc override and the file is the durable store; record it as `[ASSUMPTION]`). A `secret:NAME` that resolves in NEITHER is a typed resolution error at start (the start is rejected, NO half-launch — mirroring how a config-apply/snapshot failure rejects before the transition), naming `NAME` + the resolvers tried WITHOUT echoing any value. The 0600 file resolver enforces the permission check (AC6); OS-keychain stays a Deferred resolver behind the same port (AD-10 — build NONE of it).

6. **The 0600-file resolver enforces a 0600 permission check, cross-OS (AC-A, NFR-6 — the filesystem-permission concern).** The secrets file is expected at mode `0600` (owner read/write only). On unix, the resolver CHECKS the file's permission bits and REFUSES to read a secrets file that is group/other-accessible (a world-readable secrets file defeats the guarantee) — a typed error telling the operator to `chmod 600`. Because a `0600`/unix-permission check is OS-specific, the actual permission inspection MUST live inside `backends::{unix,windows}` (AD-4 — the sole allowlisted `#[cfg]` home; the OS-cfg grep gate confines `cfg(...)` to `backends/`). **Cross-OS handling (Windows is now a live CI gate — flag this):** unix mode bits do not exist on Windows, so the Windows backend implements the permission check with a Windows-appropriate rule (record the Decision: RECOMMENDED — the Windows impl either (i) checks the ACL so only the current user has access, or (ii) if a faithful ACL check is out of v1 scope, SKIPS the strict-permission refusal and documents that Windows relies on default per-user profile ACLs, returning a portable "permission not verifiable on this OS" note rather than a false pass or a hard failure). The domain/resolver code stays OS-agnostic; only the permission INSPECTION is a per-backend function. Do NOT branch on OS anywhere outside `backends/`.

7. **The `SecretString` newtype redacts `Display`/`Debug` and resists accidental serialization/logging (AC-A, AC-B — the "safe by construction" core, NFR-6/AD-10).** A `SecretString(String)` newtype (record its home — RECOMMENDED the engine `domain`, e.g. `domain::secret`) whose `Display` AND `Debug` both emit a fixed redaction (e.g. `"secret:***"` / `"[REDACTED]"` — record the token) and NEVER the inner cleartext. It exposes the cleartext ONLY through an explicit, greppable accessor (e.g. `expose_secret(&self) -> &str`, mirroring the `secrecy` crate convention — record whether a crate is adopted or it is hand-rolled; RECOMMENDED hand-rolled to avoid a new dependency, since the type is tiny and the guarantee is easy to test). It MUST NOT derive `Serialize` (accidental `serde_json` of a struct holding one would leak) — record that any serialization is a deliberate masked encode, never a derive. Optional hardening (record if adopted): zeroize-on-drop is NOT required for v1 (flag as out-of-scope unless trivially free). The type is what lets AC-A hold: the adapter path calls `expose_secret()` for delivery; every display/log/serialize path gets the redacting `Display`/`Debug`.

8. **Masking hooks the ONE 2-3 display choke point so all three surfaces mask at once (AC-A, AC-C — the surgical change 2-3 set up).** [`ResolvedValue::display()`](crates/ktesio-engine/src/domain/config.rs) (the single path the human table, `config get --json`, AND the `effective-config.json` snapshot all render through — 2-3 AC8) is made secret-aware: when the leaf is secret-classified (AC4), `display()` returns the MASK, not the cleartext. Because 2-3 funnelled all three surfaces through this one method, this single change masks the human table + `--json` + the snapshot simultaneously. Record the exact seam: `display()` gains the secret-check (RECOMMENDED — the fewest choke points), OR a parallel `display_masked()` is introduced and the three surfaces switch to it while the adapter delivery path keeps the raw value (record which; RECOMMENDED keep `display()` masking + expose the real value to `apply_config_mapping` via the resolved `SecretString`/a distinct delivery accessor, so display defaults to safe and delivery is the explicit exception).

9. **The adapter still receives the REAL resolved secret value at start (AC-A — display and delivery diverge).** 2-2's `apply_config_mapping` places each leaf's value into the adapter's native mechanism (env/flag/file) at `start_inner`. For a secret-classified leaf, the value placed MUST be the RESOLVED CLEARTEXT (from the `SecretString` via `expose_secret()`), not the `secret:NAME` reference and not the mask — the agent needs a usable API key. This is the crux: the SAME leaf renders masked in `config get`/snapshot/logs but delivers cleartext to the adapter's private native config. Record where resolution happens (RECOMMENDED: at `start_inner`, the reference resolves to a `SecretString` BEFORE `apply_config_mapping`, and the mapping's value-placement calls `expose_secret()` for a secret leaf; the effective config's `display()`-based surfaces stay masked). The rendered native config FILE the adapter reads (2-2's `write_config_file`) will contain cleartext by necessity (it is the agent's private config inside the Agent Home) — record this as an explicit, accepted boundary (the Agent Home is process/filesystem-isolated per FR-2, not a security sandbox — NFR-6; the file is the agent's own secret to hold, exactly like the 0600 secrets file).

10. **No secret reaches an event payload or a log line (AC-B — AD-14 + AD-12 "never log secrets").** Audit every `TransitionCause` `detail` producer (launch-error, crash, forced-stop, pause/resume best-effort — [`event.rs`](crates/ktesio-engine/src/domain/event.rs)) and every log line (the per-instance `instance.log` transition events + the engine's own log — AD-12) to prove none can carry a resolved secret. In practice: a launch-error `detail` must not echo the resolved env/args (which now hold cleartext for a secret leaf); the spawn/launch diagnostic names the binary/kind, not the env values. Record the audit result + any redaction added (RECOMMENDED: the `SecretString`'s redacting `Debug` is the primary guard — anything that formats a value holding secrets gets the mask; assert with the no-leak matrix). The `agent.log` (the agent's OWN stdout/stderr, AD-12) is the agent's output, not engine-emitted config — if the agent echoes its own key that is the agent's concern, NOT a Ktesio leak (record this boundary honestly).

11. **The `--reveal` flag is the sole un-mask, scoped to `config get` machine-readable output (AC-C — AD-12).** Add `--reveal` to `kt agent config get` (clap wiring in [`main.rs`](crates/kt/src/main.rs)); it flows to `config_get`/`config_json`. Default (no `--reveal`): secret leaves render masked in BOTH `--json` and the human table. With `--reveal`: the machine-readable (`--json`) output carries the unmasked value (record whether `--reveal` also un-masks the human table — RECOMMENDED: yes, symmetric, since a human explicitly asking to reveal wants to see it). `--reveal` NEVER changes the snapshot, the logs, or event payloads (AC-C scope). Record how `--reveal` obtains the cleartext (RECOMMENDED: it re-resolves `secret:NAME` through the `SecretResolver` for the read — so the reveal is live and honest; a resolution failure under `--reveal` is a diagnostic, not a crash). No new interactive prompt (FR-34) — `--reveal` is a flag, not a confirmation dialog.

12. **Output discipline + honest scoping notes (AD-12, AD-10 final delivery).** `config get`'s masked (or `--reveal`ed) values ride STDOUT (the table / the `--json` document); diagnostics (resolution failures, `chmod 600` remediation) go to STDERR with a non-zero exit. `--json` stays pure JSON on stdout. The snapshot write stays silent on success. As the FINAL Epic 2 story, the stale "secrets are Epic 2.4 / masking is 2-4" forward-reference comments left across 2-1/2-2/2-3 (`config.rs`, `adapter/mod.rs`, `registry.rs`, `kt` `config_set`/`config get` docs — see the grep in Dev Notes) are RESOLVED now that secrets ship: update or remove each so no false deferral note remains (record which). No new interactive prompt (FR-34).

### Cross-OS 0600 permission check (Windows is now a live CI gate)

**The problem.** AD-10 mandates the secrets file be mode `0600`. A meaningful guarantee CHECKS this: a world-/group-readable secrets file defeats "safe by construction," so the 0600-file resolver should REFUSE such a file. But `0600` is a UNIX permission concept — `std::os::unix::fs::PermissionsExt` gives the mode bits; Windows has no unix mode and models access via ACLs. Since the pivot pinned the toolchain and made CI toolchains explicit (AI-17), **Windows is a LIVE CI gate** — the Windows backend must COMPILE and behave sanely, not `unimplemented!()`.

**The rule (AD-4).** OS-conditional code lives ONLY in `backends::{unix,windows}` (the sole allowlisted `#[cfg]` home; the OS-cfg grep gate FAILS the build if `cfg(unix)`/`cfg(windows)` appears elsewhere). So: the resolver/domain code stays OS-agnostic and calls a per-backend `check_secrets_file_permissions(path) -> Result<(), SecretError>` (record the exact name). The `#[cfg]` split is confined to `backends/`.

- **Unix (`backends::unix`).** Read the file's mode via `PermissionsExt::mode()`. REFUSE if any group/other bit is set (i.e. require `mode & 0o077 == 0`); a failing check is a typed error with a `chmod 600 <path>` remediation (NFR-1). This is the real enforcement of AD-10's "mode 0600."
- **Windows (`backends::windows`) — record the Decision (AC6).** Unix mode bits are meaningless here. Two defensible options, RECOMMENDED **(B)** for v1:
  - **(A) Faithful ACL check.** Inspect the file's DACL so only the current user (and SYSTEM/Administrators) has access; refuse otherwise. Correct but heavier (needs `windows`/`winapi` ACL calls) — likely over-scope for v1's "tiny secrets type" budget.
  - **(B) Documented portable skip (RECOMMENDED).** Do NOT attempt a unix-style refusal; return `Ok(())` (or an `Ok` carrying a portable "permission not strictly verifiable on this OS; relies on default per-user profile ACLs" note surfaced once to stderr) and DOCUMENT that on Windows the secrets file's protection relies on the default per-user profile ACLs (the state dir lives under the user's profile). This avoids a FALSE PASS masquerading as a unix-grade check AND avoids a hard failure that would make secrets unusable on Windows. Record this clearly in `docs/architecture.md` so the Windows guarantee is HONEST (NFR-6's "boundary is stated in docs").

**Testing posture (AC6).** Unix: a temp secrets file `chmod 0644` is REFUSED (typed error); a `0600` file passes — gate the assertion `#[cfg(unix)]` (test-side cfg is allowed under the testing convention; keep it minimal). Windows: a PORTABLE assertion that the resolver does not falsely fail on a normally-created file (the check returns `Ok`), plus — if option (B) — that the documented note path is exercised. Do NOT write a unix-only test that would fail to COMPILE on the Windows gate; guard OS-specifics behind `#[cfg]` in the test module or keep them in the backend's own tests.
