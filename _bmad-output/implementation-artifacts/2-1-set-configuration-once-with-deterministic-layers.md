# Story 2.1: Set configuration once — with deterministic layers

Status: done

## Story

As an Operator,
I want config layered as engine defaults < agent-kind defaults < instance config < invocation overrides,
so that the same key always resolves predictably. (FR-11)

## Acceptance Criteria

Verbatim from `epics.md` Story 2.1 (the FOUNDATION story of Epic 2 — config). The three headline ACs are the deterministic precedence resolution (AC-A), the write-time unknown-key rejection + nearest-key suggestion (AC-B), and the TOML-at-every-layer / path-authority storage (AC-C, AD-9). The derived criteria below make the pure resolution function, the `agent.*` pass-through boundary, the CLI set/get surface, and the seams for 2-2/2-3/2-4 explicit and testable.

> **CRITICAL SCOPING (read before AC-A):** This story delivers the config **MODEL** — the four-layer data model + deterministic precedence resolution + write-time validation + TOML storage under path authority (AD-9). It does NOT deliver: the per-adapter NATIVE-mechanism mapping (files/env/flags) — that is **2-2 (FR-12)**; the effective-config **provenance rendering** + the persisted `EffectiveConfig` snapshot surface — that is **2-3 (FR-13)**; and **secrets** (`secret:` resolvers, `SecretString`, masking) — that is **2-4 (FR-14, AD-10)**. Build NONE of those here. Where the model must leave a seam for a later story (a pass-through namespace 2-2 consumes; a resolver that returns per-value provenance so 2-3 can render + persist it; a value type that 2-4 can later classify as secret), note it as a seam and stop. Do NOT introduce `SecretResolver`, `SecretString`, or any `secret:` handling — a `secret:`-prefixed value in Epic 2.1 is just an ordinary string that survives round-trip untouched (2-4 will teach the engine to resolve + mask it).

1. **AC-A (deterministic precedence).** **Given** the same key set at kind level and instance level **when** the effective config resolves **then** the instance value wins, every time, per the documented precedence (AD-9): **engine defaults < agent-kind defaults < Agent Home instance config < invocation overrides** (later layers override earlier).

2. **AC-B (write-time validation + nearest-key suggestion).** **Given** a config write with an unknown key OUTSIDE the pass-through namespace **when** validation runs at WRITE time **then** the write is rejected (nothing persisted) and the nearest valid key is suggested.

3. **AC-C (TOML + path authority).** **And** all four layers are TOML and stored/read ONLY through engine APIs (path authority) — no caller reads or writes a config file directly; the engine owns every path (AD-9, consistent with AD-6's path-authority stance).

### Derived / consequence criteria (make explicit; enforced by tests)

4. **Precedence resolution is a PURE, exhaustively-tested function (AC-A).** The core deliverable is a pure `resolve(layers) -> EffectiveConfig` function (no I/O): given the four ordered layers as parsed TOML maps, it folds them last-wins into a single effective map. It is total and deterministic — the SAME inputs always yield the SAME output, independent of machine, OS, or clock. Key-level (not table-level) override: setting `a.b = 1` at the instance layer overrides ONLY `a.b`, leaving sibling keys from lower layers intact (a deep/per-leaf merge, NOT a shallow whole-table replace — otherwise a single instance override would silently drop kind-level siblings). Exhaustively unit-tested: key present in one layer only (each of the four), key present in adjacent layers (each precedence pair), key present in all four (top layer wins), nested tables, and the empty-layer / all-empty cases. This mirrors how AD-15's transition table is "data, exhaustively unit-tested."

5. **The resolver makes provenance TRACTABLE without rendering it (seam for 2-3).** So that 2-3 (FR-13) can render "each value's source layer" and persist the `EffectiveConfig` snapshot WITHOUT re-architecting the resolver, `resolve` tracks, per resolved key, which layer supplied the winning value (an internal `SourceLayer` tag alongside each value). 2-1 does NOT render provenance to any human/JSON surface and does NOT persist the snapshot — it only produces a resolver whose output CAN carry the tag. Whether the tag is exposed on a public type now or kept internal is a recorded dev decision (RECOMMENDED: model it in the resolver's return type so 2-3 is purely additive; keep it out of the 2-1 CLI output). No provenance column, no snapshot file, no `kt agent config show`-with-sources in this story.

6. **Write-time validation rejects unknown keys with a nearest-valid-key suggestion (AC-B).** Validation runs when a value is WRITTEN (e.g. `kt agent config set <key> <value>`), BEFORE anything is persisted — a rejected write leaves the instance config byte-unchanged (mirror the registry's "reject before any side effect" atomicity). A key is VALID if it is a known unified key (in the 2-1 known-key set) OR it lives under the `agent.*` pass-through namespace (AC7). An unknown key outside `agent.*` is rejected with an error that NAMES the offending key AND suggests the nearest valid known key (edit-distance / prefix match over the known-key set; if nothing is within a sane threshold, say so rather than suggest nonsense). The suggestion mechanism is unit-tested against fixed near-miss inputs (e.g. `modle` → suggest `model`).

7. **The `agent.*` pass-through namespace is a first-class boundary (seam for 2-2).** Keys under the reserved `agent.*` prefix are the escape hatch for agent-native extras (FR-12): they BYPASS unknown-key validation (delivered verbatim) and are NOT checked against the known-key set. 2-1 establishes the boundary — the namespace prefix, the "pass-through keys skip validation and round-trip verbatim" rule — and unit-tests that an `agent.*` key writes successfully while an equally-unknown non-`agent.*` key is rejected. 2-1 does NOT deliver the mapping of pass-through keys into an Agent's native mechanism (that is 2-2, FR-12) and does NOT render the "un-validated" marking in effective-config output (that is 2-3, FR-13); it only reserves the namespace and honors the bypass. Record the exact reserved prefix (`agent.`).

8. **The four layers are TOML, each with a defined source under path authority (AC-C, AD-9).** The engine owns where every layer lives and is the ONLY reader/writer: **(1) engine defaults** — a static, engine-owned TOML (embedded constant or engine-managed file; recorded decision), the same for every instance; **(2) agent-kind defaults** — a per-kind TOML the adapter/kind supplies (in Epic 2.1 this MAY be empty/absent for the `mock` kind — record how a kind with no defaults resolves, i.e. to an empty layer, NOT an error); **(3) instance config** — the existing per-Agent-Home `config.toml` that `materialize_home` already writes (`crates/ktesio-engine/src/paths.rs::INSTANCE_CONFIG_FILE`); **(4) invocation overrides** — ephemeral, supplied at resolve/start time (NOT persisted to disk in 2-1; a map passed into `resolve`). All parsing goes through the engine; a malformed TOML layer surfaces a typed error naming the layer + path (never a panic).

9. **Config lives as TOML files under path authority — NOT in SQLite (AC-C).** SQLite remains the lifecycle/registry/Usage-Ledger store (AD-6); config does NOT move into it. This preserves AD-9's "TOML at every layer" literally and keeps the instance layer editable-in-place in the Agent Home (the existing `config.toml`). The engine gains a `toml` PARSE dependency (the workspace already pins `toml = "1"`; today only `ktesio-adapter-api` consumes it per AD-3 — this story adds it to `ktesio-engine` for config parsing, which is an approved, additive runtime dep). Record this in the boundary-gate notes.

10. **CLI surface: `kt agent config set` / `get` (FR-11, AD-12).** `kt agent config set <name> <key> <value>` writes the key to the instance layer (validated per AC-B; rejected writes touch nothing and print the suggestion to stderr). `kt agent config get <name> [<key>]` reads the EFFECTIVE (resolved) config — with `<key>`, prints that key's effective value; without, prints the whole effective map — honoring output discipline (result → stdout, diagnostics/notes → stderr, AD-12). No new interactive prompt (FR-34). `--json` on `get` is OPTIONAL for 2-1 (record the decision); provenance/source-layer in the output is explicitly 2-3. The command attaches as a new `AgentCommands::Config { … }` subcommand in `crates/kt/src/main.rs`, dispatched into `crates/kt/src/cli/agent.rs` (the same module `list`/`show` live in).

11. **Output discipline + honest scoping notes (AD-12).** Where 2-1 surfaces a value that a later story will enrich, it says so honestly on stderr, never fabricates: `get` output does NOT show source layers (a one-line stderr note may point to 2-3 for provenance), and a `secret:`-prefixed value is rendered/stored as-is with NO masking (2-4 owns masking) — but 2-1 MUST NOT print a real secret it resolved, because it resolves none (a `secret:` value is an opaque string in 2-1). No number or source is invented.

### The config-model design (the story's core value — define exactly)

**Two things are the deliverable: a PURE resolver and the LAYER PLUMBING that feeds it.**

| Concern | Mechanism | Surface |
| --- | --- | --- |
| **Deterministic precedence (AC-A)** | A pure `resolve([EngineDefault, KindDefault, Instance, InvocationOverride]) -> EffectiveConfig` that folds layers last-wins with a DEEP per-leaf merge, recording the winning `SourceLayer` per key. No I/O, no clock — same inputs, same output, every machine. | `EffectiveConfig` domain type (values + per-key source tag). |
| **Write-time validation (AC-B)** | `validate_write(key, value)`: accept a known key OR an `agent.*` pass-through key; reject an unknown non-`agent.*` key with the nearest known key suggested (small edit-distance over the known-key set). Runs BEFORE persistence — a rejected `set` touches nothing. | `ConfigError::UnknownKey { key, suggestion }`. |
| **TOML layers under path authority (AC-C)** | Engine defaults (engine-owned static TOML) + kind defaults (per-kind TOML, may be empty for `mock`) + instance `config.toml` (already in the Agent Home) + invocation overrides (a map at resolve time). **Deep-merge, not shallow (the subtle correctness point).** Setting `a.b` at the instance layer must override ONLY `a.b`, leaving a kind-level `a.c` intact. A shallow whole-table replace would silently drop `a.c` the moment an operator set any sibling — a data-loss bug. The resolver merges per leaf (recurse into tables; a scalar at a later layer wins for that exact dotted key). Exhaustively unit-test the nested-sibling case.

**Precedence, unambiguously (AD-9):** `EngineDefault (weakest) < KindDefault < Instance < InvocationOverride (strongest)`. A later layer always wins for a given key. The `SourceLayer` enum's ordering encodes this; the fold applies layers weakest-first so the last write wins.
