## Story

As an Operator,
I want to supply input/output Rates and set a Cost Cap,
so that a runaway agent pauses before it surprises my bill. (FR-20, FR-21; SM-2)

1. **AC-A (verbatim — a Rate derives dollars; no retroactive repricing; a Rate change re-prices future only).** **Given** a Rate supplied for an instance **when** usage accrues **then** the Usage Ledger derives dollars from metered tokens, historical dollars keep the Rate in force when consumed (no retroactive repricing), and changing the Rate re-prices future consumption only. The `Rate` is per-instance input + output `$/1M`-token prices (PRD FR-20 `[ASSUMPTION: split rates]`, glossary "input and output rates supported"). Dollars are DERIVED, not stored on the `UsageEvent` (which stays 3-1's frozen token-only shape — AD-6 keeps `record_usage_event` the sole writer): the engine computes `cost = input_tokens × rate.input / 1e6 + output_tokens × rate.output / 1e6` in a **billing-safe integer micro-dollar representation** (NOT `f64` — AD-8, the 3-1 `u64→i64` money lesson). Record the Decision: **"no retroactive repricing"** means the ledger's per-event dollar figure is computed at the Rate IN FORCE when that usage was consumed, and a later Rate change does NOT re-walk historical events (PRD FR-20 `[ASSUMPTION: no retro-repricing]`). RECOMMENDED mechanism (record + justify): because the current implementation derives-on-read from the token ledger, "keeping the historical Rate in force" requires the consumed Rate to be RECOVERABLE per event — either (a) persist the effective Rate onto each committed ledger event (a new derived column, NOT on the adapter-facing `UsageEvent` wire type — an engine-side ledger concern), or (b) persist a Rate-change history (Rate + effective-from) and price each event by the Rate active at its `occurred_at`. Pick ONE and record it; (a) is simpler and matches "the Rate in force when consumed" most literally. A Rate changed while `running` applies to the NEXT event only (mirrors 3-2's AC-B live-config read + the no-retroactive-un/re-breach discipline).

### Derived / consequence criteria (make explicit; enforced by tests)

4. **Money is integer micro-dollars, NEVER `f64` — the billing-correctness crux (AC-A, AC-C — AD-8; the 3-1 `u64→i64` lesson).** THE decisive representation decision of this story. Dollars MUST NOT be floating-point anywhere on the billing/enforcement path — `f64` accumulates rounding error and cannot represent `$0.01` exactly, and a cost cap enforced on a lossy figure is not a trustworthy guardrail. RECOMMENDED: a newtype `Micros(i64)` (or `u64`) representing **integer micro-dollars** (1 dollar = 1_000_000 micros; `$0.000001` granularity — fine enough for `$/1M`-token pricing where a single token costs sub-cent fractions). Record the type + the module (RECOMMENDED `domain::cost` — `Micros`, `Rate`, `CostCap`, `EstimateLabel`, the cost derivation + the evaluator; sibling to `domain::budget`). Record why micro-dollars over cents: `$/1M`-token rates produce per-token costs far below one cent (e.g. `$3/1M` = `$0.000003`/token), so cents would truncate every realistic per-event cost to `0` — micro-dollars preserve it; the RENDER layer rounds to cents/dollars for humans (AD-8), the LEDGER keeps micros. Derive `Serialize`/`Deserialize` (as an integer, snake_case) so it rides the Fleet cost view + the breach payload without a float ever touching the wire. This echoes 3-1's `u64→i64` retro lesson: pick the honest integer domain up front; no lossy money.

5. **The cost derivation is a pure function with an explicit rounding rule (AC-A — AD-8; exhaustively unit-tested).** A PURE function (record the shape — RECOMMENDED `fn cost_micros(input_tokens: u64, output_tokens: u64, rate: &Rate) -> Micros`, or a `Rate::cost_of(&UsageTotals) -> Micros`) computing `input_tokens × rate.input_micros_per_1m / 1_000_000 + output_tokens × rate.output_micros_per_1m / 1_000_000`, where each `rate.*_micros_per_1m` is the per-1M-token price already in micro-dollars (an integer config value). Record the **rounding rule EXPLICITLY** (the money-correctness crux): the division by `1_000_000` truncates in integer math, so specify **round-half-up** (add `500_000` before the integer divide, or use a documented banker's/half-up policy) so a fractional micro-dollar rounds deterministically — and record which (RECOMMENDED round-half-up, simplest to reason about and test). Record **overflow discipline**: use saturating/checked arithmetic (`u128` intermediate for the `tokens × price` multiply to avoid `u64` overflow at large token counts × large rates, then divide down to `i64` micros, saturating) — a runaway token count must NEVER wrap the cost to a small number and silently un-breach. NO I/O, NO ledger, NO lifecycle — pure, so the boundary/precision/overflow tests are cheap and cross-OS by construction. This function is BILLING MONEY: its unit tests are exhaustive (see Task 1 + Dev Notes) — zero tokens → zero cost; input-only / output-only; input≠output rate (the two directions priced independently); the rounding boundary (a token count landing on a half-micro); a huge count that would overflow `u64` in the multiply (proven to saturate, not wrap); a zero rate → zero cost.

6. **The `Rate` is per-direction: separate input and output `$/1M` prices (AC-A — FR-20 `[ASSUMPTION: split rates]`).** FR-20 + the PRD glossary say "input and output rates supported"; the 3-1 ledger ALREADY stores `input_tokens` and `output_tokens` separately (`UsageTotals`/`UsageEvent`, `usage.rs:108-110`/`:142-144`), so the two directions have real, independent token counts to price. Record the `Rate` shape (RECOMMENDED `struct Rate { input_micros_per_1m: u64, output_micros_per_1m: u64 }` — integer micro-dollars per 1M tokens, matching AC4). Either direction may be set; record the Decision for a partially-specified Rate (RECOMMENDED: a Rate REQUIRES both directions to derive dollars — or an unset direction prices at `0` for that direction — pick ONE and record it; RECOMMENDED require both present for a Rate to be "supplied", so a half-Rate is treated as no-Rate-yet (inert, AC-B), avoiding a silently-half-priced ledger). NO single blended rate. Record the config leaf types (the per-direction price is a config value — see AC8). This is why the derivation (AC5) multiplies each direction by its OWN rate: input≠output pricing is the common real case (most models price output several× input).

7. **The `CostCap` mirrors `TokenBudget`: per-run + cumulative DOLLAR ceilings (AC-C — FR-21 "per-run and cumulative scopes, same as FR-18").** A `CostCap` struct (record module `domain::cost`) carrying the two FR-21 scopes in MICRO-DOLLARS: `per_run: Option<Micros>` + `cumulative: Option<Micros>` (structurally identical to 3-2's `TokenBudget`, but the ceiling is money not tokens). Either/both may be unset (an unset scope never breaches). Record whether it derives `Serialize` (Fleet cost view + breach payload). Record the enforced scope: enforce BOTH on every evaluation — the per-run dollar breach checks the current Run's derived cost, the cumulative dollar breach checks the lifetime derived cost — reusing 3-2's `BreachScope::{PerRun, Cumulative}` VERBATIM (no new scope enum). A `CostCap` set with no Rate is inert (AC-B). NO token field (that is `TokenBudget`, 3-2). Naming discipline: the dollar ceiling type is `CostCap` (matching the PRD glossary "Cost Cap"); the token ceiling stays `TokenBudget`.

8. **The dollar evaluator REUSES 3-2's `BreachDecision`/`BreachScope`/`BreachAction`/breach path — greenfield is only the cost math + `CostCap` (AC-C — AD-7; the story's efficiency crux).** The enforcement DECISION machinery is DONE (3-2): `BreachDecision { WithinBudget | Breached { scope, action, limit, observed } }`, `BreachScope`, `BreachAction`, the `≥` threshold, the per-run-before-cumulative precedence, the per-Run latch, the always-recorded breach event, and the Epic-1 `pause`/`stop`/`warn` execution in `Supervisor::enforce_budget`. ### The dollar design (the story's core value — define exactly)

**Six things are the deliverable: `Micros` + a per-direction `Rate` + a pure cost derivation, a `CostCap`, a dollar evaluator REUSING 3-2's decision, the `EstimateLabel` + the single currency module, the config keys with no-retro-repricing, and the dollar fields on the breach event + Fleet view.** The unifying tension: dollars must be BILLING-CORRECT (integer micros, never `f64`, explicit rounding — AD-8 + the 3-1 money lesson); the cap must be checked EXACTLY where 3-2 checks tokens (the SAME commit-path choke point — AD-7, no new race); the enforcement must REUSE 3-2's honest lifecycle path intact; every rendered dollar must carry its `EstimateLabel` through the ONE currency module (AD-8); and no-Rate must be honestly INERT (AC-B), never a fabricated `$0.00`.

**Key design decision 1 — money is integer micro-dollars with round-half-up, NEVER `f64` (THE crux — billing correctness).** THE decision this story lives or dies on. Represent all money as **integer micro-dollars** (`Micros(i64)`, 1 dollar = 1_000_000 micros). Rationale: (i) AD-8's honesty spine + the 3-1 `u64→i64` retro lesson — a cost cap is a financial guardrail; enforcing it on a lossy `f64` (which cannot represent `$0.01` and drifts over a long accrual) is dishonest; (ii) `$/1M`-token rates yield sub-cent per-token costs (`$3/1M` = 3 micros/token), so cents would truncate to `0` and micros preserve them. The derivation `cost = tokens × price_micros_per_1m / 1_000_000` per direction uses a **`u128` intermediate** for the multiply (a runaway `u64::MAX` tokens × a large rate must not wrap — it SATURATES) and **round-half-up** on the divide (add `500_000` pre-divide; deterministic, testable). Record `i64` signedness (a cost is never negative, but `i64` lets remaining/headroom saturate to `0` honestly and leaves room for a future reconciliation credit). The RENDER layer (AD-8's single module) is the ONLY place micros become `$X.XX` — the ledger/cap/wire keep micros. Exhaustive pure unit tests (Task 1) cover the rounding boundary, input≠output, and the overflow-saturation — this is money, so the tests are the spine, not an afterthought.

**Key design decision 2 — the Rate is per-direction (input ≠ output); a half-Rate is inert (AC6, AC-B — FR-20).** FR-20 + the glossary say "input and output rates supported" (`[ASSUMPTION: split rates]`), and the 3-1 ledger ALREADY splits `input_tokens`/`output_tokens` — so the two directions price independently: `cost = input_tokens × rate.input/1e6 + output_tokens × rate.output/1e6`. This matters because real models price output several× input; a single blended rate would misprice every run. RECOMMENDED: a `Rate` is "supplied" only when BOTH directions are present — a half-configured Rate is treated as no-Rate (inert, AC-B), avoiding a silently-half-priced ledger. Record the per-model-key scope (FR-20 says "per Agent Instance or per model key") — RECOMMENDED v1 per-INSTANCE Rate only; per-model-key is a config-shape extension recorded as deferred if it does not fit cleanly.

**Key design decision 3 — REUSE 3-2's evaluator/breach/lifecycle path; greenfield is only the money (AC7, AC8 — AD-7, the efficiency crux).** The decision machinery (`BreachDecision`/`BreachScope`/`BreachAction`, the `≥` threshold, per-run-first precedence, the per-Run latch, `record_breach` + `enforce_pause`/`enforce_stop`, the always-recorded event, the ordering guarantee) is DONE (3-2). 3-3 adds ONLY: the money types + derivation, the `CostCap`, a thin `CostEvaluator` returning 3-2's `BreachDecision`, and the dollar fields on the event. RECOMMENDED a sibling `CostEvaluator` over a generic evaluator (keeps 3-2's token tests + the two evaluators independently readable; `BreachDecision`'s `limit`/`observed` are already `u64` and unit-agnostic — reconcile `Micros(i64)`→`u64` at the boundary honestly, or store micros as `u64` in the decision). The supervisor's `enforce_budget` runs BOTH evaluations in the same choke point; the latch distinguishes a token breach from a dollar breach of the same scope (keyed `{(Kind, BreachScope)}`), so each fires ≤1/Run and BOTH can fire on the same event (the action is identical). This is why 3-3 is ONE coherent story, not a rebuild.

**Key design decision 4 — no-Rate is honestly inert; no-retroactive-repricing (AC-A, AC-B — FR-20, AD-8).** With NO Rate: the ledger derives NO dollars (cost ABSENT, never `$0.00` fabricated), a `CostCap` cannot be enforced (inert + SAYS SO — a diagnostic, not a silent no-op, not a fake breach), and every TOKEN feature works fully. No-retroactive-repricing: a Rate change re-prices FUTURE consumption only; historical dollars keep the Rate in force when consumed — implemented by pricing each event at the Rate resolved AT ITS commit (persist a per-event effective Rate as an engine-side ledger column, or a Rate-change history priced by `occurred_at` — Task 4; RECOMMENDED per-event Rate, the most literal reading of "the Rate in force when consumed"). A Rate changed while `running` applies to the NEXT event (mirrors 3-2's live-config AC-B + the no-retroactive-un/re-breach discipline).

### Test robustness (retro-driven — read before writing a single test)

**3-3 has TWO test surfaces: (a) the PURE money math — exhaustive, instant, cross-OS by construction — and (b) the dollar-cap enforcement integration — the same cross-OS-fragile shape the Epic-2 retro flagged. Put the bulk of coverage in (a); reuse 3-2's robust harness for (b).**

- **The money math is pure — test it exhaustively HERE (billing correctness).** The `cost_micros` derivation + the `CostEvaluator` + the dollar-string→micros parse + the currency render are pure `std`, so their tests are instant and identical on every OS. This is BILLING MONEY — the boundary/precision/overflow coverage lives here, not in a flaky integration test: zero tokens; input-only/output-only; **input≠output rate**; the **round-half-up boundary** (a count landing on a half-micro); the **overflow saturation** (`u64::MAX` tokens × a large rate proven to saturate not wrap); a zero rate; the `≥` micro-dollar cap boundary (cost EXACTLY at the cap breaches; one micro below does not); the parse rejecting sub-micro/non-numeric. NFR-3 ≥95% is easy to hit here because every branch is a cheap pure test.
- **The failure mode to avoid (retro AI-35/38).** The Epic-2 retro found agent-spawning tests using the "spawn a real agent + poll a dump file on a wall clock" `_live` pattern were cross-OS-fragile — several were gated Linux-only because timing raced on macOS/Windows. Do NOT build the dollar-cap enforcement tests as "start the agent, sleep N ms, assert paused."
- **The robust pattern to USE (inherited from 3-1/3-2).** Drive the Rate'd instance through the **surviving-engine harness `start_via_surviving_engine`** (`crates/kt/tests/agent_cli.rs:43`) so it is genuinely `running` under a real supervising engine. Gate progress on a **readiness handshake + committed-STATE polling**: set a `Rate` + a small `budget.dollars.cumulative`, emit a KNOWN token total via `fake_agent --emit-usage` whose DERIVED cost crosses the cap, then POLL THE COMMITTED LIFECYCLE STATE (query the store / `kt agent show --json`) until `paused` (or `stopped` for the `stop` action) — asserting on durable committed state, NOT a wall-clock sleep. Because the dollar evaluator is synchronous inside the ingestion path (same as 3-2's token one), the transition commits as soon as the breaching event is ingested. For `warn`, assert the state stays `running` AND a dollar breach event is recorded. For AC-B inert, assert a `CostCap`-set-no-Rate instance keeps running (no dollar enforcement) while token enforcement still fires.
- **Determinism levers.** Keep the emitted token totals + the Rate fixed so the derived cost is EXACT (`Rate` input=output=`$1/1M`=1 micro/token, cap = the cost of exactly N tokens; emit N tokens for the `≥` boundary, N-1 for no-breach). For input≠output, set distinct rates + distinct input/output token sentinels and assert the summed cost. For the live-Rate-change test (AC-A no-retro), start under a Rate, accrue, change the Rate, emit more, and assert the historical dollars kept the old Rate while the new event used the new one.
- **Run the 3-OS CI matrix EARLY (retro AI-37).** The cost math, the evaluator, the config parse, the currency render, and `fake_agent --emit-usage` are all pure `std` — there is NO legitimate reason for a dollar-enforcement test to be OS-gated. If a test seems to need Linux-only gating, the harness is wall-clock racing — FIX the harness. Run Linux/macOS/Windows on the FIRST PR (AI-37); record the Windows posture of every enforcement integration test explicitly (all pass on all three).
