# Story 3.1: Meter self-reported usage into one durable ledger

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want the engine to ingest the agent's own usage accounting into a per-instance Usage Ledger,
so that consumption is tracked from day one. (FR-19 self-reported half)

## Acceptance Criteria

Verbatim from `epics.md` Story 3.1 (the FIRST story of Epic 3 — Cost Governance). The three headline ACs are: usage batches emitted by a `self-reported` adapter land in the append-only `usage_events` table with the AD-7 minimum shape, one transaction per event, **without double-counting** even when a batch is replayed (AC-A); a **Run** is delimited exactly as the span from a `starting` transition to the next terminal state, and per-run totals reflect it (AC-B); and the active Metering Source is visible in Fleet listing detail (AC-C). The derived criteria below make the `UsageEvent` domain shape, the `MeteringSource` ingestion port (AD-7 — the ingest side of the pipeline seam), the append-only `record_usage_event` + read/rollup `StateStore` methods (one txn per event, AD-6), the idempotency/replay-dedup key, the Run-id derivation, the `usage`-in-Fleet surfacing, and the `AgentAdapter` usage-reporting contract addition (with its CONTRACT_VERSION bump) explicit and testable.

> **CRITICAL SCOPING (read before AC-A):** This is the **FIRST** metering story and it sets the foundation for ALL of Epic 3. It delivers **capture → ledger ONLY**: the `self-reported` half of FR-19 (`engine-observed` is 3-4), landing usage into ONE durable ledger. It BUILDS ON Epic 1 (which froze the `usage_events` DDL to AD-7's minimum shape, added `count_usage_events` returning `0`, and seeded `FleetEntry.usage = None` as the honest Epic-1 placeholder) and Epic 2 (config/secrets — untouched here). It introduces: (1) a `UsageEvent` domain type + the `MeteringSource` **ingestion** port (AD-7's ingest seam — the trait `ports/mod.rs` reserves) with a v1 self-reported impl; (2) the append-only `record_usage_event` write + the usage READ/rollup methods on `StateStore` (one transaction per event — AD-6); (3) an idempotency/replay-dedup discipline so a re-delivered batch does not double-count; (4) the **Run** span (`starting`→next terminal) + a per-instance Run-id the supervisor stamps on every event; (5) `usage` surfaced in Fleet listing detail (making the Epic-1 `None` seed real) + the visible active Metering Source; and (6) the `AgentAdapter` contract addition — a usage-reporting method — plus the `fake_agent` behavior that emits self-reported batches for tests. It is **EXPLICITLY OUT OF SCOPE** to build: budget/enforcement/`BudgetEvaluator`/`BreachDecision` (3-2 — the ledger COMMIT PATH is the seam 3-2 hooks, so make the commit path a clean single choke point but wire NO evaluator), dollar Rates/derivation/`EstimateLabel` (3-3), `engine-observed` loopback metering (3-4), and usage/cost READ surfaces beyond the Fleet-detail `usage` totals + the AD-8 currency-rendering module (3-5 — this story renders tokens only, NEVER a dollar figure). 3-1 is capture→ledger.

1. **AC-A (verbatim — usage batches land append-only, one txn per event, no double-count).** **Given** the mock adapter declaring `self-reported` and emitting usage batches **when** usage arrives (including a replayed batch) **then** UsageEvents land in the append-only `usage_events` table with the minimum shape {instance id, run id, input tokens, output tokens, metering source, timestamp} (AD-7), one transaction per event, without double-counting. The `usage_events` DDL is ALREADY frozen to this shape (Epic 1 — `id, instance_id, run_id, input_tokens, output_tokens, metering_source, occurred_at`), so 3-1 needs **no breaking migration**: it POPULATES the table it inherited. Each ingested event is written in its OWN transaction (AD-6 — the ≤1s durability bound the WAL/`synchronous=NORMAL` substrate already guarantees applies per-event). "Without double-counting" is the REPLAY guarantee: a self-reporting agent may re-send a batch (the FR-19 "delayed batches reconcile … without double-counting" consequence + UJ-1's batch-reconcile edge case), so ingestion MUST be idempotent on a stable per-event key (record the key as a Decision — RECOMMENDED a `(run_id, sequence)` monotonic ordinal the agent supplies, so a re-delivered event is recognized and skipped, NOT re-inserted).

2. **AC-B (verbatim — a Run is `starting`→next terminal; per-run totals reflect it).** **And** a Run is delimited exactly as the span from `starting` to the next terminal state, and per-run totals reflect it. Per AD-7's Run definition (verbatim: "the span from a `starting` transition to the next terminal state (`stopped`/`failed`) of that Agent Instance"). At each `starting` transition the supervisor MINTS a fresh Run id (record the derivation — RECOMMENDED a monotonic-time-plus-nonce or a per-instance counter; it must be unique per run and stable for that run's lifetime) and stamps it on every `UsageEvent` ingested during that Run. A per-run total is the sum over `usage_events` scoped to `(instance_id, run_id)`; the cumulative total is the sum over all of the instance's rows. Restart-Policy restarts (story 1-6) each cross `starting` again, so a restarted instance opens a NEW Run with its own id — per-run totals never bleed across a crash/restart boundary. (Note: "Run" is absent from the PRD Glossary — the spine flags this as a PRD open item; this story treats AD-7's definition as authoritative.)

3. **AC-C (verbatim — the active Metering Source is visible in Fleet listing detail).** **And** the active Metering Source is visible in Fleet listing detail. The Metering Source is ALREADY resolved at registration (FR-19 hard line, story 1-3) and persisted on the registry row (`RegistryInstance::metering_source: String`), and Story 1.7's Fleet listing already reads per-instance detail. 3-1 SURFACES it: the `metering_source` appears in `kt agent list`/`show` detail (human + `--json`) alongside the now-real `usage` totals. This is a read-surfacing of state that already exists — no new resolution logic.

### Derived / consequence criteria (make explicit; enforced by tests)

4. **The `UsageEvent` domain type is the AD-7 minimum shape, and NOTHING more (AC-A).** A `UsageEvent` struct in the engine `domain` (record the module — RECOMMENDED `domain::usage` or `domain::metering`) carrying exactly {instance id (or `InstanceName`), run id, input tokens, output tokens, metering source, timestamp} plus the replay-dedup ordinal (AC-A key). Token counts are non-negative integers (record the type — RECOMMENDED `u64`, matching the SQLite `INTEGER` column decoded via `.max(0) as u64`, mirroring `count_usage_events`). NO dollar field, NO `EstimateLabel`, NO budget/headroom field — those are 3-3/3-5; a `UsageEvent` this story is tokens-only. Record whether the type is `Serialize` for the AD-14 wire (see AC10) or purely a DB/domain shape.

5. **The `MeteringSource` ingestion port + a v1 self-reported impl (AC-A — AD-7, AD-1).** Introduce the `MeteringSource` **ingestion** port (the AD-1 side port `ports/mod.rs` reserves, distinct from the `ktesio-adapter-api::MeteringSource` *enum* that merely DECLARES the source kind — record this naming carefully so the port and the declaration enum do not collide; RECOMMENDED name the port `UsageSource` or `MeteringIngest` to avoid shadowing the enum). The port's job: yield `UsageEvent`s from a running instance. The v1 impl is **self-reported**: it reads the batches the agent emits over the declared channel (record the channel — see AC6) and turns them into `UsageEvent`s. The `engine-observed` impl (loopback listener) stays a DEFERRED impl behind this SAME port (3-4) — build none of it. The port lands `UsageEvent`s into the ingestion→commit choke point (AC7), never writing the ledger directly.

6. **The self-reported channel: how the agent's usage reaches the engine (AC-A — the mechanism, AD-12).** Record PRECISELY (as the load-bearing Decision of this story) HOW a `self-reported` agent conveys usage to the engine. The adapter contract's `[metering] source = "self-reported"` declares THAT the agent reports; 3-1 must define the CHANNEL by which it does. Options to weigh + record one: (a) a structured line convention on the agent's stdout the engine already captures (AD-12 — e.g. a `KTESIO_USAGE {json}` sentinel line the log-capture pipeline parses out); (b) a usage file the agent appends to under a path the engine hands it (like the 0600/dump-file precedent, but appended over the Run — NOT a one-shot startup dump); (c) an explicit `AgentAdapter` method the engine polls/awaits (see AC9). RECOMMENDED (a) the stdout-sentinel-line convention: it reuses the AD-12 capture the engine already owns, needs no new IPC, and is what `fake_agent` can emit deterministically for tests; the parser extracts `{run-relative fields}` and MUST tolerate/ignore malformed lines (a bad usage line is a diagnostic, never a crash, and never pollutes the agent's own output stream). Record the exact convention (prefix token, JSON field names — snake_case per AD-14 conventions) so `fake_agent` and any real adapter agree.

7. **Append-only `record_usage_event` + usage reads on `StateStore`, one txn per event (AC-A, AC-B — AD-6).** Extend the `StateStore` port ADDITIVELY (its doc already promises "usage-event writes" are added later) with: (a) `record_usage_event(&self, event: &UsageEvent) -> Result<RecordOutcome, StoreError>` — a single-statement INSERT (one transaction per event, AD-6), returning whether the row was newly inserted or was a recognized replay (AC-A dedup); (b) a usage READ — per-run + cumulative token totals scoped by `(instance_id[, run_id])` (record the exact method(s) — e.g. `usage_totals(name) -> UsageTotals` and/or `run_totals(name, run_id)`), summing `input_tokens`/`output_tokens`. Idempotency is enforced in the SCHEMA where possible (RECOMMENDED a `UNIQUE(instance_id, run_id, sequence)` index so a replayed event hits the constraint and is classified as a no-op replay — mirroring how `classify_insert` maps a `UNIQUE` violation, so dedup is a DB invariant, not just application logic; record if this needs a schema v3 additive migration for the index, or whether the frozen v1 DDL is amended — since Epic 1 froze the columns but NOT a uniqueness index, adding the index is an additive v3 migration). Keep `count_usage_events` (Epic 1) working. NO `BudgetEvaluator` call in this path — but structure the write as the single ledger-commit choke point 3-2 will hook (AC8).

8. **The ledger commit path is ONE choke point, evaluator-ready but evaluator-free (AC-A — AD-7 forward seam).** AD-7 mandates the pipeline `MeteringSource → UsageEvent → ledger transaction → BudgetEvaluator (inside the same commit path) → BreachDecision`. 3-1 builds the FIRST THREE stages and stops: all usage ingestion funnels through ONE engine method (record it — e.g. `Engine::ingest_usage` / a supervisor path) that constructs the `UsageEvent`, stamps the Run id, and calls `record_usage_event` in its own transaction. Structure it so 3-2 adds the `BudgetEvaluator` call INSIDE this same path with no re-plumbing (the AD-7 "inside the same commit path" rule). Record explicitly that NO other code path may write `usage_events` (AD-7's "no other code path may mutate the Usage Ledger" — the invariant 3-2's enforcement relies on). Add NO budget/breach logic, NO breach event.

9. **The `AgentAdapter` usage-reporting contract addition + its CONTRACT_VERSION bump (AC-A — AD-2/AD-3, FR-27/FR-30).** The `AgentAdapter` trait (in `ktesio-adapter-api`) today has `metering_source()` but NO usage-reporting surface. 3-1 adds the contract element that lets the engine obtain self-reported usage (the method OR the documented channel convention of AC6 — record which the contract carries; if the channel is a pure stdout convention (AC6-a), the CONTRACT change may be DOCUMENTARY (the manifest `[metering]` section's documented usage-line format) rather than a new trait method — record this precisely). ### The self-reported ingestion design (the story's core value — define exactly)

**Five things are the deliverable: a `UsageEvent`, a Run, a self-reported CHANNEL, an append-only replay-safe LEDGER WRITE, and ONE evaluator-ready commit CHOKE POINT.** The unifying tension: usage arrives ASYNCHRONOUSLY and possibly REDUNDANTLY (batches, replays) from an agent the engine does not fully trust, and must land EXACTLY ONCE in a durable ledger scoped to the right Run — while leaving the enforcement seam (3-2) clean.

| Concern | Mechanism | Surface |
| --- | --- | --- |
| **`UsageEvent` (AC4)** | The AD-7 minimum shape + a replay-dedup `sequence` ordinal; `u64` tokens; NO dollars/label. | new `crates/ktesio-engine/src/domain/usage.rs` (record module). |
| **Run span (AC-B)** | Minted at `starting`, closed at the next terminal; a per-run-unique id stamped on every event; a restart opens a new Run. | `supervisor` (mint at the `starting` transition; carry alongside supervision state). |
| **Self-reported channel (AC6)** | RECOMMENDED a `KTESIO_USAGE {json}` stdout-sentinel-line convention parsed out of the AD-12 capture; malformed lines skipped, never fatal, never on `kt` stdout. | the ingestion port impl + `fake_agent --emit-usage`. |
| **Append-only ledger write (AC7)** | `record_usage_event` = one-statement INSERT (one txn, AD-6); a `UNIQUE(instance_id, run_id, sequence)` violation → `DuplicateReplay` (no double-count as a DB invariant). | `StateStore` + SQLite impl + schema v3 index. |
| **Commit choke point (AC8)** | ONE engine method builds+stamps+records the event; the SOLE `usage_events` writer (AD-7 invariant); 3-2 adds `BudgetEvaluator` here. | `Engine::ingest_usage` / a supervisor path. |
| **Fleet visibility (AC-C, AC11)** | Real `usage` token totals from the reads + the persisted `metering_source`. | `fleet_entry_for` + `kt agent list`/`show`. |

**The idempotency / no-double-count design (AC-A — the security-of-correctness heart).** A self-reporting agent may re-send a batch (FR-19 "delayed batches reconcile without double-counting"; UJ-1's batch edge case). The ledger must recognize a re-delivered event and NOT re-insert it. RECOMMENDED: the agent stamps each usage event with a `(run, sequence)` ordinal monotonic within the Run; the engine records `(instance_id, run_id, sequence)` under a `UNIQUE` index, so a replay hits the constraint and `classify_insert`-style handling returns `DuplicateReplay` (a no-op, not an error). This makes "no double-count" a DATABASE INVARIANT, not fragile application bookkeeping — the same discipline the registry uses for duplicate names. Record the ordinal source precisely (the agent supplies `sequence`; the engine supplies `run_id`). If an agent cannot supply a stable ordinal, record the fallback (RECOMMENDED: without a stable key, dedup is best-effort and the story documents the limit — but the mock/`fake_agent` path, which is what AC-A tests, DOES supply one).

**The Run-id derivation (AC-B — get the boundary exactly right).** A Run = `starting`→next terminal (AD-7). Mint the id AT the `starting` transition in the supervisor (the same place 1-6's spawn record is armed). It must be unique per run and stable for that run (RECOMMENDED monotonic time + a nonce, or a persisted per-instance monotonic counter — record which; a persisted counter is more auditable, a time+nonce is simpler). Store the current Run id where ingestion can read it during the Run (RECOMMENDED beside the supervision/spawn state). At the terminal transition the Run closes; the next `starting` (including a Restart-Policy restart) mints a fresh id — so per-run totals never bleed across a crash/restart. Persist `run_id` on each `usage_events` row (the column already exists). Cumulative = sum over all the instance's rows; per-run = sum scoped to `(instance_id, run_id)`.

**The ingestion port vs the declaration enum (AC5 — avoid the name collision).** `ktesio-adapter-api::MeteringSource` is an ENUM that DECLARES which source an adapter uses (`self-reported`/`engine-observed`) — it already exists and is resolved at registration. The AD-1 "`MeteringSource` side port" the spine names is a different thing: the INGESTION trait that YIELDS `UsageEvent`s. Name the port distinctly (RECOMMENDED `UsageSource` or `MeteringIngest`) so it does not shadow the enum. The port has one v1 impl (self-reported, reading the AC6 channel); `engine-observed` (3-4) is a second impl behind the same trait. The port lands events into the AC8 choke point — it never writes the ledger itself (keeping the AD-7 single-writer invariant).

**The evaluator-ready, evaluator-free commit path (AC8 — the seam that makes 3-2 clean).** Build the pipeline HEAD: `channel → UsageEvent → (stamp Run id) → record_usage_event (one txn)`. Put it behind ONE method. Add NOTHING after the ledger write — no budget read, no evaluator, no breach event. But shape the method so 3-2 inserts `let decision = BudgetEvaluator::evaluate(&totals); if breached { supervisor.execute_breach(...) }` immediately after the commit, inside the same path, with no signature churn. Document the AD-7 invariant on the method: this is the SOLE `usage_events` writer. This is the 3-1 analogue of how 2-3 funnelled all display through one `display()` so 2-4 could hook masking in one place — here the funnel is the ledger commit, and 3-2 is the hook.

### Test robustness (retro-driven — read before writing a single test)

**This story spawns a real agent to observe self-reported usage — exactly the test shape the Epic-2 retrospective flagged as cross-OS-fragile. Get the harness right the FIRST time.**

- **The failure mode to avoid (retro AI-35/38).** The Epic-2 retro found that agent-spawning tests using the "spawn a real agent + poll for a dump file on a wall clock" `_live` pattern were cross-OS-fragile — **4 such tests were gated Linux-only** because the timing raced on macOS/Windows. `fake_agent`'s `--dump` file is a ONE-SHOT startup observation written before racing on stdout capture; it is NOT a model for OBSERVING USAGE OVER A RUN. Do NOT build the metering tests as "start the agent, sleep N ms, read a usage dump file, assert." That pattern is what got gated off two of three OSes.
- **The robust pattern to USE.** Drive the metered instance through the **surviving-engine harness `start_via_surviving_engine`** (`crates/kt/tests/agent_cli.rs:43`) — the same harness the lifecycle/adoption tests use to make an instance GENUINELY `running` under a real supervising engine that outlives the `kt` invocation. Gate progress on a **readiness handshake** (the instance reaching `running` / a committed transition the test can query), NOT a wall-clock sleep. Then assert on the LEDGER STATE (query `usage_events` / the usage-total reads / `kt agent list --json`) — durable committed state the test reads deterministically, not a timing-sensitive side file. For the ingestion itself, prefer asserting the COMMITTED ROWS over intercepting the transport: emit a known batch, wait for readiness + the row count to reach the expected value (poll the DB, which is deterministic), then assert totals + dedup.
- **Run the 3-OS CI matrix EARLY (retro AI-37).** Do not defer the Linux/macOS/Windows CI run to the end. The retro's AI-37 lesson: run the 3-OS matrix on the FIRST PR of this story so any cross-OS fragility surfaces immediately, not after the code is written to a Linux-shaped assumption. The `fake_agent` usage emitter + the sentinel-line parser MUST be pure `std` with NO OS-cfg (the OS-cfg grep gate covers `ktesio-conformance`), so there is no legitimate reason for a usage test to be OS-gated. If a metering test seems to need Linux-only gating, that is a signal the harness is wrong (wall-clock racing) — fix the harness, do not gate the OS. Record the Windows posture of every metering integration test explicitly (they should all pass on all three).
- **Determinism levers.** `fake_agent` should emit usage on a readiness-gated, count-bounded schedule (e.g. "emit exactly K events then idle"), so the test waits for K committed rows rather than a duration. The replay test emits a duplicate `sequence` deterministically. Keep the emitted token numbers fixed sentinels so totals are exact-match assertions.
