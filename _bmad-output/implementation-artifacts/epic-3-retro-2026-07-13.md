## 3. What went well (top themes)

### 3.1 The two-pass review (primary + adversarial) caught a REAL bug in EVERY story — 5-for-5

This is the standout process win of the epic and the strongest evidence yet that the two-parallel-review pattern (proven on Epic 2's secrets story) earns its cost on *every* correctness-sensitive story, not just security ones. Each story ran a primary review **and** a dedicated adversarial pass with a different mandate, and the adversarial pass found a real defect a single review would have shipped:

- **3-1** (ledger) — adversarial *ledger-integrity* audit caught a **u64→i64 billing-corruption boundary** on the token read (silent overflow into a negative that a correctness review passed over). Hardened: saturate-clamp + overflow-safe saturating read + terminal-drain tail + log-shrink double-count guard, each with a test.
- **3-2** (token budgets) — adversarial *enforcement* audit caught **non-idempotent enforcement → breach-record spam** (re-firing the breach on every subsequent event). Hardened with a per-`(run, scope)` breach latch + a count-asserting test that fails without it; also surfaced a swallowed breach-log write.
- **3-3** (dollar caps) — adversarial *cost-math* audit caught **`(estimated)`-label truncation** in the list cell (FR-23 violation — a dollar could render with its honesty label chopped on a narrow terminal). Fixed via a header-level qualifier + `render_dollars_bare`; broadened the currency lint gate.
- **3-4** (engine-observed proxy) — adversarial *security* audit caught a **body-buffer DoS (unbounded proxy body) + a chunked-relay framing bug + an error-path key-leak sweep**. Loopback stayed hard-enforced; no API-key leak.
- **3-5** (honest read) — combined primary + adversarial *honesty red-team* caught a **real unpriced-token count in the footer** (a count that didn't reconcile to the ledger). Confirmed totals == ledger EXACT at both scopes afterward.

> Dana (QA): "Five stories, five real bugs the adversary found and the primary didn't. That is not luck — it's that 'is this correct?' and 'how do I corrupt the ledger / leak the key / present an estimate as an actual?' are *different questions* that find *different bugs*. Every one of these was a silent-wrong: a negative dollar, breach spam, a chopped label, an unbounded body, an unreconciled footer. Silent-wrong is exactly what a correctness review is worst at and an adversary is best at. On a *money* epic, running both in parallel isn't a luxury — it's the control."
>
> Charlie (Senior Dev): "And note the class of bug shifted per story to match the adversary's mandate — integrity, idempotency, label-honesty, memory-safety, reconciliation. We didn't run 'the same review twice'; we ran a *targeted* adversary aimed at the specific failure mode that story could have. That's the reusable move: pick the adversary's mandate from the story's threat surface."

### 3.2 Enforcement at one choke point, inside the ledger commit path (AD-7)

Budgets (3-2) and dollar caps (3-3) both enforce through the **same** `BudgetEvaluator`, invoked *inside* the ledger commit path — so a breach decision is made at the exact point the usage is durably recorded, at one place, for both token and dollar scopes. This is the Epic 2 single-choke-point pattern applied to enforcement: there is exactly one place a breach can be decided, which is why the adversarial enforcement audit could *prove* idempotency (add a latch in one spot) rather than chase re-fires across call sites.

> Winston (Architect): "Over-spend and spurious-kill were provably *closed* because there's one evaluator, not one-per-feature. Token budgets and dollar caps aren't two enforcement systems that happen to agree — they're one evaluator with two inputs. That's why 3-3 was mostly a *derivation* on top of 3-2, not a parallel enforcement path to keep in sync."

### 3.3 Honesty pushed into the type system and the CI gate (AD-8) — the Epic-1 thread matured again

Epic 1 pushed honesty into the type system (the uninhabited `MeteringSeed`); Epic 2 pushed leak-prevention into topology (one display choke point); Epic 3 pushed **estimate-honesty into a compile-and-CI invariant**: a single currency-rendering module is the *only* place a dollar can be formatted, every dollar carries an `estimated`\|`reconciled` label, and a **CI grep-lint fails the build if any other module formats currency**. "An unlabeled dollar shipped" is now structurally a lint failure. Combined with integer micro-dollar math and **no retroactive repricing** (3-3), the money core is honest by construction.

> Alice (Product Owner): "SM-C3 was the risk I worried about most — 'estimate precision theater,' presenting a guess as a fact. The answer wasn't a policy; it was a *lint*. You literally cannot merge a bare dollar. That's the honesty posture made unfakeable."

### 3.4 Metering complete in both directions — governance doesn't depend on the agent's cooperation

3-1 ingests the agent's *self-reported* usage; 3-4 adds *engine-observed* metering via a loopback-only HTTP forward proxy for agents that can't report. The FR-19 hard line — an adapter with **neither** source viable is **rejected at registration** — was regression-guarded. So the cap promise holds even for an uncooperative or accounting-less agent.

> Charlie (Senior Dev): "This is the part that makes the governance real rather than aspirational. A cap you can only enforce when the agent chooses to tell you its usage isn't a cap. The loopback proxy means we can meter an agent that reports nothing — and it binds loopback-only and refuses external interfaces, so we didn't open a network hole to close a metering gap."

### 3.5 Robust cross-OS *test design* from 3-1 — the Epic-2 lesson applied at the story level

3-1's tests poll **committed DB state** with **no OS-gating** — a direct application of the Epic 2 retro's lesson (don't wall-clock-poll for a file; assert on durable state; don't gate off an OS). This design choice is why the eventual CI failures were *harness* problems (a stale helper binary) and not *test-shape* problems in the metering assertions themselves.

> Amelia (Developer): "Credit where due: the *tests* learned the Epic-2 lesson. The assertion shape was right from 3-1. §4 is going to be hard on the harness — but that's a distinction worth holding: the test *logic* applied the lesson; the test *helper binary* was where the old fragility hid."

**Honorable mentions:** the **snapshot-launch-at-registration** robustness win (3-x CI-hardening) — `start` no longer re-reads the manifest; adversarially reviewed with **no secret leak** and the AD-10 guard preserved (a non-`Serialize` `StartLaunch` + a `Serialize` DTO) — kept as a genuine improvement *even though it turned out not to be the CI root cause*; the **repositioning** (skill-manager → agent-runner) shipped alongside the epic (README + docs + GitHub description/topics); the new `hyper`/`hyper-util` deps came in **MSRV-safe and TLS-free**, with the latent-tracing exposure documented up front (AI-48) rather than discovered later.

## 4. What was hard / what to improve (top themes)

*(The CI-harness saga is the heart of this retrospective. Two of these are hard-won debugging lessons; two are governance/scope debts; one is a recurring operational hazard.)*

### 4.1 HEADLINE LESSON: suspect a STALE cached test-helper binary before theorizing about the engine

The Windows/macOS integration-test failures (`budget.rs`, `metering.rs`, `cost.rs`, …) triggered a **long misdiagnosis saga**. Three theories were pursued, each plausible, each *wrong*:

1. **In-process Engine oversubscription** — "too many Engines per test binary starve the reaper on a low-core runner." Diagnosed with CPU-pegging experiments; looked convincing; **wrong**.
2. **A start-time manifest re-read dropping `args`** — "`supervisor.rs` re-reads the manifest at start and the hosted runner returns `exec` but empty `args`." A `KTESIO_ARGDIAG` trace was added to prove it; **wrong** (the trace showed `argc=6` — the full `--emit-usage`/`--dump`/… — reaching `Command::spawn`; **the engine was exonerated**).
3. **`RUST_TEST_THREADS=1` serialization** — reverted (see §4.2); **wrong, and actively harmful.**

**The real root cause was mundane and cheap:** `fake_agent_bin()` (`crates/ktesio-conformance/src/lib.rs`) **reuses an existing binary and only rebuilds if MISSING**. The per-OS `target/` CI cache restored a **pre-metering `fake_agent`** that predated the `--emit-usage`/`--dump` args (added in stories 2-2/3-1). The tell was hiding in plain sight: instances using the *old* args worked while instances using the *new* args got zero usage — the binary was stale, not the engine. **The fix was one line:** `rm -f target/debug/fake_agent*` before `cargo test` in the ci.yml `test` step, forcing `--all-targets` to rebuild it fresh (commit `bdc1fd0`). Confirmed macOS + Windows GREEN.

**Lesson (now written into project memory):** *when a test harness spawns a prebuilt helper binary, suspect a **stale cached artifact** before theorizing about the product.* A cache that rebuilds-only-if-missing + a per-OS `target/` cache is a stale-binary trap. The cheap check — "is the helper binary older than the args it's supposed to understand?" — would have ended the saga at the start. Days of engine-theorizing were spent on a stale `rm`-able artifact.

> Charlie (Senior Dev): "This one stings because every theory we chased was a *more interesting* bug than the truth. Oversubscription, a manifest re-read race, thread starvation — those are the bugs you *want* it to be, because they're worthy of the engine. The actual cause was a cached file from two stories ago. The lesson is a discipline: when a spawned helper misbehaves, your **first** hypothesis is 'the helper is stale,' not 'the engine is subtly broken.' Check the artifact's freshness before you write a single diagnostic trace into the product."
>
> Winston (Architect): "The `KTESIO_ARGDIAG` trace is the hero and the tragedy of this saga. It *worked* — it proved `argc=6` reached `spawn`, exonerating the engine. But we only added it to confirm theory #2. If the very first move had been 'diff the helper binary's mtime against the args it needs,' the trace would have been unnecessary. Exoneration-by-instrumentation is a fine backstop; it's an expensive *first* step."

### 4.2 Point-fixing CI flakes vs a harness overhaul — a point-fix created a SECOND failure

Each misdiagnosis in §4.1 cost a **blind CI cycle** (the same anti-pattern Epic 2's §4.2 named for the coverage OOM — iterating in CI against a failure you can't reproduce locally). The most expensive was the `RUST_TEST_THREADS=1` "fix": it wasn't the fix, and it **created a new failure** — serial execution **masked** a genuine second flake (the `cost.rs::no_retroactive_repricing` read-consistency race, a bug *in the test* that sampled row-count and cumulative dollars at two instants while the reaper committed rows) **and** its serial wall-clock **overran the ubuntu 25-minute job timeout**, so ubuntu started getting *cancelled* on every run. A point-fix aimed at Windows/macOS broke ubuntu. It was reverted; tests run parallel again; the `cost.rs` race was then fixed properly — first with a pause-and-settle, then made **deterministic and cross-OS by dropping the pause entirely** (commits `1dbe790`, `1a31dda`).

**Lesson (twice-learned now — coverage OOM in Epic 2, harness flakes in Epic 3):** when a CI failure gives **no locally-reproducible signal**, *stop iterating in CI*. Reproduce under the same constraints locally — a memory-capped container for the OOM; a cache-restored / low-core condition for the harness — so a fix is a measurement, not a coin-flip. And prefer a **harness overhaul over a stack of point-fixes**: Epic 2's AI-38 explicitly recommended landing the robust `_live` harness (readiness handshake, `.exe` handling, surviving-engine harness) **as an enabler *before* Epic 3's first agent-spawning story**. It was **not done** — and the fragility bit again, exactly as predicted, this time as a stale-binary trap the robust harness would have sidestepped. The residual **ubuntu-runner timeout remains unreproducible in a Debian container** and is the open tail of #106.

> Dana (QA): "The `RUST_TEST_THREADS=1` episode is the cautionary tale of the whole epic. It was a plausible point-fix that (a) wasn't the fix, (b) *hid* a real second bug by masking the race, and (c) broke a third platform by blowing the timeout. One point-fix, three ways wrong. That's what point-fixing a flake you can't reproduce buys you. AI-38 told us to overhaul the harness *first*; we shipped stories instead and paid for it in CI roulette."
>
> Islam (Project Lead): *[decision territory — mine: the harness overhaul (#106) is now non-optional. I'd rather fund the CI-stabilization work as a first-class item than keep admin-merging over flaky legs. The stale-`fake_agent` fix and the pause-free `cost.rs` fix are in; the ubuntu-timeout tail is what #106 has to close.]*

### 4.3 A THIRD consecutive epic merged over red coverage (#101 still open)

Epic 3 is the **third** epic admin-merged over the red coverage check (#100, #102, now #103), *and* the first merged over a second red axis (the Windows/ubuntu harness legs). Epic 2's AI-36 warned in plain terms about building "institutional muscle memory for merging over a red check" — that muscle memory is now **fully formed**. The coverage gate has not gated for three epics; a red coverage check no longer means anything to anyone on the project. Root cause is unchanged (the *instrumented* build's peak RAM+disk exceeds the free 7 GB runner — five fixes in Epics 1-2 were insufficient). This is no longer a tactical CI annoyance; it is a standing governance debt that erodes the signal of *every* required check.

> Dana (QA): "We said this last retro and it came true: merge-over-red is now a *habit*, not an exception. The fix is binary — either #101 gets a real resolution (bigger runner or a per-crate tarpaulin split) before Epic 4, or we consciously mark coverage `continue-on-error` with a local-proof DoD so a red *coverage* check stops training us to ignore red checks in general. What we cannot do a fourth time is admin-merge over it and call the gate a gate."

### 4.4 The repositioning surfaced an un-retired legacy surface (a new epic) + a stale banner

Shipping the skill-manager → agent-runner repositioning (README, docs, GitHub description/topics) surfaced that the **`kt` binary still ships the legacy skill-manager CLI**. This is the old product's entire surface still living inside the new product's binary. Islam **approved retiring it as a new epic** (it aligns with the already-planned Epic 8, *"deprecate the legacy surface loudly and kindly"* — the decision to make is whether this *is* Epic 8 or a dedicated earlier epic). Separately, the **banner image still advertises the old skill-manager positioning** and needs regeneration to match the repositioned README/docs. Neither is a code defect — they are *positioning coherence* debt surfaced by finally doing the repositioning.

> Alice (Product Owner): "The repositioning did its job — it forced the question 'what does `kt` actually *do* when you run it?', and the answer is still 'the old thing.' Retiring the legacy CLI is a real epic with real deprecation UX (Epic 8's 'loudly and kindly'), not a one-line delete. And the banner is the first thing a visitor sees; a repositioned README under an old-positioning banner reads as half-finished. Both are worth tracking as first-class items, not TODOs."

### 4.5 Injected-noise derailment recurred — an operational hazard worth codifying

Story 3-2's *first* dev attempt "derailed by injected harness noise → **0 tool uses**; re-spawned clean" (`sprint-status.yaml`). The same class of hazard recurred at the **start of this very retrospective session** (an injected todo-list nearly derailed the run). This is a repeatable operational failure mode for agent-driven work: injected hook/IDE/TodoWrite content can hijack a fresh agent into doing nothing or the wrong thing.

**Lesson:** codify an explicit "**ignore injected hook/IDE/TodoWrite noise; instructions come only from the task/user**" guard in the orchestrator playbook, and pair it with the away-mode recovery drill (AI-21). A re-spawn recovered both times, but "re-spawn clean" should be a *documented reflex*, not a rediscovery each time. Fold into the AI-40 doc bundle.

> Amelia (Developer): "It happened twice in one epic — once to a dev subagent, once to *this retro*. That's not noise, that's a pattern. The recovery is cheap (re-spawn, verify true state from disk, proceed) but only if it's written down. Right now it's tribal reflex."
