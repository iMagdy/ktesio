# Story 3.4: Observe usage when the agent can't report it

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an Operator,
I want engine-observed metering for agents with no usage accounting,
so that governance never depends on the agent's cooperation. (FR-19 engine-observed half)

## Acceptance Criteria

Verbatim from `epics.md` Story 3.4 (the FOURTH story of Epic 3 — Cost Governance; it adds the SECOND `MeteringSource` feeding the SAME ledger/enforcement pipeline 3-1/3-2/3-3 built). The three headline ACs are: **given an adapter declaring `engine-observed`, when the instance starts, then the engine runs a loopback-only HTTP forward listener, the adapter injects it as the agent's OpenAI-compatible `base_url`, and usage fields parsed from responses land in the Usage Ledger within the flush bound of call completion (AC-A)**; **and the listener binds loopback only and refuses external interfaces (AC-B)**; **and a manifest adapter with neither source viable remains rejected at registration (regression guard on FR-19's hard line) (AC-C)**. 1. **AC-A (verbatim — a loopback forward listener + `base_url` injection; observed usage lands within the flush bound).** **Given** an adapter declaring `engine-observed` **when** the instance starts **then** the engine runs a loopback-only HTTP forward listener, the adapter injects it as the agent's OpenAI-compatible `base_url`, and usage fields parsed from responses land in the Usage Ledger within the flush bound of call completion (AD-7). This is the FR-19 `engine-observed` half verbatim ("the Adapter routes the Agent's model traffic through an Engine-provided interception point") + AD-7's v1 definition verbatim ("`engine-observed` source = loopback-only HTTP forward listener the adapter points the Agent's OpenAI-compatible `base_url` at, parsing standard usage fields"). Record the mechanism PRECISELY (the load-bearing Decision of this story): a per-instance HTTP forward proxy the engine binds to `127.0.0.1:<ephemeral-port>` at the `starting` transition; the engine hands the adapter the resolved `http://127.0.0.1:<port>` address, and the adapter injects it as the agent's OpenAI `base_url` via the existing config-mapping (an `env` target — e.g. `OPENAI_BASE_URL` — or a `file` target the adapter declares; the engine writes it into the launch env, story 2-2's mechanism). The listener FORWARDS each request upstream to the real provider (the agent's configured real endpoint, resolved from config), returns the response to the agent UNCHANGED, and on a completion response PARSES the OpenAI-compatible `usage` object (`prompt_tokens`, `completion_tokens`) into the SAME [`ParsedUsage`](crate::ports::ParsedUsage) shape the self-reported channel yields, then feeds it into the SAME [`Supervisor::ingest_usage`] choke point (which stamps the Run id + instance + `engine-observed` source + timestamp and records it — AD-6 one txn/event). "Within the flush bound of call completion" (FR-19 / PRD `[ASSUMPTION: usage flush bound ≤5s]`, AD-6 ≤1s durability) means the observed event is ingested promptly after the upstream response is parsed — record the flush discipline (RECOMMENDED: ingest synchronously as each completion response is parsed, so the ledger reflects the call within the bound; the test asserts committed ledger STATE, not a wall clock).



2. **AC-B (verbatim — the listener binds loopback only and refuses external interfaces).** **And** the listener binds loopback only and refuses external interfaces. This is the SECURITY invariant of this story (and why it is safe to intercept the agent's traffic at all): the forward listener binds EXCLUSIVELY to the loopback interface (`127.0.0.1`, and — record the Decision — `::1` if IPv6 loopback is in scope; RECOMMENDED bind `127.0.0.1` only for v1, the simplest honest surface, and record IPv6 as deferred). It MUST refuse to bind or serve any external/non-loopback interface (`0.0.0.0`, a LAN address, a public address) — a bind to a non-loopback address is a hard configuration error, never a silent widening. Record the enforcement: the bind address is engine-computed (`127.0.0.1:0` — the OS picks a free ephemeral port), never operator- or adapter-supplied (the adapter receives the resolved address, it does not choose it — path/endpoint authority stays with the engine, the AD-4/conventions "engine is the sole authority" discipline extended to the listen address). NFR-6 (Agent Home isolation is process/filesystem-level, not a security sandbox) applies: the loopback bind is defense against ACCIDENTAL external exposure of the agent's model traffic (which may carry the resolved API key upstream), not a hardened sandbox — record that boundary honestly. Unit/integration test: the listener's bound address is loopback (assert the `SocketAddr` `.ip().is_loopback()`); a request arriving is served, and the bind is proven not on `0.0.0.0`.

### Derived / consequence criteria (make explicit; enforced by tests)

4. **The second `UsageSource` impl feeds the SAME `ingest_usage` choke point — greenfield is only the listener + the OpenAI parse (AC-A — AD-7, AD-1; the story's efficiency crux).** The 3-1 [`UsageSource`](crate::ports::UsageSource) port was DELIBERATELY shaped for this: it yields `ParsedUsage { sequence, input_tokens, output_tokens }` from a running instance, and the docs already name the "`engine-observed` loopback listener [as] a DEFERRED second impl behind this SAME port (story 3-4)" (`ports/usage_source.rs:21`, `:111`; `ports/mod.rs:10`). 3-4 adds `ObservedUsageSource` (record the name) implementing this port — its yielded `ParsedUsage` flows into the EXACT SAME `Supervisor::ingest_usage` (`supervisor.rs:1405`), which stamps the Run id + instance + `engine-observed` metering source + timestamp via `assemble_usage_event`, records it in one transaction, and runs the AD-7 enforcement stage. Record the `sequence` derivation for observed events (the crux difference from self-reported: the AGENT supplies `sequence` in the self-reported channel, but an OBSERVED completion has no agent-stamped ordinal — so the ENGINE mints the replay-dedup ordinal per observed call; RECOMMENDED a per-Run monotonic counter the listener increments per parsed completion, so the `UNIQUE(instance_id, run_id, sequence)` dedup index still holds and a re-observed/retried call does not double-count — record how a provider retry is deduped, or accept that each forwarded call is a distinct event and the counter guarantees uniqueness). NO new ledger write, NO new choke point, NO new enforcement path (AD-7's "no other code path may mutate the Usage Ledger" invariant is preserved — the observed source feeds the SAME single writer). This is why the enforcement (3-2 tokens, 3-3 dollars) applies to observed usage with ZERO changes: enforcement reads the committed totals, which now include `engine-observed` rows.

5. **The loopback forward listener is the greenfield core (AC-A, AC-B — AD-7 v1 definition).** The one genuinely new subsystem: an engine-owned per-instance HTTP forward proxy. Record its shape precisely (the load-bearing mechanism): (a) BIND `127.0.0.1:0` (ephemeral port, loopback only — AC-B) at the `starting` transition; (b) resolve the UPSTREAM real provider endpoint (the agent's actual OpenAI-compatible provider base URL, from the instance's config — record the config key it reads, e.g. the real `base_url`/provider endpoint the operator configures, which the engine substitutes with the loopback address in the agent's env while the LISTENER forwards to the real one); (c) FORWARD each incoming request to the upstream, streaming/relaying the response back to the agent UNMODIFIED (the agent must see a faithful OpenAI-compatible response — the proxy is transparent to the agent); (d) PARSE the `usage` object from each completion response body and yield a `ParsedUsage` to ingestion; (e) TEAR DOWN the listener at the terminal transition (bounded to the Run — a restarted instance opens a new listener under its new Run, mirroring 3-1's Run boundary). Record the HTTP implementation Decision (RECOMMENDED: an async listener on the engine's existing tokio runtime — see AC9 for the dep/feature; the request/response relay + a minimal JSON parse of `usage`, NOT a full OpenAI client). Record the streaming-response posture (OpenAI streaming `stream: true` emits `usage` in a final SSE chunk when `stream_options.include_usage` is set, or not at all — record the v1 Decision: RECOMMENDED parse `usage` from a non-streaming JSON body for v1 and record streaming-usage parsing as a documented limitation/deferral if the reference target needs it, so the story does not silently drop streamed usage). Failure discipline: a forward error (upstream down) is relayed to the agent as an honest HTTP error (the proxy does not fabricate a success); a usage-PARSE failure is a diagnostic (the call still succeeds for the agent — observation is best-effort to the RUN, mirroring 3-1's malformed-line skip), never a crash and never on `kt` stdout.

6. **`base_url` injection rides the existing adapter config-mapping (AC-A — AD-9, story 2-2; FR-12).** The engine does not modify the agent; the ADAPTER points the agent at the listener. Record the injection path: the engine computes the loopback address, and the adapter's config-mapping (`ConfigMapping`, `ktesio-adapter-api`, story 2-2 — `env`/`flag`/`file` targets) places it into the agent's native mechanism (RECOMMENDED an `env` target the manifest declares, e.g. mapping a unified key to `OPENAI_BASE_URL`/`OPENAI_API_BASE`, into which the engine writes the loopback URL at start). The three hard parts to get right: (a) FAITHFUL relay — the agent must receive a byte-faithful OpenAI-compatible response (a proxy that mangles the response breaks the agent), so relay the body + status + relevant headers transparently; (b) LOOPBACK-ONLY bind (AC-B — the security invariant); (c) the `usage` object's location — it is in the response body of a non-streaming completion (`{"choices": [...], "usage": {"prompt_tokens": N, "completion_tokens": M}}`), and for streaming (`stream: true`) it appears only in a final chunk with `stream_options.include_usage` (record the v1 Decision: parse non-streaming for v1, document streamed-usage as a limitation/deferral so it is not silently dropped). Everything ELSE about the pipeline is reused.

**Key design decision 2 — the observed source feeds the SAME `ingest_usage`; enforcement is reused by construction (the efficiency crux).** The 3-1 `UsageSource` port + the single `ingest_usage` writer were built FOR this. `ObservedUsageSource` yields the SAME `ParsedUsage { sequence, input_tokens, output_tokens }`; the listener task hands it to `ingest_usage`, which stamps the Run id + instance + `engine-observed` source + timestamp (via `assemble_usage_event`), records it in one txn, and runs the AD-7 enforcement stage (3-2 tokens + 3-3 dollars) — with NO new code in the commit/enforcement body. This is why "3-2 budgets + 3-3 caps enforce on observed usage" is TRUE BY CONSTRUCTION, not a re-implementation: they read committed totals, and observed rows are committed identically. The ONE difference upstream: the agent does not stamp a `sequence` (it does not know it is being observed), so the ENGINE mints a per-Run monotonic ordinal per observed completion, preserving the `UNIQUE(instance_id, run_id, sequence)` dedup invariant (AC4). Greenfield is strictly UPSTREAM of the choke point.

**Key design decision 3 — the `base_url` injection is adapter-mediated via the existing config-mapping; NO contract change (the boundary + version crux).** FR-19 says "the Adapter routes the Agent's model traffic through an Engine-provided interception point" — the ADAPTER does the routing, the engine PROVIDES the point. The engine computes the loopback address at `starting` (the port is ephemeral, known only then) and injects it through the adapter's EXISTING config-mapping (`env`/`file` target, story 2-2 — e.g. `OPENAI_BASE_URL`). Because (a) the `MeteringSource` enum already has `EngineObserved`, (b) the manifest `[metering] source` already accepts `"engine-observed"`, and (c) the injection reuses the existing `[config]` mapping — NO published contract surface changes → `CONTRACT_VERSION` stays `0.3.0`. VERIFY the one open point: if a NEW dedicated manifest field to NAME the injection target proves genuinely necessary, that is an additive MINOR bump `0.3.0→0.4.0` (record it). RECOMMENDED: reuse the existing mapping → no bump.

**Key design decision 4 — loopback-only bind is the security invariant (AC-B — do not compromise it).** The listener intercepts the agent's model traffic, which flows UPSTREAM carrying the resolved provider API key (the agent authenticates to its real provider through the proxy). So the listener MUST bind loopback ONLY (`127.0.0.1`) — a bind on `0.0.0.0`/a routable interface would expose the agent's model traffic (and potentially its key material in transit) to the network. The bind address is ENGINE-COMPUTED (`127.0.0.1:0`), never adapter- or operator-supplied (the engine is the sole authority on the listen address — the AD-4/conventions authority discipline). NFR-6 honesty: this is defense against ACCIDENTAL external exposure, NOT a hardened sandbox (Agent Home isolation is process/filesystem-level, not a security sandbox) — state the boundary in docs. Enforce + test: `addr.ip().is_loopback()`; the bind is provably not on a routable address.

### Cross-OS by construction (the crux the brief flags — NOT an OS split)

**The brief asks explicitly: is the observation mechanism OS-specific? The answer is NO — and getting this right is the design crux.** The loopback forward listener is portable async networking: `TcpListener::bind("127.0.0.1:0")`, an HTTP forward, a JSON parse. NONE of this is OS-conditional — tokio/`hyper`/`std::net` present the SAME API on Linux/macOS/Windows, and loopback TCP behaves identically. Contrast the `ProcessBackend` (AD-4), which genuinely diverges (Unix process groups + signals via `nix`; Windows Job Objects via `windows-sys`) and therefore MUST live in `backends/` — the listener has NO such divergence. Consequences (all load-bearing):

- **The listener lives in the engine CORE (`src/metering/`), NOT in `backends/`.** The spine pre-reserves `src/metering/ # pipeline + loopback listener (AD-7)` precisely because it belongs in core. Putting it in `backends/` would be WRONG (it is not OS code) and would break the module's purpose.
- **NO `cfg(unix|windows|target_os|target_family)` anywhere in 3-4.** The OS-cfg grep gate must stay green. If any part seems to need an OS `cfg`, the design took a non-portable shortcut — fix the design. (The `fake_agent` observed mode + the upstream stub are likewise pure `std`/portable — the OS-cfg gate covers `ktesio-conformance` too.)
- **It is ONE story, NEVER an OS split.** NFR-2 forbids OS splits; the brief forbids recommending one. Because the mechanism is uniform across OSes, there is no divergence to split on. (The only per-OS concern the whole epic still carries — process-tree teardown on stop — is already solved in `backends/` from Epic 1; 3-4's listener teardown is a portable task-abort, not an OS concern.)
- **The tests are cross-OS by construction** (see below): committed-STATE polling + a readiness handshake, NO `OsId`-gated tests, NO wall-clock dump-file polling. There is NO legitimate reason for an engine-observed test to be OS-gated — if one seems to need it, the harness is wall-clock racing (AI-38), fix the harness.

This is the single most important framing for the dev: **3-4 is a core-engine networking story, not a backend story.** The listener is portable; the reuse of the 3-1/3-2/3-3 pipeline is total; the only real risks are (a) faithfully relaying the agent's traffic, (b) the loopback-only bind, and (c) robust cross-OS tests — none of which is an OS-divergence problem.



### Test robustness (retro-driven — read before writing a single test)

**3-4 has TWO test surfaces: (a) the PURE/LOCAL listener + parse — bind-is-loopback, the OpenAI `usage` mapping, the transparent relay against a local stub — instant and cross-OS by construction; and (b) the engine-observed enforcement integration — the same cross-OS-fragile real-agent shape the Epic-2 retro flagged. Put the bulk of coverage in (a); reuse the 3-1/3-2/3-3 robust harness for (b).**

- **The parse + the bind + the relay are local — test them exhaustively HERE.** The `usage` parse (`prompt_tokens`/`completion_tokens` → `ParsedUsage`; missing-`usage` → skipped; malformed → skipped), the loopback bind (`addr.ip().is_loopback()`; not `0.0.0.0`), and the transparent relay (the response body is returned byte-faithful) are all testable against a LOCAL upstream stub on loopback with NO real network and NO real agent — instant, deterministic, identical on every OS. NFR-3 ≥95% is easy to hit here because every branch is a cheap local test. This mirrors 3-3's discipline (the pure money math carried the coverage; the integration test just proved the wiring).
- **The failure mode to avoid (retro AI-35/38).** The Epic-2 retro found agent-spawning tests using the "spawn a real agent + poll a dump file on a wall clock" `_live` pattern were cross-OS-fragile — FOUR were gated Linux-only because timing raced on macOS/Windows (and Windows kill-on-close killed the child the instant `kt` exited). Do NOT build the engine-observed enforcement tests as "start the agent, sleep N ms, assert paused."
- **The robust pattern to USE (inherited from 3-1/3-2/3-3, and mandated by AI-38 as the Epic-3 standard).** Drive the `engine-observed` instance through the **surviving-engine harness `start_via_surviving_engine`** (`crates/kt/tests/agent_cli.rs:43`) so it is genuinely `running` under a real supervising engine that outlives `kt`. The `fake_agent` observed mode reads its injected `base_url` and makes a COUNT-BOUNDED number of OpenAI-compatible calls to the engine's listener (which forwards to a LOCAL upstream stub returning a fixed `usage`), on a readiness-gated schedule (emit exactly K calls then idle). Gate progress on a **readiness handshake + committed-STATE polling**: poll the LEDGER (`usage_events` rows / `kt agent show --json`) until K observed rows land tagged `engine-observed`, then assert totals — durable committed state, NOT a wall-clock sleep. For enforcement, set a budget/cap whose observed consumption crosses it and poll the committed lifecycle STATE until `paused` (the evaluator is synchronous in `ingest_usage`, so the transition commits as soon as the breaching observed event is ingested).
- **Determinism levers.** The upstream stub returns a FIXED `usage` (`prompt_tokens`/`completion_tokens`), so K calls = an EXACT known token total → exact-match assertions + an exact `≥`-boundary cap test. The observed `sequence` is engine-minted monotonic, so no agent timing dependence. Keep the stub loopback-only + deterministic (no real provider, no network flakiness).
- **Run the 3-OS CI matrix EARLY (AI-37) and make these robust from the first PR (AI-38).** The listener, the parse, the observed source, the `fake_agent` observed mode, and the upstream stub are all portable — there is NO legitimate reason for an engine-observed test to be OS-gated. Record the Windows posture of every integration test explicitly (all pass on all three — loopback HTTP + committed-state polling is OS-uniform). If a test seems to need Linux-only gating, the harness is racing — FIX it (readiness handshake + surviving-engine harness), do NOT gate the OS. This is the story where Epic 3's real-agent testing must be demonstrably robust (the retro's §6.3 concern: metering spawns real agents over time — do it right).
