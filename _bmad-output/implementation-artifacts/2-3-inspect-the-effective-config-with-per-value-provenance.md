## Story

As an Operator,
I want to see exactly what will apply on next start and where each value came from,
so that config debugging is never guesswork. (FR-13)

## Acceptance Criteria

The two headline ACs are the per-value SOURCE-LAYER rendering in effective-config inspection + the persisted `EffectiveConfig` snapshot written to the Agent Home at start (AC-A), and the honest secrets-seam note that the masking requirement (FR-14) binds only from the moment the secrets capability exists — story 2-4 (AC-B). The derived criteria below make the provenance rendering (human + `--json`), the snapshot FORMAT/PATH/LIFECYCLE, the exact start seam where the snapshot is written, and the 2-4 masking seam explicit and testable.

It BUILDS ON story 2-1's resolver (which ALREADY records the winning [`SourceLayer`](crates/ktesio-engine/src/domain/config.rs) per leaf — that was 2-1's ONE forward-design obligation, built FOR this story) and story 2-2's rendering (which ALREADY added a "Validated" column via [`EffectiveConfig::is_unvalidated`](crates/ktesio-engine/src/domain/config.rs) and applies the mapping at the `supervisor::start_inner` seam). 2-3 RENDERS the provenance 2-1 already recorded and PERSISTS a snapshot — it should need **little or no new resolver logic**. It does NOT re-open the layered model, the precedence rules, write-time validation (all 2-1, done), or the unified→native mapping (2-2, done). It does NOT deliver **secrets** (`secret:` resolution, `SecretString`, masking) — that is **2-4 (FR-14, AD-10)**. 1. **AC-A (per-value provenance rendering + persisted snapshot at start).** **Given** values set across multiple layers **when** I inspect the instance's effective config **then** every rendered value names its source layer (default / kind / instance / override), AND a persisted `EffectiveConfig` snapshot with the same provenance is written to the Agent Home at start (AD-9). The provenance is rendered in BOTH `kt agent config get <name>` (human table) and `kt agent config get <name> --json` (machine-readable), sourced from the [`SourceLayer`](crates/ktesio-engine/src/domain/config.rs) 2-1 already records per leaf (no new resolver logic). The snapshot is a file in the Agent Home (AD-6: "effective-config snapshots are files inside the Agent Home — never blobs in the DB"), written at the SAME start seam 2-2 applies the mapping, carrying every resolved leaf's value + its source-layer tag.

2. **AC-B (secrets masking seam — binds only from 2-4).** **And** no secret-classified keys exist at this point in the epic; the masking requirement for effective-config output binds from the moment the secrets capability exists (FR-14 — story 2-4). 2-3 therefore renders + persists values UN-masked (there is no secret to leak — `KNOWN_KEYS = ["model"]`, and a `secret:` value is an ordinary opaque string per 2-1/2-2). 2-3's obligation is to leave the rendering + snapshot so 2-4 hooks masking in cleanly: EVERY value's display goes through ONE render path (2-1's [`ResolvedValue::display`]) and the snapshot serialization goes through ONE encode path, so 2-4 makes exactly those two secret-aware. 2-3 MUST NOT fabricate a masking marker, resolve a `secret:` value, or build any secret machinery.

RECOMMENDED: write before the transition and treat a failure as a typed start failure (the snapshot is a promised AD-9 artifact, not a nicety) — record the decision + the error surface (a new typed variant or reuse of an existing one).

7. **Snapshot lifecycle: overwritten every start (AC-A — the "what will apply on NEXT start" promise).** Because the snapshot answers "what will actually apply on next start" (FR-13), it is REWRITTEN (overwritten in place) on EVERY successful start / restart, so it always reflects the config resolved for the CURRENT run — never a stale earlier resolution. Record this as an `[ASSUMPTION]`: the snapshot is overwritten each start (not appended, not versioned-per-start); a restart (2-1/1-6 restart path also flows through `start_inner`) refreshes it too. Record whether `kt agent config get` reads the LIVE resolve (RECOMMENDED — it already does, showing "what WOULD apply") vs the persisted snapshot; the persisted snapshot is primarily the durable AD-9 artifact for Hosts/debugging, and `config get` continues to resolve live.

8. **The 2-4 masking seam is left clean — ONE display path + ONE encode path (AC-B).** Provenance rendering and the snapshot both route every value through a SINGLE display/serialize path so story 2-4 can make masking a surgical change: the human table + `--json` + the snapshot all render a leaf's value via 2-1's [`ResolvedValue::display`] (or one shared helper), and 2-4 will make THAT path consult a `secret:`/classification check before emitting. Record the seam explicitly: 2-3 adds a "Source" column + a snapshot but does NOT branch value rendering on secret-ness (there are no secrets yet); 2-4 adds the mask at the single choke point. 2-3 MUST NOT add a `--reveal` flag, a masking marker, or any `secret:` branch.

9. **Output discipline + honest scoping notes (AD-12).** The "Source" column rides `kt agent config get`'s STDOUT (part of the result table); `--json` is pure JSON on STDOUT. Any residual note stays on STDERR. The stale 2-1/2-2 "provenance arrives in Epic 2.3" STDERR note is retired (AC3). No new interactive prompt (FR-34).
